## Блокирующие замечания

**Б1. `api` на стенде не стартует после слияния: `APP_FILES_ENCRYPTION_KEY` не передаётся в контейнер.** `infra/compose.prod.yaml` задаёт `SPRING_PROFILES_ACTIVE: prod`, а в блоке `environment` появилась только `FILES_STORAGE_DIR`. `FileCryptography` в `prod` без ключа бросает `IllegalStateException("APP_FILES_ENCRYPTION_KEY обязателен в prod")` → контекст не поднимается, healthcheck красный, `restart: unless-stopped` крутит контейнер. Описание PR и `docs/M04-participant-documents.md` предлагают создавать gitignored `infra/compose.files.override.yaml` и запускать с двумя `-f` — это не отражено ни в `infra/deploy`-скриптах, ни в M09 (`pr/25` тоже не добавляет `env_file` или эту переменную). «Минимальный diff compose» не означает «нерабочий compose»: достаточно одной строки по образцу `JWT_SECRET` — `APP_FILES_ENCRYPTION_KEY: ${APP_FILES_ENCRYPTION_KEY:?APP_FILES_ENCRYPTION_KEY is required in infra/.env.prod}`. Тогда `docker compose --env-file infra/.env.prod -f infra/compose.prod.yaml up` либо работает, либо падает с понятным сообщением на этапе интерполяции, а не в JVM. S3-переменные можно передать аналогично с пустыми default (`${APP_FILES_PROVIDER:-local}` и т.д.) — это ещё 6 строк, либо отложить до реальной настройки S3.

**Б2. Загрузка готового PDF/фото с телефона невозможна из-за `capture="environment"`.** `DocumentsPanel.tsx`: `<input type="file" accept="image/*,application/pdf" capture="environment">`. По HTML Media Capture при наличии `capture` браузер предпочитает захват с камеры: iOS Safari открывает камеру сразу, без пункта «Медиатека/Файлы»; Android Chrome ведёт себя так же при `capture` + `image/*`. То есть справку в PDF (самый частый формат от клиник) или уже сделанное фото с телефона не загрузить вовсе, а на десктопе атрибут игнорируется. Задание просит `accept + capture` как способ «загрузки с телефона», но в реализации это должно быть: основной input без `capture` (системный выбор файла на iOS/Android и так предлагает «Снять фото»), и, при желании, вторая кнопка «Сфотографировать» с отдельным `<input accept="image/*" capture="environment">`. Проверить на реальном iPhone/Android — PR это не делал (сказано в «Что не сделано»).

## Желательные замечания

**Ж1. Разделение ключей.** Один и тот же 32-байтный секрет служит ключом AES-256-GCM и ключом HMAC-SHA256 для подписи ссылок (`FileCryptography.sign` → `new SecretKeySpec(key, "HmacSHA256")`). Практической атаки нет, но это нарушение key separation: выведите подключи один раз в конструкторе — `encKey = HMAC(key, "flounder-files-enc-v1")`, `sigKey = HMAC(key, "flounder-files-sig-v1")` (HKDF-extract/expand на `javax.crypto.Mac`). Существующие файлы на стенде ещё не зашифрованы, значит менять формат можно сейчас бесплатно; после первого деплоя — уже нет (ключ не ротируется, перешифровки нет — это PR честно пишет).

**Ж2. Файл целиком в памяти на каждом запросе.** `readNBytes(10 MiB+1)` → `encrypt` создаёт вторую копию → `Files.write`; на скачивание `readAllBytes` + `decrypt` + `ResponseEntity<byte[]>`. До ~30 МБ heap на запрос при `-Xmx1024m` и `-XX:+ExitOnOutOfMemoryError` (контейнер убьёт себя). Для «загрузки справок 1000 участников в последний вечер» это реальный риск. Достаточно `CipherInputStream`/`CipherOutputStream` поверх `Files.newOutputStream`/`newInputStream` и `StreamingResponseBody`/`InputStreamResource` в контроллере; контракт `FileStorage` сменить на `InputStream`/`OutputStream`. Можно вынести в M04-followup, но до нагрузки на реальном соревновании.

**Ж3. Путь `/api/v1/public/documents/{id}/content` не публичный.** Эндпоинт лежит под `permitAll` `/api/v1/public/**`, но требует Bearer (иначе 404) — «подписанная ссылка» не работает как ссылка (нельзя открыть `<a href>`, поделиться, положить в `<img>`); фронт всё равно делает fetch с токеном и Blob. Из-за этого пришлось пробивать исключение в PWA-кэше (`publicApiCachePattern`) и ломать инвариант «всё под /public — кэшируемо и анонимно», на который завязаны Caddy/аналитика/QA05. Проще перенести на `/api/v1/documents/{id}/content` (authenticated, подпись остаётся как второй фактор и защита от CSRF-подобного перебора), убрать regex-исключение из `vite.config.ts` и спецслучай `signed-document → 404 для anonymous` в QA04 (станет обычный 401). Либо, если нужна именно ссылка без токена, — подписывать её так, чтобы токен был не нужен (сейчас подпись и так привязана к `userId`), и тогда убрать требование Bearer. Выберите одно; текущий вариант — худшее из двух.

**Ж4. Журнал доступа не фиксирует отказы.** `file_access_log` пишется только на успешных операциях (`log()` вызывается после проверок прав). Для 152-ФЗ/инцидент-анализа ценнее как раз `DENIED` с `user_id`, `file_key`/`document_id` и причиной. Добавить `DENIED` в CHECK и писать его в `ParticipantDocumentService.content/download` при `documents.access_denied`/`files.not_found` в отдельной транзакции (`REQUIRES_NEW`, иначе откатится вместе с исключением). Заодно индекс по `user_id` — выборка «кто что смотрел» по субъекту ПДн.

**Ж5. FK `uploaded_by`/`file_access_log.user_id → users(id)` без `ON DELETE`.** Удаление/обезличивание пользователя (право на удаление по 152-ФЗ, M02-followup) упрётся в FK. Решить сейчас: `on delete set null` для журнала (user_id nullable) или зафиксировать в docs, что удаление пользователя = soft-delete. Также `profile_id` FK не даёт удалить профиль с документами — это, наоборот, правильно, но нужен сценарий «удалить документы вместе с профилем».

**Ж6. Dev-режим с эфемерным ключом.** Вне `prod` при пустом ключе генерируется случайный ключ: в профиле `local` каталог `./data/files` переживает рестарт, а ключ — нет → все ранее загруженные документы дают 503 `files.corrupt`. Только WARN в логе. Предложение: в `local` писать сгенерированный ключ в `./data/files/.dev-key` (gitignored) и переиспользовать, либо требовать ключ, если каталог непуст.

**Ж7. `GlobalExceptionHandler.handleLargeUpload` различает лимиты по `request.getRequestURI().contains("/documents")`.** Хрупко (pr/33 добавляет свои `/documents`-пути для PDF-протоколов, конфликт уже есть). Лучше поднять `max-file-size` только для multipart документов через явную проверку размера в сервисе (она уже есть) и единый код `files.too_large`, а лимит импорта 5 МБ проверять в `imports` явно.

**Ж8. Мелочи.** `DELETE` разрешён только роли `PARTICIPANT` — организатор, загрузивший не тот файл, не может его убрать до появления экрана комиссии (зафиксировать как known limitation). `status` включает `NOT_UPLOADED` при том, что строка без файла невозможна — оставить, но отметить в docs. `file_access_log` не связан с `document_id` — после удаления документа восстанавливать «чей файл» можно только по `participant_documents`, которой уже нет; добавить `document_id uuid` (без FK). `playwright.documents.config.ts` — четвёртый отдельный конфиг Playwright во frontend; объединить с `playwright.organizer.config.ts` в следующем PR. `.gitignore`: строку `infra/compose.files.override.yaml` убрать вместе с Б1.

**Риски для стенда:**

1. **Новый именованный том `flounder_files`** монтируется в `/data/files`. Права: образ создаёт каталог с `chown app:app`, и Docker при первом монтировании пустого именованного тома копирует владельца из образа — работает только если том создаётся заново. Если `FILES_STORAGE_DIR` переопределить на другой путь (не созданный в образе) — каталог будет root-owned → `Files.createDirectories` упадёт → все загрузки 503 `files.storage_unavailable`. Не переопределять переменную без `mkdir/chown` в Dockerfile. Относительный путь в `FILES_STORAGE_DIR` сломает mount (`flounder_files:./data` невалиден).
2. **Ключ шифрования** — генерировать `openssl rand -base64 32` (ровно 44 символа, заканчивается на `=`), положить в `infra/.env.prod` как `APP_FILES_ENCRYPTION_KEY=…` (без кавычек; в M09 скрипты `source` этот файл — `=` в base64 безопасен, но проверить, что в конце нет пробела). До правки Б1 ключ в контейнер не попадёт и API не стартует. Потеря ключа = потеря всех документов: бэкап ключа хранить отдельно от бэкапа тома (M09 `backup.sh` том копирует, ключ — нет). Ротация не поддерживается.
3. **Миграция V031** — только `create table`, обратимая (`drop table file_access_log, participant_documents`), данных не трогает. Откат кода без отката миграции безопасен.
4. **Multipart-лимит поднят с 5 до 10 МБ глобально** — Caddy `request_body` лимит (если задан в M09) должен быть ≥ 11 МБ, иначе 413 от прокси без русского текста.
5. **Память**: до ~30 МБ heap на запрос документа при `-Xmx1024m` и `ExitOnOutOfMemoryError` (Ж2). Не запускать массовую загрузку до стриминга; следить за рестартами `flounder-api`.
6. **PWA**: service worker кэшировал `/api/v1/public/*`; новая сборка исключает документы — старые SW у пользователей обновятся при следующем заходе (`cleanupOutdatedCaches`), до этого документов в кэше всё равно нет (эндпоинт новый).
7. **S3 на стенде не включён** и без правки compose не включится; `app.files.provider=s3` при пустых endpoint/bucket уронит старт (`@Value` без default на `endpoint/bucket/keys`).
