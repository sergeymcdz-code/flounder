## Желательные

1. **Импорт Excel теперь шлёт `registration_confirmed`.** `RegistrationImportLookupService.java:70` публикует `RegistrationConfirmedEvent` для каждой созданной заявки; его слушает не только `PaymentReminderScheduler.confirmed`, но и `NotificationEventListener.confirmed:47` → письмо «Заявка подтверждена» каждому импортированному участнику с аккаунтом (раньше импорт писем не слал). Для импорта 200 строк с привязанными аккаунтами — 200–400 писем за один запрос. Если это осознанно — явно написать в PR и в `docs/13_Инструкция_пользователя.md`; иначе ввести отдельное событие (например `RegistrationFeeAssignedEvent`) только для напоминания или не публиковать `RegistrationConfirmedEvent` при `source=IMPORT`.
2. **`new ObjectMapper()` в горячем пути.** `EventResponse.payment():97` (вызывается при сериализации каждого события, в т. ч. в списках), `EventPublicLookupService.publicPayment:80`, `UpdateEventUseCase:39`, `EventPaymentSettings.fromJson`. Создание `ObjectMapper` — миллисекунды и память; плюс у «голого» маппера `FAIL_ON_UNKNOWN_PROPERTIES=true`: любой лишний ключ в `settings_json.payment` (ручная правка в БД, будущая версия DTO) даст `IllegalStateException` → 500 на `GET /events/{id}` и публичной карточке. Правка: инжектировать Spring-овый `ObjectMapper` (в `EventResponse` — статический экземпляр с отключённым `FAIL_ON_UNKNOWN_PROPERTIES`).
3. **Планировщик напоминаний — каждую минуту полный проход по событиям.** `PaymentReminderScheduler:24` cron `0 * * * * *` → `paymentReminderEventIds:34-53` каждую минуту грузит все события в 6 статусах (включая DRAFT и COMPLETED) и для каждого делает `venues.getTimezone` (запрос на событие). Для 50 событий терпимо, но: (а) проверка `hour==9 && minute==0` повторяется внутри `send:70-74` по текущему `clock.instant()` — если обработка пачки перейдёт за 09:00:59, остаток заявок молча пропускается до завтра; (б) пропущенный тик (деплой/рестарт в 09:00) = нет напоминаний в этот день. Правка: вычислять `now` один раз на запуск и передавать в `send`; окно 09:00–09:09 с дедупликацией «уже отправляли сегодня» (есть `lastAt`); ограничить выборку событий статусами с открытой/закрытой регистрацией и LIVE; получать timezone одним запросом (join venue).
4. **Счётчик повторов.** `eligible:57-62` считает `count<3` от всех строк outbox, включая первичное письмо. Если первичное не создалось (настройка организации была выключена, у участника не было e-mail), повторов будет 3. Мелочь; можно считать повторы по `delivery_key` суффиксу или хранить `kind` в payload.
5. **N+1 в `RegistrationMapper`.** `toResponse` для каждой заявки вызывает `fees.settings(eventId)` → `events.getById` и `users.findById(paidBy)` (`RegistrationMapper.java:46,59-62`). В списке организатора на 500 заявок это спасает только кэш первого уровня в рамках транзакции/OSIV. Лучше: `dueDays` получать один раз в `ListRegistrationsForReviewUseCase`/`ListMyRegistrationsUseCase` и передавать в маппер; имена `paidBy` — батчем `users.findAllByIds`.
6. **PER_EVENT в `assign` грузит все заявки события.** `RegistrationFeeService.assign:63-77` — `registrations.findByEventId(...)` на каждую заявку; при импорте 300 строк в режиме PER_EVENT — 300 полных выборок. Добавить запрос `existsByEventIdAndParticipantProfileIdAndIdNotAndStatusIn…` (или JPQL с условием по `fee_amount>0 or payment_status='PAID'`).
7. **Матрица QA04: judge исключён по подстроке пути.** `Qa04RoleMatrixIntegrationTest.java:51-52` — `if (actor.equals("judge") && e.path().contains("/payments/summary")) return 403`. Честнее добавить политику `manage-finance` (organizer/operator/platform_admin без judge) в TSV и в `switch` — тогда правило видно в таблице, а не в коде.
