На `main` сегодня для `parent@` этот запрос даёт 200 и переименовывает профиль родителя (ключ не меняется) — 500 только у профилей без ключа (`admin@` из V002).
- **Сценарий шага 3 (`docs/demo-script.md:122-131`):** `parent@` подаёт форму на вымышленного **Демова Тимофея, 18.04.2014, М** — в `docs/scripts/demo/out/set-M.json` фамилии «Демов» нет (0 совпадений), в сиде профиль с таким ключом создаёт только сама форма. Значит `imported == null`, ветка QA03-04 не выполняется, ответ 200. Повтор на репетиции и на демо — тот же ключ, идемпотентно. Reset по `reset.sql` удаляет заявки события, профиль родителя остаётся (так и записано в `demo-script.md:95`).
- **Вывод: для демо — не блокер** (путь не воспроизводится при следовании сценарию). Остаточный риск — импровизация: кто-то на телефоне вводит фамилию из списка (например, «Коновалов», которого скрипт предлагает искать на live) — на `pr/18` без guard это 500 на экране. Поэтому guard из п. 1 «Блокирующих» (409 с текстом) — обязательная страховка перед деплоем на стенд, а не косметика. Для MVP — major: нужна политика объединения профилей аккаунта и импорта (вместе с QA04-10 «подтверждение владения импортированным профилем» и вопросом «несколько детей на один аккаунт родителя») — отдельная задача после M04/M05, до появления реальных ПДн.
