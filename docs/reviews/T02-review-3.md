## Замечания (не блокирующие)
1. `common/api/ApiErrorResponse.java:10` — `List<?> violations` стирает тип `FieldViolation` в Swagger-схеме ошибки: фронт T04 должен различать `{field, message}` (валидация) и `{code, severity, message, …}` (scheduling) по форме объекта. Зафиксировать в описании T04 / в `docs/02_ТЗ_демо.md` §5 при следующей правке ТЗ.
2. `results/infrastructure/GeneratedCompetitionUnitStore.replace:59–82` vs `SwimResultsUseCase.save` T03: ввод результата блокирует заплыв (`CompetitionUnitRepository.lockById`, PESSIMISTIC_WRITE), а пересоздание — событие (`EventLockService`). Гонка «результат записан между проверкой `exists(results)` и `delete from competition_unit_entries`» даст нарушение FK `results.competition_unit_entry_id` (500) вместо 409. Для демо-нагрузки неактуально; при желании — в `replace` после проверки брать `select … from competition_units where event_discipline_id=? for update` либо в `SwimResultsUseCase` брать `EventLockService.lockForUpdate(eventId)`.
3. `results/application/UpdateCompetitionUnitEntryUseCase.java:65–76` — разбор `venue_meta.lanes` по-прежнему продублирован относительно `SchedulingData.pool` (замечание 2 второго ревью); `main` общего `PoolSpec` не принёс, так что оставлено осознанно. Кандидат на вынос в `organizations/VenueLookup.getLanes()` при T04/T06.
4. `scheduling/application/GenerateForEventUseCase.java:41–50` — у пропущенной (ненастроенной) дисциплины в `EventGenerationResponse` `runId = null`, `heats = []` — в Swagger-примере по-прежнему не показано (замечание 3 второго ревью, косметика для T04).
