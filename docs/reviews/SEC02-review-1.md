## Желательные

1. **N+1 в `list` для менеджера** (`ParticipantDocumentService.java:68-72`): `canManagerSeeDocument` вызывается на каждый документ и каждый раз выполняет `assertManager` (`access.assertCanManage` + `existsByEventIdAndParticipantProfileId`), `profiles.getById` и `exists…FORM` — 4 запроса на документ, хотя `assertManager` для этого же `profileId/eventId` уже выполнен на `:66`. Вынести расчёт «есть FORM-заявка владельца» в одну переменную до `filter` (или разделить метод на `assertManager` + чистый `profileConsent(profileId, eventId)`); в `review` (`:77` и `:80`) `assertManager` тоже выполняется дважды.
2. **Статус FORM-заявки**: `existsByEventIdAndParticipantProfileIdAndSourceAndParticipantUserId` и `findByEventIdInAndSource` не учитывают `status` — отозванная (`WITHDRAWN`) FORM-заявка владельца продолжает давать организатору доступ к профильным документам. Задание этого не требует, но правило «пока родитель не подаст заявку сам» естественно читать как «действующую». Решить с владельцем продукта; если исключать — одинаково в обоих местах (`ParticipantDocumentService:141`, `DocumentSummaryService:30`) и добавить случай в `documentConsentCases`.
3. **Тип на фронтенде**: `registration.types.ts:49` `participantUserId: string` → `participantUserId?: string | null` (поле теперь отсутствует у IMPORT-заявок); `mocks/fixtures.ts:116` при желании добавить IMPORT-фикстуру без поля.
4. Косметика: `RegistrationResponse.java:12` и `DocumentSummaryService.java:18,20` — полные имена классов inline вместо `import`; в `RegistrationImportLookupService:49-50` комментарий, почему снимок перезаписывается только для IMPORT (защита FORM-заявки того же спортсмена).
5. В описании PR и/или `docs/manual/Инструкция_администратора.md` стоит отметить, что для ранее импортированных заявок город/`sportMeta` остаются в БД до повторного импорта (в API уже не отдаются) — чтобы владелец не удивился при просмотре таблицы.
