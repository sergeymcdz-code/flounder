## Блокирующие замечания

Дефектов, требующих переписывания логики, нет. «До слияния» — только то, что иначе ветку нельзя будет влить после соседних PR:

1. **Конфликты при ребейзе (см. таблицу).** Порядок волны: M02 (#29) и M04 (#38) с высокой вероятностью уйдут в `main` раньше M03 (M03 помечен «после демо»), поэтому Codex должен ребейзить на актуальный `main` и разрешить:
   - `frontend/src/api/documents.api.ts` — **переименовать файл M03 в `protocols.api.ts`** (функция `downloadProtocol`), чтобы не делить имя с `documents.api.ts` M04 (документы участников). Обновить импорт в `PdfDownloadButton.tsx`.
   - `vite.config.ts` — после M04 исключение `.pdf` должно жить в `src/utils/publicApiCache.ts` (`publicApiCachePattern`), а не в лямбде `vite.config.ts`; добавить туда `&& !url.pathname.endsWith('.pdf')` и покрыть существующим тестом утилиты, если он есть в M04.
   - `http.ts` — после M02 сохранить `authenticatedFetch` из M02 и необязательный `accessToken` из M03: `headers: accessToken ? { Authorization: … } : {}` и `authenticatedFetch(path, { headers }, accessToken)` (без токена refresh не нужен — `authenticatedFetch` при `!accessToken` возвращает ответ как есть).
   - `GlobalExceptionHandler.java`, `qa04-endpoints.tsv` — объединить `case`/строки, оба набора нужны.

2. **`sport-platform/src/main/java/com/acme/sportplatform/documents/infrastructure/PdfRenderer.java:41-42` — шрифты (2 × ~0,5 МБ) читаются из classpath и парсятся заново на каждый рендер.** Это видно в собственных цифрах PR: «первоначальная загрузка шрифтов — 1446 мс» против 250–342 мс. Организаторские PDF не кешируются вовсе, т.е. каждое нажатие «Скачать PDF» — 1 МБ чтения из jar + разбор TTF + мусор в heap; на стенде с ограниченной памятью при 5–10 параллельных скачиваниях это заметно. Исправить просто: прочитать оба файла один раз в `byte[]` (в конструкторе или `static final`), а в `useFont` передавать `() -> new ByteArrayInputStream(bytes)`. Строка кода, тест `PdfRendererTest` не меняется.

## Желательные замечания

1. `documents/infrastructure/PdfRenderer.java` — нет ограничителя параллелизма: два публичных эндпоинта без аутентификации, промахи кеша на разных `slug` и все организаторские запросы рендерятся без очереди. Для демо-стенда хватит `Semaphore(2)` вокруг `builder.run()` с `tryAcquire(10 s)` → `BusinessException("documents.busy", "Сервер занят формированием PDF, повторите через несколько секунд")` → 503 в `GlobalExceptionHandler`. Защищает JVM от OOM при одновременных скачиваниях с телефонов на репетиции 17–18.10.
2. `results.html:34,38` — в колонке «Статус» у ранжированных строк печатается `VALID` (видно на образце, стр. 2). В бумажном протоколе статус нужен только для DNS/DNF/DSQ; для валидных строк выводить пусто или «—» (`th:text="${row.status == 'VALID' ? '' : row.status}"`). Публичная веб-таблица (`Protocol.tsx:184-192`) так и делает.
3. `DocumentDataService.java:59-61` — порядок видов: `session.orderNo → orderInSession (nulls last) → id`, тогда как публичный API (`PublicationReadRepository.disciplines`) — `s.order_no nulls last, d.order_in_session nulls last, d.created_at, d.id`. При `order_in_session = null` у нескольких видов нумерация «Вид № N» в PDF и на `/e/{slug}/start-list` может разойтись. Добавить `createdAt` в `EventDisciplineSummary` (если его там нет) или сортировать так же. Та же мысль про организаторский PDF: там нумерация идёт по всем видам, включая DRAFT, — приемлемо, но стоит написать в README образцов.
4. `start-list.html:17` + образец стр. 1: при `page-break-inside: avoid` на заплыв и текущих отступах на страницу помещается ровно 2 заплыва по 8 дорожек, ~35 % листа пустует (11 страниц на 25 заплывов). Уменьшить `padding` ячеек до 1 мм и `margin-bottom` заплыва до 2,5 мм — влезет 3 заплыва, протокол на треть короче. Не меняет тесты.
5. `DocumentService.java:21` — имя файла `Итоговый-протокол-<uuid>.pdf`. UUID в имени бесполезен пользователю; лучше `slug` или дата (`protocolHeader` уже отдаёт `startsAt`): `Стартовый-протокол-<slug>-2026-10-17.pdf`. Фронт всё равно подставляет своё имя через `link.download`, так что это только для прямых ссылок/писем.
6. `pom.xml` — `com.openhtmltopdf` 1.0.10 (2021) — проект на GitHub архивирован; живой форк `io.github.openhtmltopdf:openhtmltopdf-pdfbox` 1.1.x (PDFBox 3). Для демо оставить как есть (задание прямо назвало артефакт), но зафиксировать в `docs/decisions/` одной строкой, чтобы не забыть при переходе на PDFBox 3. Также `spring-boot-starter-thymeleaf` регистрирует MVC `ThymeleafViewResolver`, который REST-приложению не нужен (`PdfRenderer` собирает свой `SpringTemplateEngine`); достаточно `org.thymeleaf:thymeleaf-spring6` без стартера — меньше автоконфигурации и предупреждений о `spring.thymeleaf.*`.
7. `fonts/README.txt` — указать версию (2.004, из `fonts-noto-core` Debian) и точный источник (URL релиза/коммита), чтобы файл можно было верифицировать по хешу.
8. `results/application/ResultsProtocolLookupService.java:54-55` — `registered.get(…)`/`athletes.get(…)` без проверки на `null`: при нарушении целостности (регистрация удалена напрямую в БД) будет `NPE` → 500 без кода. FK защищают, но дешёвый `Objects.requireNonNull` с сообщением или `filter` по наличию сделают ошибку диагностируемой.
9. `security/DocumentsSecurityIntegrationTest.setMRequestIncludingLookupsGeneratesEachPdfUnderThreeSeconds` и `PdfRendererTest` — проверки по wall-clock (≤ 3000 мс) на общих раннерах GitHub могут мигать под нагрузкой. Порог — требование задания, оставить; но если тест начнёт флапать, не ослаблять, а вынести тайминг в `assumeTrue(!CI)` + печать длительности, как сейчас.
10. Кросс-PR: M04 (`pr/38`) вводит коды ошибок `documents.not_found`, `documents.access_denied`, `documents.not_pending` для модуля **`registrations`**, M03 — `documents.generation_failed` для модуля **`documents`**. По AGENTS.md п. 8 код = `module.reason`; коды M04 должны стать `registrations.document_*` (или `files.*`, который там уже используется) — замечание для ревью M04, здесь менять нечего.
11. Описание PR хорошее (эндпоинты, межмодульные контракты, «как проверить», ограничения). Не хватает только фиксации в `docs/02_ТЗ_демо.md` §5 (или §6.4) четырёх новых путей и правила «публичный PDF может отставать до 60 с» — одной таблицей.

- **Jar тяжелеет на ~8–9 МБ** (pdfbox, fontbox, openhtmltopdf, thymeleaf, шрифты) — сборка образа и первый `docker pull` на стенде чуть дольше; `dependency:go-offline`-слой в Dockerfile инвалидируется один раз.
- **Память/CPU:** рендер 200 заявок — 250–350 мс и короткий всплеск heap (PDF ≤ 200 КБ, но DOM/лейаут openhtmltopdf в разы больше). Без п. 3 правок одновременные скачивания с нескольких телефонов на репетиции могут упереться в память контейнера; проверить лимит JVM (`-Xmx`/`MaxRAMPercentage`) в compose стенда.
- **Публичный PDF отстаёт до 60 с** от публикации/исправления результата — на демо после «Опубликовать результаты» ждать минуту перед «Скачать PDF» на публичной странице (организаторский PDF — всегда свежий). Если это неудобно для сценария, в `PublishDisciplineResults`/`CorrectResult` можно инвалидировать `publicPdfCache` по `slug` — не входит в задание.
- **PWA:** `.pdf` исключены из SW-кеша, но уже установленный service worker у тестовых телефонов обновится только после перезагрузки страницы (workbox `skipWaiting`/`clientsClaim` — как настроено в проекте); до этого запрос `.pdf` с телефона может отдать HTML-оболочку — кнопка покажет «Сервер вернул файл в неверном формате.» — это ожидаемое и безопасное поведение, а не дефект.
- **Шрифты/AWT:** образ `eclipse-temurin:21-jre` (Ubuntu) — fontconfig/freetype на месте; openhtmltopdf с PDFBox не использует системные шрифты, но первый рендер на стенде всё равно проверить и посмотреть лог на `UnsatisfiedLinkError`/`fontconfig`.

## Что проверить на стенде после деплоя

1. Под организатором: «Заплывы» → «Скачать PDF» до публикации — файл `Стартовый-протокол-….pdf` открывается, кириллица, шапка (название/дата/площадка/организация), время старта в часовом поясе площадки, заплывы не разорваны между страницами, «Страница N из M», «Сформировано: …». «Открыть печатную форму» работает как раньше.
2. Аноним: `GET https://<стенд>/api/v1/public/events/<slug>/start-list.pdf` до публикации заплывов → PDF с текстом «Заплывы ещё не опубликованы или не сформированы.» (без фамилий); после «Опубликовать стартовый протокол» и ≤ 60 с — заплывы есть. `…/results.pdf` до «Опубликовать результаты» — без результатов; после — «Абсолют», возрастные группы, блок «Без места · DNS / DNF / DSQ», ничья 1,1,3, пометка CORRECTED после исправления (подождать 60 с).
3. Организатор другой организации: оба `GET /api/v1/events/{eventId}/documents/*.pdf` → 403 `events.access_denied`; без токена → 401; судья → 403. Несуществующий/черновой slug → 404 `events.public_not_found`.
4. Заголовки ответа (`curl -I`): `Content-Type: application/pdf`, `Content-Disposition: attachment; filename*=UTF-8''…`, `Cache-Control: no-store`; Nginx/прокси стенда не режет `Content-Disposition` и не кеширует `.pdf` по расширению (проверить конфиг `location`/`proxy_cache`).
5. С телефона (PWA): кнопка «Скачать PDF» на `/e/{slug}/start-list` и `/results` — файл сохраняется, а не открывается HTML; если показалось «Сервер вернул файл в неверном формате.» — перезагрузить страницу (обновление service worker) и повторить.
6. Нагрузочно: 5–10 одновременных скачиваний организаторского PDF (набор M) — время ответа и память контейнера (`docker stats`), в логе нет `OutOfMemoryError`/`documents.generation_failed`.
7. Лог старта: нет предупреждений Thymeleaf о `classpath:/templates/` и ошибок загрузки `/fonts/NotoSans-*.ttf`.
