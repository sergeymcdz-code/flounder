# M02 — ревью 1 (PR #29, b1aa758)

Ветка `pr/29` (b1aa758, «feat(identity): harden passwords and rotate refresh sessions») → `origin/main` (47ac549). Ревьюер: Claude, 13.10.2026. Диф: 54 файла, +1500/−114. CI на b1aa758: backend ✅, frontend ✅.

**Вердикт:** слить после правок; **на стенд sportgate.pro — только после демо (16.10)**.

Задание закрыто полностью и на хорошем уровне: все 5 backend-пунктов и 3 frontend-пункта реализованы, `AuthHardeningIntegrationTest` (15 сценариев, 255 строк, реальный PostgreSQL без внешней транзакции, подменяемый `identityClock`) покрывает каждый сценарий из п. 5 задания, включая 429 с `Retry-After: 900` и сброс через 15 минут, ротацию refresh, logout/logout-all, отказ заблокированному, истёкшие/повторные/заменённые reset-токены, bcrypt-лимит 72 байта и даже конкурентные гонки refresh/reset (пессимистические блокировки в едином порядке user → token). В БД хранятся только SHA-256 хеши; raw-токен — 32 байта `SecureRandom` в base64url. Ответ `/auth/login` расширен **аддитивно** (`refreshToken`), `expiresIn` по-прежнему 7200, формат JWT/issuer/secret не менялись — существующие сессии стенда переживут деплой. Modulith-границы соблюдены (`MailSender` в `common`, `identity` разрешает `common`), все 6 новых эндпоинтов в `qa04-endpoints.tsv` с рабочими состояниями фикстуры, QA04-08 перенесён из `Qa04KnownDefectsIT` без ослабления, ни один старый тест не удалён. Фронт: `AuthProvider` на `useSyncExternalStore` с тем же ключом/формой `sessionStorage`, объединённый refresh на 401 с одним повтором, русские тексты, 7 Vitest-тестов формы + 7 на `http.ts` + 3 на `AuthProvider`.

Блокирующих дефектов безопасности **нет**. Четыре правки нужны до слияния, и все они короткие: (1) на стенде ссылка восстановления собирается с `http://localhost:5173`, потому что `APP_PUBLIC_URL` не передаётся в `infra/compose.prod.yaml`; (2) лимит входа жёстко зашит (5/15 мин) и не сбрасывается успешным входом — на демо 15.10 пять аккаунтов входят с одного ноутбука, и пять опечаток за 15 минут блокируют вход **всем** на 15 минут, включая верные пароли; нужны настраиваемые параметры и сброс счётчика email при успехе; (3) описание PR и README утверждают, что за прокси все клиенты сливаются в один IP, — это неверно для стенда (`application-prod.yml:38` `forward-headers-strategy: native` → Tomcat `RemoteIpValve`, Caddy в docker-сети 172.x ⊂ internal-proxies по умолчанию, реальный IP клиента берётся из `X-Forwarded-For`); текст надо поправить, иначе эксплуатация примет неверное решение; (4) `docs/02_ТЗ_демо.md` §5 не дополнен контрактами M02 (чек-лист §3 «контракты §5 соблюдены дословно» — новых контрактов в ТЗ просто нет).

Что **не** удалось проверить локально: Docker/Maven/npm из этой сессии недоступны — `mvn test`, `npm test/build/lint` не прогнаны, опираюсь на зелёный CI (backend + frontend jobs на b1aa758) и статический разбор. Ручная приёмка на стенде не выполнялась.

## Блокирующие замечания

1. **`infra/compose.prod.yaml:45-51`, `infra/.env.prod.example` — `APP_PUBLIC_URL` на стенд не передаётся.** `PasswordService.java:30` берёт `${app.public-url:http://localhost:5173}`, `application.yml:93` — `${APP_PUBLIC_URL:http://localhost:5173}`; ни compose, ни пример env переменную не задают → на sportgate.pro ссылка в письме/логе будет `http://localhost:5173/reset-password?token=…`, т.е. восстановление пароля на стенде неработоспособно без ручного копирования токена. Исправить: в `infra/compose.prod.yaml` (environment сервиса `api`) добавить `APP_PUBLIC_URL: ${APP_PUBLIC_URL:-https://${DOMAIN}}`, в `infra/.env.prod.example` — строку `APP_PUBLIC_URL=https://demo.flounder.kz` с комментарием. pr/25 (M09) тоже правит `compose.prod.yaml` — пересечения по строкам нет, но кто сливается вторым, тот ребейзится (регламент §4).

2. **`identity/application/LoginAttemptLimiter.java:18-19,34-38` — лимит 5/15 мин зашит константами и не сбрасывается успешным входом; для демо 15.10 это реальный риск отказа входа.** По сценарию демо пять аккаунтов (`admin@`, `org@`, `sec@`, `judge@`, `parent@flounder.demo`) входят с одного ноутбука (один IP, см. «IP за Caddy» в таблице): пять опечаток пароля за 15 минут в сумме по всем аккаунтам → `429` на **любой** логин с этого IP, включая верный пароль, до 15 минут. Задание требует именно «5 за 15 минут», поэтому порог не меняю, но нужно: (а) вынести в свойства `app.auth.login.max-failures` (default 5) и `app.auth.login.window` (default PT15M) с env `APP_AUTH_LOGIN_MAX_FAILURES`/`APP_AUTH_LOGIN_WINDOW`, чтобы на день демо поставить, например, 20 без пересборки; (б) после успешной аутентификации вызывать `limiter.succeeded(email)` → `failures.invalidate("email:" + normalize(email))` (счётчик IP не трогать — он защищает от перебора по многим email), чтобы «вошёл со второй попытки» не накапливал хвост на весь вечер. Дополнить `rateLimitByNormalizedEmail…` проверкой: 4 неудачи → успех → ещё 4 неудачи → 401, а не 429; и тест с `app.auth.login.max-failures=2` через `@TestPropertySource` (или вложенный класс).

3. **Описание PR («Что не сделано», 3-й пункт), `sport-platform/README.md:375-378`, `docs/qa/QA04-security-rbac.md:204` — утверждение «за reverse proxy общий `remoteAddr` объединяет клиентов в один IP-лимит» неверно для стенда и вводит в заблуждение.** `application-prod.yml:38` уже включает `server.forward-headers-strategy: native` (Tomcat `RemoteIpValve`; Caddy в docker-сети 172.x входит в `internal-proxies` по умолчанию и сам добавляет `X-Forwarded-For`), поэтому на sportgate.pro `getRemoteAddr()` — это реальный адрес клиента. Из-за неверного текста эксплуатация либо «починит» то, что работает, либо наоборот решит, что лимит на стенде сломан. Исправить текст в README/QA-doc/PR: «на стенде (`prod`-профиль) IP клиента берётся из `X-Forwarded-For` через `RemoteIpValve`; без `forward-headers-strategy` (локально/тест) используется прямой `remoteAddr`, присланный клиентом заголовок не доверяется». Код не менять.

2. `features/auth/LoginPage.tsx:112` — ссылка «Забыли пароль?» появится на стенде, где письма не отправляются: посетитель получит «мы отправили ссылку» и никогда её не получит. До M05 либо спрятать ссылку за `VITE_PASSWORD_RESET_ENABLED` (default `true` в dev, `false` в prod-сборке), либо в success-тексте для стенда честно написать «письма пока не рассылаются, обратитесь к организатору».
3. `identity/application/AuthSessionService.refresh:40-48` — нет reuse-detection: предъявление уже отозванного (ротированного) refresh-токена возвращает 401, но не отзывает остальные токены пользователя. Стандартная практика (RFC 6819 §5.2.2.3): при `revokedAt != null` вызывать `tokens.invalidateAll(userId)` — украденный и уже использованный злоумышленником токен тогда лишает сессии обоих, и легитимный пользователь перелогинится. 3 строки + тест (старый токен после ротации → 401 и новый тоже → 401).
4. `PasswordService.change:44-45` / `confirmReset:88-89` — смена пароля отзывает **все** refresh, включая текущее устройство: через ≤2 ч пользователь получит «Сессия истекла» прямо после того, как сам сменил пароль. Либо `change-password` возвращает новую пару (`AuthTokenResponse` вместо 204 — изменение контракта, описать в ТЗ), либо фронт после успешной смены сам вызывает `login` с новым паролем / показывает «Войдите заново с новым паролем» и делает `logout`. Сейчас `PasswordPage.tsx:40` просто показывает успех.
5. `features/auth/LoginPage.tsx:44-47` — при 429 показывается только «Слишком много попыток входа. Попробуйте позже» без времени: `ApiError` не несёт `Retry-After`. Добавить в `ApiError` поле `retryAfter?: number` (читать заголовок в `apiFetch`) и выводить «Попробуйте через N мин». На демо это сэкономит нервы, если п. 2 блокирующих всё же сработает.
6. `PasswordService.requestReset:61-75` — запрос восстановления не ограничен по частоте: каждый вызов — `invalidateAll` + `insert` + строка INFO-лога; скриптом можно раздувать `password_reset_tokens` и лог. Переиспользовать `LoginAttemptLimiter` (отдельные ключи `reset-ip:`/`reset-email:`, например 5 за 15 мин → тоже 202, но без письма — не раскрывать). Также отсутствует очистка: `refresh_tokens` растёт на строку за каждый логин (на демо-стенде с `scripts/demo` это десятки в день — не страшно, но для MVP нужен `@Scheduled` `delete … where expires_at < now() - interval '30 days' or revoked_at < now() - interval '7 days'`).
7. `identity/infrastructure/security/IdentityClockConfig.java:10` — `@Primary` на `identityClock` не нужен (все потребители с `@Qualifier`); с ним любой будущий неквалифицированный `Clock` в другом модуле молча получит «часы identity». Убрать `@Primary`.
8. `LoginAttemptLimiter.assertAllowed:28` — `synchronized` на весь инстанс: каждый логин сериализуется. Для одного сервера и демо-нагрузки незаметно; при переходе на Redis (описано в PR) уйдёт само. Отметить TODO.
9. `identity/api/ChangePasswordRequest.java:7`, `PasswordResetConfirmRequest.java:9` — `newPassword` без `@NotBlank`: `null` корректно отбивается `PasswordPolicy` (`identity.password_weak`), но сообщение «не менее 8 символов, буквы и цифры…» на пустое поле выглядит странно рядом с «Укажите текущий пароль». Добавить `@NotBlank(message = "Укажите новый пароль")` для единообразия с `LoginRequest`.
10. `frontend/src/components/AppLayout.tsx:111` — баннер `sessionMessage` (`<p role="alert">`) без стилей и без возможности закрыть; сбрасывается только при следующем логине. Использовать существующий класс ошибки/уведомления из `AppLayout.module.css` и очищать при переходе на `/login`.
