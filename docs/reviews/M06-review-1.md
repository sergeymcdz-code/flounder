### 3. Блокировки и производительность (прочитано построчно)

- `EventLockService.lockWritableForUpdate:47-53` — `select status … for update` + отказ `events.archived`. В `main` `lockForUpdate` тоже `for update`, так что против `main` регрессии нет. **Но** pr/40 (M07) переводит `lockForUpdate` на `for no key update` именно потому, что `for update` на строке события конфликтует с `KEY SHARE`, который берёт вставка `rule_execution_logs(event_id)` при вводе результата (unit lock → event KEY SHARE), а генерация/пересчёт/публикация держат event → units; с `for update` это цикл. #46 переключил `GenerateForEvent`, `GenerateCompetitionUnits`, `PublishUnits`, `RecalculateSchedule`, `UpdateCompetitionUnitEntry` на новый метод — после слияния обоих PR эти пять use case снова на `for update`, и исправление M07 для них отменяется. Правка — одна строка (Б1).
- `EventRepository.lockById` (PESSIMISTIC_WRITE → `for update`) используется в `EventLookupService.lockById`, а тот — из `RegistrationCapacityService.hasPlace:815` на каждую проверку, в т.ч. в цикле `promote`. Строка уже заблокирована тем же `lockWritableForUpdate`, повторный `for update` в той же транзакции ожидания не создаёт; `refresh` нужен, потому что `getPublicBySlug` раньше в запросе загрузил `EventEntity` в контекст (тест `lockedLookupRefreshesEventReadEarlierInTheSameRequest`). Принимаю.
- `hasPlace` каждый раз грузит все заявки события (`findByEventId`), `promote` — O(W×N); `form()` — все заявки + `getForScheduling` на вид. Для 200 заявок — миллисекунды, для MVP на 50 соревнований — ж. 5.
- `EventLifecycleScheduler` каждую минуту открывает по транзакции на каждое PUBLISHED/REGISTRATION_OPEN событие без фильтра по датам (ж. 6).

## Блокирующие

1. **`sport-platform/src/main/java/com/acme/sportplatform/events/EventLockService.java:49`** — `lockWritableForUpdate` должен брать `for no key update`, как `lockForUpdate` в pr/40 (M07), иначе после слияния #40 `GenerateForEvent`/`GenerateCompetitionUnits`/`PublishUnits`/`RecalculateSchedule`/`UpdateCompetitionUnitEntry` снова держат `FOR UPDATE` на строке события и воспроизводят дедлок с вводом результатов (unit lock → вставка `rule_execution_logs` → `KEY SHARE` на events), который M07 устранил. `NO KEY UPDATE` по-прежнему взаимоисключающий со всеми нашими писателями (все берут тот же метод), пропускает только FK-вставки. Заодно пусть `lockWritableForUpdate` и `lockForUpdate` используют одну константу SQL, чтобы при ребейзе #40 не разъехались.
