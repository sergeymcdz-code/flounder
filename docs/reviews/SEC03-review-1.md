## Желательные

1. **Сопоставление пути в фильтре** (`YooKassaWebhookRequestFilter.java:33-36`): `getRequestURI()` сравнивается со строкой буквально — путь с `;параметр` или процентным кодированием (`…/yookass%61`) минует фильтр, но попадает в контроллер (Spring MVC декодирует и убирает `;`). Опасности нет: при YOOKASSA контроллер падает на `IllegalStateException` (`:48`) → 500 без чтения тела и записи в БД, при MANUAL → 404. Но вместо 500 должно быть 403/413: использовать `AntPathRequestMatcher`/`PathPatternRequestMatcher` (они нормализуют путь) либо в контроллере при отсутствии атрибута возвращать 403.
2. **Переменная `YOOKASSA_ALLOWED_CIDRS` не доходит до контейнера**: `infra/compose.prod.yaml:76-103` перечисляет переменные явно, и в нём нет ни `YOOKASSA_ALLOWED_CIDRS`, ни существующих `YOOKASSA_SHOP_ID/SECRET_KEY/RETURN_URL` (старый пробел — включить YOOKASSA на стенде сейчас в принципе нельзя без правки compose). Добавить четыре переменные в `environment:` api, в `infra/.env.prod.example` (закомментированные) и строку `YOOKASSA_ALLOWED_CIDRS` в таблицу `sport-platform/README.md:184-187`. Можно сделать в SEC06 вместе с остальной инфраструктурой.
3. **Логирование**: во всём пути вебхука нет ни одного `log.warn` — отклонённые уведомления (чужой IP, несовпадение суммы, 503 от API) видны только в `payment_webhook_events`. Добавить `warn` с `eventId`, причиной и `providerPaymentId` (без тела и заголовков) в `reject` и в фильтре на 403/413 — иначе на стенде не заметить ни атаку, ни сломанные учётные данные магазина (401 от API → бесконечные 503 → ЮKassa будет повторять 24 ч).
4. **Мёртвый код**: `payments/infrastructure/yookassa/webhook/YooKassaWebhookPayload.java` и `YooKassaWebhookPaymentObject.java` больше нигде не используются — удалить.
5. **Блокировка строки платежа на время HTTP-запроса** (`Process:58-77`): `PESSIMISTIC_WRITE` берётся до `getPayment`, т. е. соединение к БД и блокировка удерживаются до 10 с (connect + read). Для текущего объёма приемлемо и даёт простую сериализацию; если когда-нибудь появятся сотни платежей — вынести вызов API до транзакции с блокировкой. Отметить в коде комментарием (сейчас комментарий `:101` стоит после вызова).
6. **Повторы при REJECTED с 200**: при расхождении суммы/статуса мы отвечаем 200, и ЮKassa повторов не делает — это осознанно (задание: «REJECTED без изменения заявки»). Но если API вернул `pending` (настоящее уведомление пришло раньше, чем ЮKassa обновила статус — такое бывает), мы тоже отвечаем 200, и настоящий `succeeded` может больше не прийти. Рассмотреть для статуса `pending`/`waiting_for_capture` ответ 503 (как при недоступности API), чтобы ЮKassa повторила доставку. Это изменение поведения — на усмотрение владельца, задание такого не требует.
7. **Оформление тестов**: в `YooKassaWebhookIntegrationTest` новые методы используют полные имена классов вместо import'ов (`org.mockito.Mockito.when`, `com.acme…YooKassaPaymentResponse`), отступ 8 пробелов, `@Autowired` поле посреди класса (`:283`) — читается тяжело. Привести к стилю файла при следующем касании.
8. `docs/qa/QA04-security-rbac.md:114` и `QA04-round2.md:146` — в матрице для webhook по-прежнему 400/400; при обновлении QA-документов заменить на 404 (MANUAL).
