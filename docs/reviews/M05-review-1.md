После слияния в контексте два бина `MailSender`; `@Primary` на `OutboxMailSender` разрешает инъекцию в `PasswordService`, но дубль должен исчезнуть — это было условием задания и п. 1 ревью M02-r2. В PR сами написали «удалить после слияния #29» — слияние состоялось, делать в этом PR. При разрешении конфликтов: `application.yml` — строка `app.public-url` одна (M02 и M05 добавляют одинаковую), `app.auth` M02 + `app.mail` M05; `compose.prod.yaml` — `APP_PUBLIC_URL` один раз, `MAIL_*` M05; `.env.prod.example` — убрать дубликат `APP_PUBLIC_URL` (оставить один, любой из вариантов); `qa04-endpoints.tsv` — 6 строк M02 + 3 строки M05; README — оба абзаца. После ребейза прогнать `mvn -q test` и убедиться, что `AuthHardeningIntegrationTest` (`@MockitoBean MailSender`) и `NotificationIntegrationTest` (`@Autowired MailSender`) зелёные с единственным бином.

2. **`results_published` рассылается на каждый заплыв всем участникам вида — лавина писем.** `PublishCompetitionUnitUseCase.execute(unitId)` вызывается на **один заплыв** (`POST /competition-units/{unitId}/publication`), публикует `ResultsPublishedEvent(UUID.randomUUID(), disciplineId)`; слушатель `results()` берёт `registrations.findByDisciplineId` и ключ `results_published:{publicationId}:{email}` — новый `publicationId` на каждый заплыв. Вид «50 м в/с, 12 заплывов» → каждый подтверждённый участник вида получает **12 писем «Результаты опубликованы»**, бо́льшая часть — не про него. Задание: «results_published (участникам вида)», ТЗ 3.7: «результат» — т.е. участнику о его результате. Исправить одним из способов (предпочтителен первый):
   - событие несёт заплыв: `ResultsPublishedEvent(UUID competitionUnitId, UUID disciplineId, List<UUID> registrationIds)` (ids из `entryRepository.findByCompetitionUnitId` — `CompetitionUnitEntryEntity.registrationId`), слушатель шлёт только участникам этого заплыва через `registrations.findByIdIn`, ключ `results_published:{unitId}:{email}` (повторная публикация того же заплыва после снятия — без дубля);
   - либо оставить «всем участникам вида», но ключ `results_published:{disciplineId}:{email}` — одно письмо на вид (тогда ссылка `/e/{slug}/results` уместна), повторных публикаций не уведомлять.
   Поправить тест `publicationOfResultsQueuesOnlyDisciplineRecipients` (сейчас фиксирует именно «всем вида») и docs/M05-notifications.md.

3. **Raw reset-ссылка M02 бессрочно хранится в `notification_outbox.payload`.** `OutboxMailSender.send` кладёт `{"subject","body"}` целиком, `body` содержит `…/reset-password?token=<raw>` (`PasswordService.requestReset:72-74`). M02 специально хранит в `password_reset_tokens` только SHA-256; M05 это обнуляет — любой с доступом к БД/бэкапу (RPO 24 ч, 30 дней хранения) получает живые ссылки на час и историю всех ссылок навсегда. Журнал организатора payload не отдаёт (`event_id=null`, DTO без payload) — через API не течёт, проблема только в хранении. Минимальная правка: в `NotificationOutboxRepository.sent()` и в `failed()` при переходе в FAILED обнулять payload — `payload = '{}'::jsonb` (для всех шаблонов, тело после отправки не нужно: журнал его не показывает, ручного retry нет); тест: после `sendBatch()` `payload::text` для строки `password_reset` не содержит `token=`. Дополнительно (можно отдельно): не хранить `password_reset` в outbox при `MAIL_ENABLED=false`, а сразу логировать — не требую.

## Желательные (не блокируют)

1. **Транзакция на строку, а не на батч.** `NotificationWorker.sendBatch()` — одна `@Transactional` на 50 строк: row-lock и JDBC-коннект удерживаются на всё время SMTP (до 50 × 15 с таймаутов ≈ 12 мин при недоступном SMTP), при падении процесса после N отправок все N уйдут повторно. Схема «claim → send → mark» в `TransactionTemplate` на каждую строку (или сначала `attempts+1`/`next_attempt_at` в короткой транзакции, затем SMTP, затем `SENT`) сужает окно дубля до 1 письма и не держит пул. `lockBatch` при этом остаётся.
2. **Тест пути M02 → outbox** после ребейза: `PasswordService.requestReset("…")` → строка `template_code='password_reset'`, `event_id is null`, затем `worker.sendBatch()` → SENT и тело не в INFO (сейчас это только в `workerBatchIsLimitedToFifty…` через `mail.send` напрямую и в ручной проверке из PR). Плюс `verifyNoInteractions` уже не нужен в `AuthHardeningIntegrationTest` — можно оставить мок, но лучше один сквозной тест.
3. **Дата в письме.** `payload.date = event.startsAt().toLocalDate().toString()` — дата в смещении, с которым JDBC вернул `timestamptz` (на стенде UTC): старт в 00:30 по Самаре (UTC+4) даст вчерашнее число, формат `2026-10-19` вместо «19 октября 2026». Конвертировать в `TZ` приложения (`ZoneId.systemDefault()`/`Europe/Samara`) и форматировать `DateTimeFormatter.ofPattern("d MMMM yyyy", new Locale("ru"))`.
4. **Исключение в слушателе валит доменную операцию.** Это осознанно (одна транзакция), но сейчас любая ошибка внутри notifications (например, невалидный JSON `participantSnapshot` обрабатывается, а `settings.enabled` при недоступной таблице — нет) отменит подачу/подтверждение заявки. Для MVP приемлемо; зафиксировать в `docs/M05-notifications.md` как известное свойство и, по возможности, оборачивать не-SQL ошибки формирования payload в `log.warn` + пропуск.
5. `assertOwner()` сначала `organizations.existsById` → любой ORGANIZER по 404/403 различает существование чужой организации. Мелочь; можно отвечать 403 и на несуществующую.
6. Фронт: пункт «Настройки уведомлений» стоит первым в навигации кабинета (`OrganizerLayout.tsx:11`), перед «Обзор» — перенести в конец списка. Вкладка «Уведомления» в событии показывается и оператору (у него `manage`) — норм.
7. Броадкаст делает `settings.enabled` + `users.findById` на каждую заявку (N+N запросов внутри транзакции организатора при публикации протокола на 500 участников). `settings.enabled` вынести из цикла (одна проверка на шаблон/организацию), `UserLookup.findByIdIn` — если появится.
8. `NotificationIntegrationTest` лежит в пакете `security` (ради `Qa04SecurityFixture`) — лучше `notifications` с импортом фикстуры, чтобы `mvn -Dtest` по модулю находил его.
