## Блокирующие

**Б1. Список заявок по организациям-«наблюдателям».** `GET /api/v1/registrations` без `eventId` (`RegistrationController.java:90-99`) → `ListRegistrationsForReviewUseCase.java:42` → `EventLookupService.accessibleEventIds` (`:36-40`) → `organizationIdsOf(userId)` — **все** членства без учёта роли. Сценарий: секретарь клуба А (operator, есть `ROLE_OPERATOR`) добавлен наблюдателем (`member`) в клуб Б → в общем списке «Заявки» видит заявки (ФИО, дата рождения, документы) событий клуба Б, тогда как `GET /registrations?eventId=<событие Б>` тому же пользователю даёт 403 (`assertCanManage`). Задание просило оставить `accessibleEventIds` «как сейчас», но это противоречит его же целевой модели («member → только просмотр») и ТЗ §5.8 — приоритет у ТЗ. Правка: в `EventLookupService.accessibleEventIds` брать организации только с ролями `owner|admin|organizer|operator|judge` (новый метод `OrganizationManagementAccess.manageableOrganizationIdsOf` или фильтр по `membershipsOf`), `listMyEvents` (`EventController.java:134-137`) оставить на всех членствах (там просмотр уместен); добавить в `S07OrganizationRolesIntegrationTest` проверку: member с глобальным operator → `GET /registrations` не содержит заявок организации-наблюдателя.

## Желательные

1. **Мёртвый код:** `UserRepository.findAuthenticationById` + `UserAuthenticationRow` (identity) больше никем не используются; поле `organizations` в `EventAccessService` тоже (остался только `verifyNoInteractions` в тесте). Удалить или оставить с комментарием.
2. **`OrganizerEventsPage` для platform_admin с членствами:** `currentOrgId` = первая организация → админ видит только её события вместо всех (`OrganizerEventsPage.tsx:78`). Для `isPlatformAdmin` не передавать `organizationId`, либо добавить пункт «Все организации» в переключатель.
3. **`PATCH /organizations/{id}` — семантика PUT с пустыми строками:** `OrganizationPage.save` шлёт `Object.fromEntries(FormData)` → `legalName/inn/contactPhone/city = ""` сохраняются как пустые строки (`OrganizationService.updateOrganization:561-573`, `meta.city=""`). Пустые значения превращать в `null` (на фронте или в сервисе); `@Valid CreateOrganizationRequest` с обязательными `type/name` — ок.
4. **Токен в outbox:** до доставки открытый токен лежит в `notification_outbox.payload` (как у `password_reset`); при исчерпании попыток остаётся навсегда. Либо чистить payload и у `FAILED`, либо отразить в ADR (там сказано только про «после доставки»).
5. **`AuthProvider` без `useMemo`:** значение контекста пересоздаётся на каждом рендере, `memberships = … ?? []` даёт новую ссылку → зависимости `useEffect` в `CreateEventPage.tsx:328` и `OrganizationPage` срабатывают чаще нужного. Вернуть `useMemo`/`useCallback` для `selectOrg`, `hasRole`, стабильный `EMPTY_MEMBERSHIPS`.
6. **Публичный `GET /invitations/{token}`** на каждый запрос с валидным токеном делает `select … for update` на `organizations` и `update … set EXPIRED`. Для публичной точки лучше читать без блокировки и помечать EXPIRED только в `accept`/`list` — не критично (токен 256 бит, перебор невозможен), но лишняя запись в read-path.
7. Имя приглашающего: `u.firstName() == null ? u.email() : u.firstName()` (`OrganizationInvitationService.java:90`) — при пустой строке `firstName` письмо начнётся с « приглашает вас…»; использовать `isBlank()` и, при отсутствии имени, название организации, а не e-mail приглашающего (лишнее раскрытие адреса).
8. `S07OrganizationRolesIntegrationTest` пересчитывает `OpaqueTokens.hash` из identity для проверки хеша, а сервис хеширует своей копией `hash()` — лучше переиспользовать `OpaqueTokens` напрямую (один алгоритм в одном месте).
