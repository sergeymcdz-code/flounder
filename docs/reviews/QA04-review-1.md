# QA04 — ревью 1 (PR #16, 4b499d8)

Ветка `pr/16` (4b499d8, «fix(security): audit RBAC and harden JWT authentication») → `origin/main` (0a75852). Ревьюер: Claude, 13.10.2026. Диф: 17 файлов, +1058/−31; из них production-кода 6 файлов (+54/−17), остальное — отчёт, 7 тестовых классов, TSV-фикстура на 98 эндпоинтов и 1 Vitest-тест.

**Вердикт:** слить (при зелёном CI на 4b499d8), **до** M01 (#15); правки — в следующий раунд (см. «Текст правок»)

Задание выполнено по букве QA00/QA04: матрица 98 эндпоинтов × 7 ролей снята параметризованным интеграционным тестом на настоящем PostgreSQL (а не моками), таблица фикстур сверяется с `RequestMappingHandlerMapping`, так что новый эндпоинт без строки в матрице ломает тест. Все 6 исправлений — настоящие дыры, каждое ≤ 40 строк, контракты §5 ТЗ и `/api/v1/public/**` не тронуты, `SecurityConfig`/CORS/заголовки не менялись, миграций нет, rate-limit не вводился. Сценарий демо (публичные страницы без токена, кабинет `org@`, судья `judge@`, импорт, посев, результаты, live) под изменения не попадает: единственное поведенческое изменение для стенда — на каждый запрос с Bearer-токеном добавляются два чтения БД (`users`, `user_role_assignments`), публичный поллинг live токена не шлёт (`frontend/src/api/public.api.ts` — `Authorization` только на `POST …/registrations`). Четыре намеренно красных теста собраны в `Qa04KnownDefectsIT`, который surefire не запускает (`pom.xml:186-189` исключает `**/*IT.java`), поэтому CI (`mvn -B test`) остаётся зелёным — регламент §3 соблюдён; красным будет только `mvn verify`/failsafe, который нигде не используется (CI, Dockerfile `package -DskipTests`).

Главное, что надо знать при слиянии: **PR #16 конфликтует с PR #15 (M01) в пяти файлах, и конфликты не только текстовые** — M01 и QA04 независимо переписали `JwtAuthenticationFilter` одинаково по идее (пользователь и роли из БД на каждом запросе), но с разными деталями; M01 по заданию отдаёт заблокированному на логине 403 `identity.user_blocked`, а QA04-04 — общий 401; после слияния M01 тест `fixtureTableCoversEveryApiV1ControllerMapping` упадёт, потому что M01 добавляет 6 эндпоинтов, которых нет в `qa04-endpoints.tsv`. Разрешение описано в «Порядке слияния». Так как #16 готов и мал, а #15 всё равно уходит на раунд правок, рекомендую слить #16 первым и дать Codex в правках M01 инструкцию по ребейзу (отступление от §4 регламента «ранний PR побеждает» — осознанное, в пользу стенда перед демо 15.10).

Что **не** удалось проверить: Maven Central и npm из контейнера недоступны → сборка, `mvn test` (Testcontainers), `npm test` не прогнаны; проверка статическая. Codex сообщает о прогоне с Docker (727 зелёных проверок, матрица, lint/build) — **сливать только при зелёном CI на 4b499d8**.

## Желательные замечания

1. `identity/application/LoginUseCase.java:41` — `catch (AuthenticationException ex)` слишком широк: `InternalAuthenticationServiceException` (сбой БД в `PlatformUserDetailsService`) превратится в 401 «Неверная почта или пароль», и инцидент на стенде будет выглядеть как ошибка пользователя. Ловить `BadCredentialsException | AccountStatusException` (последний покрывает `DisabledException`, `LockedException`, `AccountExpiredException`), остальное пропускать в `GlobalExceptionHandler` → 500. При этом `DaoAuthenticationProvider` проверяет `isEnabled()` **до** пароля (`preAuthenticationChecks`), поэтому 403 `identity.user_blocked` из M01 отдаётся при любом пароле — это перечисление заблокированных аккаунтов. Компромисс, который удовлетворяет и M01 п. 4, и QA04 п. 3–4: на `DisabledException` проверить `passwordEncoder.matches(request.password(), user.getPasswordHash())` — при совпадении 403 `identity.user_blocked`, иначе 401 `identity.invalid_credentials`. Тест QA04 `loginForDisabledAccountsReturns401WithoutLeakingAccountState` тогда переписать на два случая (верный пароль → 403 `identity.user_blocked`; неверный → 401 без слова `blocked`).
2. `sport-platform/src/test/java/com/acme/sportplatform/security/Qa04KnownDefectsIT.java:12-15` — намеренно красный класс исключён из `mvn test` только по суффиксу `IT`, но failsafe привязан к `verify` (`pom.xml:195-205`), и `mvn verify` теперь гарантированно красный (`AuthIT`/`RbacIT`/… тоже не в CI, их состояние неизвестно). Чтобы ловушка не сработала при переходе CI на `verify` (M09), пометить класс `@Tag("known-defect")`, в failsafe добавить `<excludedGroups>known-defect</excludedGroups>`, а в отчёте оставить команду запуска `mvn -q test -Dtest=Qa04KnownDefectsIT` (параметр `-Dtest` игнорирует `excludes`, так что она работает). Это не `@Disabled` — тесты остаются «живыми» и красными, что требует QA00. Дополнительно: у каждого из 4 тестов указать в Javadoc задачу-владельца (QA04-07/08 → M02, QA04-06 → M09 или отдельная задача, QA04-10 → отдельная задача), чтобы они не повисли.
3. `identity/infrastructure/security/JwtAuthenticationFilter.java:103` — отключённый пользователь и несуществующий `uid` отвечают одинаковым `authentication_required`. Для фронта это нормально (разлогин), но M01 отдаёт для заблокированного `identity.user_blocked` с русским сообщением — при слиянии взять вариант M01 (с учётом M01-review желательного 3 про `UserBlockedException`).
4. `JwtAuthenticationFilter.java:105` — `findRoleCodesByUserId` включает scoped-назначения (`organization_id`/`event_id`), M01 перешёл на `findGlobalRoleCodesByUserId`. Сейчас scoped-назначений никто не создаёт, но при слиянии оставить вариант M01 (глобальные), иначе `/auth/me` и authorities разойдутся по семантике.
5. `JwtAuthenticationFilter.java:78-92` — требование непустого claim `roles` после перехода на роли из БД стало мёртвым: токен с `roles: []` отклоняется, хотя права всё равно берутся из БД. M01 эту проверку уже ослабил до «`roles` — коллекция» (тест `oldTokenReflectsRoleChangesAndZeroRolesRemainAuthenticated`). При слиянии взять M01.

Между слиянием #16 и #15 окно небольшое, в демо-сценарии удаления пользователей нет — приемлемо, но помнить.
