# Flounder — решение по стратегии разработки и план до демо 15.10.2026

Версия 1.0 · 12.10.2026 · автор: Claude (техдиректор/координатор) · владелец: Сергей Герасимов

## 1. Решение

**Берём существующий код MVP (github.com/Psix10/Flounder, Spring Boot 3 / Spring Modulith / PostgreSQL / React), копируем в собственный репозиторий и достраиваем. Код пишет ChatGPT (Codex) по заданиям из папки `tasks/`. Claude — архитектура, ТЗ, ревью PR, приёмка, координация.**

Почему не новый стек:
- в репозитории уже ~60 % рутины MVP: авторизация и роли, события, дисциплины, заявки с модерацией, ручная оплата и ЮKassa-webhook, ввод результатов, пересчёт мест, публикация, публичный каталог, панель судьи, React-фронт (15 тыс. строк Java, 8,6 тыс. строк TS, 52 теста);
- для демо не хватает 5 вещей: 4 блокера, модуль посева заплывов, импорт из Excel, печатные протоколы, 3 экрана UI. Это 3 параллельных потока по 2 дня;
- архитектурные артефакты диплома (ER-модель, API, гипотеза о модульном монолите, гипотеза об алгоритме посева) остаются в силе.

Что в коде плохо и будет исправлено в первую очередь (из аудита 12.10):
1. Организатор не может создать событие: членство в организации (`organization_members`) никем не создаётся, работает только под `platform_admin`.
2. Оплата не переводит заявку в статус «оплачено».
3. Нет проверки «чьё событие»: любой организатор правит чужие дисциплины/заявки/заплывы.
4. Во фронте роль `platformadmin` вместо `platform_admin` — админ не попадает в защищённые разделы.
5. В git закоммичены `.env` с JWT-секретом и папка `target/`; seed-админ с нерабочим хешем пароля.
6. Нет OpenAPI, Dockerfile, CI; Kafka и Redis подключены, но не используются.

## 4. Регламент работы

1. Ветки `feat/T0X-...` от `main`, один PR на задание, squash-merge. В `main` напрямую не пушим.
2. В каждом PR: описание «что сделано / как проверить», зелёные `mvn test` и `npm run build`, обновлённый `README`/`docs`, если менялись запуск или API.
3. Claude ревьюит каждый PR по чек-листу (см. `05_Регламент_агентов.md`) и пишет вердикт: «слить» / «слить после правок» / «вернуть».
4. Секреты только в `.env` (не в git) и в переменных окружения сервера.
5. Язык интерфейса и сообщений об ошибках — русский. Код, идентификаторы, коммиты — английский.

## 6. Риски демо и запасные ходы

| Риск | Вероятность | Запасной ход |
|---|---|---|
| Codex не успевает модуль посева за 2 дня | средняя | эталонная реализация алгоритма (TypeScript, `reference/seeding.ts`) приложена — перенос 1:1 на Java; крайний случай — посев выполнить скриптом и загрузить заплывы через существующий API `POST /competition-units` |
| Импорт Excel не готов | низкая | загрузка заявок CSV-скриптом через API (T10 содержит скрипт) |
| Печать PDF кривая | низкая | печать из браузера по `@media print` — требование T07; серверный PDF — после демо |
| Сервер не готов | средняя | демо с ноутбука Сергея (`docker compose up`), публичные страницы через ngrok/cloudflared на телефон |
| Нет реальных данных Самары | высокая | синтетический набор M, фамилии вымышленные |
