# Flounder — регламент работы агентов-разработчиков и ревью

## 1. Роли
- **Сергей** — владелец продукта: приоритеты, приёмка демо, доступы, запуск задач в Codex, слияние PR после вердикта.
- **Claude** — техдиректор/координатор: ТЗ и контракты, декомпозиция, ревью каждого PR, приёмка по чек-листу, ведение рисков, протоколы решений.
- **ChatGPT (Codex)** — разработчик: реализует задания `tasks/T0X` в ветках, пишет тесты, описывает PR.

## 2. Цикл задачи
1. Сергей запускает задачу Codex: текст `tasks/T0X_*.md` целиком + строка «Работай по AGENTS.md. Ветка feat/T0X-…».
2. Codex создаёт PR. Сергей присылает Claude ссылку (или `git diff`), Claude отвечает вердиктом в течение рабочего часа: **слить** / **слить после правок (список)** / **вернуть (почему)**.
3. Правки — той же задачей Codex («внеси правки по ревью: …»). После «слить» Сергей делает squash-merge.
4. Claude обновляет статус в плане и пульте; при блокере — сразу пишет Сергею.

## 3. Чек-лист ревью Claude (применяется к каждому PR)
- Соответствие ТЗ: контракты §5 ТЗ демо соблюдены дословно (пути, поля, коды ошибок).
- Тесты: новые тесты есть и осмысленны; старые не удалены/не ослаблены; CI зелёный.
- Архитектура: модульные границы Modulith не нарушены; нет обращений к чужим репозиториям; нет бизнес-логики в контроллерах.
- Безопасность: `assertCanManage` на всех управляющих эндпоинтах; нет секретов; ввод валидируется; нет SQL-конкатенации.
- Данные: миграции только добавляющие, с CHECK/FK/индексами; `ddl-auto: validate` проходит.
- UX: русские тексты, состояния загрузки/ошибок, мобильная ширина для публичных страниц.
- Производительность: нет N+1 на списках; пагинация там, где список может вырасти.
- Документация: README/Swagger/`docs` обновлены, описание PR содержит «как проверить».

## 4. Параллельность и конфликты
Потоки A (backend-core), B (backend-seeding/publication), C (frontend) не трогают файлы друг друга. Общие точки: `EventDisciplineLookup`, `RegistrationLookup`, `GlobalExceptionHandler`, `SecurityConfig`, фронтовые `api/*.ts` — изменения в них делать минимальными и упоминать в PR; при конфликте слияния побеждает более ранний PR, поздний ребейзится.

## 5. Коммуникация
- Ежедневно в 21:00 МСК Claude присылает статус: что слито, что в ревью, блокеры, план на завтра (и пишет его в пульт).
- Любой вопрос агента, требующий решения продукта, Codex фиксирует в описании PR в разделе «Вопросы», Claude отвечает в ревью.
- Решения, меняющие ТЗ, записываются в `docs/decisions/ГГГГ-ММ-ДД-тема.md` (ADR: контекст, решение, последствия).
