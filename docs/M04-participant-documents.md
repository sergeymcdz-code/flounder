# M04 — документы участников

Документы загружаются без проверки комиссией: новый документ получает `PENDING`.
Статусы `NOT_UPLOADED`, `PENDING`, `ACCEPTED`, `REJECTED` заложены в V031.
Предупреждения о справке не изменяют статус заявки и не блокируют посев.

## Хранение и настройка

По умолчанию используется `LocalFileStorage`, каталог `FILES_STORAGE_DIR`
(`./data/files` для локального запуска, `/data/files` в production compose).
Том `flounder_files` подключён к `api`; образ создаёт `/data/files` с правами пользователя `app`.
Файлы обоих провайдеров хранятся как AES-256-GCM ciphertext с отдельным случайным nonce
и аутентификацией ключа объекта через AAD. Имя файла не используется как путь хранения.

`APP_FILES_ENCRYPTION_KEY` — base64 от 32 случайных байт. Сгенерировать один раз:

```bash
openssl rand -base64 32
```

Записать результат в `infra/.env.prod` как `APP_FILES_ENCRYPTION_KEY=…`.
Основной compose напрямую передаёт ключ в `api` и отклоняет конфигурацию, если он пуст.
В `prod` неверный base64 или длина приводят к отказу запуска; секрет не логируется.
Запуск использует обычный deployment-конфиг:

```bash
docker compose --env-file infra/.env.prod -f infra/compose.prod.yaml up -d --build
```

Из мастер-ключа один раз выводятся HMAC-SHA256-подключи:
`flounder-files-enc-v1` для AES и `flounder-files-sig-v1` для подписей.
Формат файла сохранён: `[1][12-byte nonce][ciphertext + GCM tag]`.
Файлы до разделения ключей несовместимы: M04 ещё не развёрнут, поэтому переход сделан до первого слияния.
Ротации ключа и перешифровки нет; смена/потеря ключа означает потерю доступа к документам.

**Ключ обязательно входит в план бэкапа и восстановления**, но хранится в защищённом
бэкапе отдельно от тома. M09 `infra/backup.sh` сохраняет том с `FILES_VOLUME=flounder_files`;
в compose закреплено именно это Docker-имя, без project-prefix. Скрипт не копирует секрет
автоматически: резервную копию `APP_FILES_ENCRYPTION_KEY` необходимо сохранить отдельно.
Для восстановления нужны PostgreSQL, архив тома и тот же мастер-ключ.
Не переопределяйте `/data/files` в контейнере без подготовки владельца/прав каталога.

Для разработки без ключа создаётся временный ключ в памяти; для сохранения документов
между перезапусками тоже задайте постоянный ключ. Автоматическое хранение dev-ключа отложено (Ж6).

S3 на стенде не включается без правки compose: добавьте в `api.environment`
`APP_FILES_PROVIDER=s3`, `APP_FILES_S3_ENDPOINT`, `APP_FILES_S3_BUCKET`,
`APP_FILES_S3_REGION`, `APP_FILES_S3_ACCESS_KEY`, `APP_FILES_S3_SECRET_KEY`.
AWS SDK v2 настроен на path-style; bucket должен быть закрытым.
Оба провайдера используют потоковые `put(InputStream, size)` / `get(): InputStream`.
Локальный провайдер пишет/читает через `CipherOutputStream`/`CipherInputStream`,
S3 передаёт потоки SDK. Контроллер возвращает `InputStreamResource` и точный
`Content-Length = size_bytes`; массивы целого файла в API/сервисах не создаются.
Magic bytes читаются из первых 8 байт через `PushbackInputStream` и возвращаются в поток;
контролируется и заявленный, и фактически прочитанный размер.
JCE-провайдер может внутренне буферизовать AES-GCM при расшифровке до проверки тега;
потоковый контракт сам по себе не гарантирует постоянный размер heap внутри JCE.

## Контракты API и права

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/api/v1/profiles/{profileId}/documents` | Multipart: `type`, `file`, `issuedAt?`, `validUntil?`, `eventId?`; ответ 201 |
| GET | `/api/v1/profiles/{profileId}/documents` | Список; организатор передаёт `eventId` |
| DELETE | `/api/v1/profiles/{profileId}/documents/{id}` | Только собственный `PENDING`; ответ 204 |
| GET | `/api/v1/documents/{id}/download` | JSON `{url, expiresAt}`, URL действует 10 минут; `eventId?` для общих документов у организатора |
| GET | `/api/v1/public/documents/{id}/content` | Скачивание с `expires`, `signature`, `eventId?` и тем же Bearer-токеном |
| GET | `/api/v1/events/{eventId}/registrations` | Заявки с `documents` и `admissionWarnings` |

Существующие `/api/v1/registrations?eventId=…` и `/api/v1/registrations/me` также
дополнены сводкой. Документы выбираются одним запросом для всех профилей, даты старта —
одним запросом для всех событий. В пределах типа приоритет у документа этого события,
затем у общего документа; внутри одного scope выбирается последняя загрузка.
Граница действия включительна: `validUntil == date(eventStartAt)` не даёт предупреждения.

Связь родителя и ребёнка соответствует T03: `profiles.user_id` указывает на аккаунт,
который ведёт профиль. Чужой профиль для участника возвращает 403. Организатор/оператор
передаёт `eventId`, проходит `EventAccessService.assertCanManage` и проверку наличия
заявки профиля в событии. Он видит общие документы и документы своего события.
Документы другого события не попадают в список, скачивание чужих возвращает 404/403.

Подпись привязана к ключу файла и пользователю. При скачивании права проверяются повторно:
отзыв членства или удаление документа делает ранее выданную ссылку непригодной.
URL без подписи, с истёкшей/неверной подписью или без авторизации возвращает 404.
Приложение ставит `Cache-Control: private, no-store`; service worker исключает документы
и `.pdf`-протоколы M03 из публичного офлайн-кэша. `file_access_log` сохраняет `UPLOAD`, `SIGN_DOWNLOAD`,
`DOWNLOAD`, `DELETE`, `DENIED` с ключом файла, ID документа, пользователем и временем.
ID документа не имеет FK и остаётся в журнале после удаления документа.
`DENIED` сохраняется через `REQUIRES_NEW` при отказе выдачи ссылки/контента и переживает
откат основного запроса. Для неизвестного файла ключ может быть NULL; анонимные отказы не записываются (S04).
user_id журнала имеет `ON DELETE SET NULL`. Индекс `(user_id, at)` дополняет `(file_key, at)`. Откат загрузки удаляет объект;
удаление объекта происходит после commit удаления метаданных.

Допустимы только PDF/JPG/JPEG/PNG до 10 МиБ (10 × 1024 × 1024): проверяются
расширение, заявленный MIME и magic bytes; MIME в ответе берётся из проверенного типа.
Глобальный multipart-лимит поднят до 10 МиБ, лимит Excel-импорта остаётся 5 МиБ;
общий servlet-413 использует `files.too_large` / «Размер файла превышает допустимый».
Проверка 5 МиБ в imports возвращает свой `imports.file_too_large` и прежний текст.
Демо-сид и остальной Excel-импорт не изменены.

После сохранения публикуется `ParticipantDocumentUploadedEvent(documentId, profileId,
eventId, uploadedBy, type, uploadedAt)` через `ApplicationEventPublisher`.
Слушатели M05/M06 должны использовать обработку после commit (`@TransactionalEventListener`);
прямых вызовов notifications нет.

## Ручная проверка

1. Запустить backend с PostgreSQL, V031 и ключом шифрования; frontend — с адресом API.
2. Войти участником/родителем, открыть `/my/registrations` на телефоне или при ширине 375 px.
3. В блоке «Документы» выбрать медицинскую справку, PDF/фото JPG/PNG, даты; загрузить.
   Основной input не содержит `capture`, поэтому готовый файл можно выбрать из системного диалога.
   Ожидается «На проверке», имя файла и срок действия. PDF/фото скачиваются кнопкой «Скачать».
4. Попробовать другой тип файла, замаскированный под PDF файл и файл больше 10 МиБ:
   ожидается понятная ошибка, документ не создаётся.
5. Участником удалить `PENDING`; документ исчезает. Документ `ACCEPTED`/`REJECTED` удалить нельзя
   (изменение статуса пока только через тестовую фикстуру, экрана комиссии нет).
6. Войти организатором события: открыть «Заявки», проверить статусы, «нет справки»,
   открыть документы участника. Справка со сроком раньше старта даёт предупреждение;
   посев остаётся доступным по существующим правилам.
7. Проверить API чужим родителем и организатором другой организации: 404/403.
8. В сетевых запросах получить signed URL; удалить `signature`, изменить подпись,
   дождаться истечения 10 минут или использовать токен другого пользователя: 404.
9. Проверить ciphertext в локальном каталоге и записи `file_access_log` при скачивании.

## Автоматические проверки и границы

`mvn -q test` включает Local/S3 storage unit-тесты, Testcontainers PostgreSQL,
проверку модульной архитектуры, QA04-матрицу всех endpoint-ов и интеграционные проверки
шифрования, доступа, подписи, журнала, транзакций, события и постоянного количества SQL
при росте списка с 1 до 21 заявки (3 запроса, из них 1 на документы).

Frontend: `npm test`, `npm run build`, `npm run lint`.
Браузерные тесты с подменённым API: `npx playwright test --config playwright.documents.config.ts`
(при необходимости `PLAYWRIGHT_CHROMIUM_EXECUTABLE=/usr/bin/chromium`).
Они проверяют загрузку, скачивание и отсутствие переполнения на 375 px, статусы и фильтр.

Выбор файла/камера на реальных iPhone/Android не проверялись; требуется ручная проверка.
Живой Selectel/Yandex S3 также не проверялся.
S3 unit-тест проверяет ciphertext, расшифровку и закрытый gateway на mock AWS client.
Комиссия, напоминания, печать листа допуска, обязательное блокирование посева и notifications
не реализованы по границам M04. `DELETE` доступен только участнику для собственного `PENDING`:
организатор пока не может удалить даже загруженный им ошибочный файл (до появления комиссии).
`NOT_UPLOADED` используется в сводке отсутствующих типов, а не для строки без файла.

Ж3 отложен: путь `/public/documents/.../content` по-прежнему требует подпись и Bearer,
проверяет права заново и возвращает 404 без подписи/авторизации. Это ссылка для authenticated
fetch из кабинета, её нельзя открыть анонимно или передать другому пользователю.
Перенос маршрута/смена этого контракта и объединение Playwright-конфигов — отдельная задача.
По Ж5 журнал допускает обезличивание user_id; текущий `DeleteUserUseCase` выполняет soft-delete
(`status=inactive`). Физическое удаление/обезличивание uploaded_by и удаление профиля вместе
с документами требуют отдельного сценария; автоматического cascade-удаления файлов нет.
Ротация/перешифровка и постоянный автоматически генерируемый dev-ключ (Ж6) отложены.

S04: `files.corrupt` возвращает 409 с русским сообщением. Перед выдачей HTTP-заголовков
FileService полностью проверяет расшифровку неизменяемого объекта, отбрасывает
прочитанное и открывает поток повторно для скачивания. Целый файл не копируется
в массив или plaintext-файл на диске; цена проверки — повторное чтение объекта.
`READ_FAILED` не пишется: CHECK V031 его не допускает, миграций в S04 нет.
