# M04 — документы участников

Документы загружаются без проверки комиссией: новый документ получает `PENDING`.
Статусы `NOT_UPLOADED`, `PENDING`, `ACCEPTED`, `REJECTED` заложены в V031.
Предупреждения о справке не изменяют статус заявки и не блокируют посев.

## Хранение и настройка

По умолчанию используется `LocalFileStorage`, каталог `FILES_STORAGE_DIR`
(`./data/files` для локального запуска, `/data/files` в production compose).
Том `flounder_files` подключён к `api`; образ создаёт `/data/files` с правами пользователя `app`.
Файлы обоих провайдеров хранятся как AES-256-GCM ciphertext с отдельным случайным nonce
и аутентификацией ключа объекта через AAD. Имя файла не используется как путь хранения.

`APP_FILES_ENCRYPTION_KEY` — base64 от 32 случайных байт. В `prod` отсутствие ключа,
неверный base64 или длина приводят к отказу запуска. Секрет не хранится в репозитории.
Ключ необходимо сохранять вместе с защищённым резервным копированием; смена ключа
не перешифровывает существующие документы. Для разработки без ключа создаётся временный
ключ в памяти; для сохранения документов между перезапусками тоже задайте постоянный ключ.

В `infra/compose.prod.yaml` по уточнению задачи добавлены только каталог и том.
Переменные encryption/S3 из `.env.prod` необходимо **явно передать в контейнер**:
Docker Compose не передаёт автоматически все переменные файла `--env-file`.
Для production создайте локальный, не коммитящийся override `infra/compose.files.override.yaml`:

```yaml
services:
  api:
    environment:
      APP_FILES_ENCRYPTION_KEY: ${APP_FILES_ENCRYPTION_KEY:?Set a base64 32-byte key}
```

Запуск:

```bash
docker compose --env-file infra/.env.prod \
  -f infra/compose.prod.yaml -f infra/compose.files.override.yaml up -d --build
```

Параллельная задача M09 может добавить передачу секрета в основной deployment-конфиг.
S3 на стенде не обязателен. Для него передайте дополнительно `APP_FILES_PROVIDER=s3`,
`APP_FILES_S3_ENDPOINT`, `APP_FILES_S3_BUCKET`, `APP_FILES_S3_REGION`,
`APP_FILES_S3_ACCESS_KEY`, `APP_FILES_S3_SECRET_KEY`. AWS SDK v2 настроен на path-style
для S3-совместимых провайдеров. Bucket должен быть закрытым; выдаются ссылки на gateway
приложения, который расшифровывает файл после проверки подписи и прав.

## Контракты API и права

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/api/v1/profiles/{profileId}/documents` | Multipart: `type`, `file`, `issuedAt?`, `validUntil?`, `eventId?`; ответ 201 |
| GET | `/api/v1/profiles/{profileId}/documents` | Список; организатор передаёт `eventId` |
| DELETE | `/api/v1/profiles/{profileId}/documents/{id}` | Только собственный `PENDING`; ответ 204 |
| GET | `/api/v1/documents/{id}/download` | JSON `{url, expiresAt}`, URL действует 10 минут; `eventId?` для общих документов у организатора |
| GET | `/api/v1/public/documents/{id}/content` | Скачивание с `expires`, `signature`, `eventId?` и тем же Bearer-токеном |
| GET | `/api/v1/events/{eventId}/registrations` | Заявки с `documents` и `admissionWarnings` |

Существующие `/api/v1/registrations?eventId=…` и `/api/v1/registrations/me` также
дополнены сводкой. Документы выбираются одним запросом для всех профилей, даты старта —
одним запросом для всех событий. В пределах типа приоритет у документа этого события,
затем у общего документа; внутри одного scope выбирается последняя загрузка.
Граница действия включительна: `validUntil == date(eventStartAt)` не даёт предупреждения.

Связь родителя и ребёнка соответствует T03: `profiles.user_id` указывает на аккаунт,
который ведёт профиль. Чужой профиль для участника возвращает 403. Организатор/оператор
передаёт `eventId`, проходит `EventAccessService.assertCanManage` и проверку наличия
заявки профиля в событии. Он видит общие документы и документы своего события.
Документы другого события не попадают в список, скачивание чужих возвращает 404/403.

Подпись привязана к ключу файла и пользователю. При скачивании права проверяются повторно:
отзыв членства или удаление документа делает ранее выданную ссылку непригодной.
URL без подписи, с истёкшей/неверной подписью или без авторизации возвращает 404.
Приложение ставит `Cache-Control: private, no-store`; service worker исключает документы
из публичного офлайн-кэша. `file_access_log` сохраняет `UPLOAD`, `SIGN_DOWNLOAD`,
`DOWNLOAD`, `DELETE` с пользователем и временем. Откат загрузки удаляет объект;
удаление объекта происходит после commit удаления метаданных.

Допустимы только PDF/JPG/JPEG/PNG до 10 МиБ (10 × 1024 × 1024): проверяются
расширение, заявленный MIME и magic bytes; MIME в ответе берётся из проверенного типа.
Глобальный multipart-лимит поднят до 10 МиБ, лимит Excel-импорта остаётся 5 МиБ;
реализация импорта и демо-сид не изменены.

После сохранения публикуется `ParticipantDocumentUploadedEvent(documentId, profileId,
eventId, uploadedBy, type, uploadedAt)` через `ApplicationEventPublisher`.
Слушатели M05/M06 должны использовать обработку после commit (`@TransactionalEventListener`);
прямых вызовов notifications нет.

## Ручная проверка

1. Запустить backend с PostgreSQL, V031 и ключом шифрования; frontend — с адресом API.
2. Войти участником/родителем, открыть `/my/registrations` на телефоне или при ширине 375 px.
3. В блоке «Документы» выбрать медицинскую справку, PDF/фото JPG/PNG, даты; загрузить.
   Ожидается «На проверке», имя файла и срок действия. PDF/фото скачиваются кнопкой «Скачать».
4. Попробовать другой тип файла, замаскированный под PDF файл и файл больше 10 МиБ:
   ожидается понятная ошибка, документ не создаётся.
5. Удалить `PENDING`; документ исчезает. Документ `ACCEPTED`/`REJECTED` удалить нельзя
   (изменение статуса пока только через тестовую фикстуру, экрана комиссии нет).
6. Войти организатором события: открыть «Заявки», проверить статусы, «нет справки»,
   открыть документы участника. Справка со сроком раньше старта даёт предупреждение;
   посев остаётся доступным по существующим правилам.
7. Проверить API чужим родителем и организатором другой организации: 404/403.
8. В сетевых запросах получить signed URL; удалить `signature`, изменить подпись,
   дождаться истечения 10 минут или использовать токен другого пользователя: 404.
9. Проверить ciphertext в локальном каталоге и записи `file_access_log` при скачивании.

## Автоматические проверки и границы

`mvn -q test` включает Local/S3 storage unit-тесты, Testcontainers PostgreSQL,
проверку модульной архитектуры, QA04-матрицу всех endpoint-ов и интеграционные проверки
шифрования, доступа, подписи, журнала, транзакций, события и постоянного количества SQL
при росте списка с 1 до 21 заявки (3 запроса, из них 1 на документы).

Frontend: `npm test`, `npm run build`, `npm run lint`.
Браузерные тесты с подменённым API: `npx playwright test --config playwright.documents.config.ts`
(при необходимости `PLAYWRIGHT_CHROMIUM_EXECUTABLE=/usr/bin/chromium`).
Они проверяют загрузку, скачивание и отсутствие переполнения на 375 px, статусы и фильтр.

Работа реальной камеры телефона и живого Selectel/Yandex S3 требует ручной проверки.
S3 unit-тест проверяет ciphertext, расшифровку и закрытый gateway на mock AWS client.
Комиссия, напоминания, печать листа допуска, обязательное блокирование посева и notifications
не реализованы по границам M04. Демо-сид и Excel-импорт не менялись.
