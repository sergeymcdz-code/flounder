Проверено по исходникам `main` на коммите `8d709be39f47b6d1a8781059c3f732e5e01512c7`, 17.10.2026.
Задание прочитано из [ветки docs/S10-task, PR #67](https://github.com/sergeymcdz-code/flounder/pull/67), а не из ещё отсутствующего файла в main.

В S10 требуется `DEMO_OWNER_EMAIL` с двумя детьми в разных событиях, стабильные профили и повторный запуск без дублей. В начале задания также указано: «если без изменения API задачу выполнить нельзя — остановиться и описать в PR, что именно нужно». Поэтому генератор, advance и сброс календаря пока не добавлены. Backend, события и тесты S02 A/B/C не изменены.

## Уточнение владельца от 17.10.2026

Эти требования приоритетнее исходного текста S10 и применяются при возобновлении реализации:

| Параметр / сценарий | Уточнённое требование |
|---|---|
| `CALENDAR_WEEKS` | По умолчанию **25**; число недель остаётся параметром |
| `CALENDAR_START` | По умолчанию понедельник за **12 недель до недели DEMO_DATE**; старт остаётся параметром |
| Горизонт | 12 недель назад, текущая неделя и 12 недель вперёд |
| Число событий | ≈28–30 с дополнительными соревнованиями в отдельных неделях |
| Все прошлые недели | `COMPLETED`, все заплывы завершены, полные опубликованные результаты и анонимные протоколы |
| Варианты архивных результатов | У ≈1/3 прошлых событий — 1–2 `CORRECTED` и DNS/DNF; у 2–3 прошлых событий — DSQ |
| Текущая неделя | `REGISTRATION_CLOSED`, готовые посев/стартовый протокол, первые два заплыва первой сессии завершены |
| +1…+3 недели | `REGISTRATION_OPEN`, заполненность 40–90 %, исправления, очередь и документы по исходному заданию |
| +4…+8 недель | `PUBLISHED`, открытие регистрации по датам lifecycle M06, заявок 0–20 % |
| +9…+12 недель | `PUBLISHED` без заявок, одно событие `DRAFT` по исходному заданию |
| Бюджет полного прогона | Не более **90 минут** |
| Бюджет `--advance` | Не более **10 минут** |

Например, при `DEMO_DATE=2026-10-19` начало по умолчанию — `2026-07-27`, последняя неделя начинается `2027-01-11`. Основные субботние соревнования приходятся на 01.08.2026–16.01.2027. План и будущий снимок-тест должны проверять этот горизонт, даты, статусы и числа заявок; даты не фиксировать в коде.

Остальные требования S10 сохраняются. Это уточнение не снимает описанный ниже блокер нескольких профилей одного родителя. Реализации плана и снимок-теста в текущем PR ещё нет.

| ID | Severity | Где | Ожидается по S10 | Фактически по исходникам | Предлагаемое исправление |

| S10-01 | blocker | Публичная подача заявки и профили пользователя | Один родитель владеет двумя самостоятельными профилями детей; их profile ID сохраняются между событиями и повторными запусками | Подача всегда выбирает единственный профиль по user ID. ## Как проверить вручную после подготовки отдельного локального стенда

Эти шаги — план воспроизведения, а не отчёт о выполненной проверке. Использовать отдельного тестового участника; `DEMO_OWNER_EMAIL` и S02 A/B/C для эксперимента не использовать.

1. Создать два отдельных события через API организатора, опубликовать подходящие виды для мальчиков 2014 г. р. и открыть регистрацию. Даты открытия/закрытия должны включать реальное текущее время backend.
2. Войти одним тестовым участником. В первое событие отправить `POST /api/v1/public/events/{slug}/registrations` с `profile` ребёнка A (например, Календарев Артём, 2014-02-10, M) и одним элементом `items` с доступным `eventDisciplineId` и `seedTimeMs: 45000`.
3. Тем же токеном подать заявку ребёнка B (Календарев Борис, 2014-06-20, M) во второе событие. В этой ветке проверки оба ребёнка ранее не импортированы.
4. Организатором прочитать `GET /api/v1/events/{eventId}/registrations` для обоих событий и сравнить `participantProfileId`. По текущему коду ID одинаков; ожидаются два разных ID, доступных одному родителю.
5. Повторить на другом чистом тестовом участнике, предварительно импортировав ребёнка B стандартным Excel-импортом во второе событие. После заявки ребёнка A попытка подать B тем же родителем должна дойти до ветки `identity.profile_already_attached`; точный HTTP-код нужно зафиксировать при выполнении.
6. После backend-исправления повторить подачу и проверить, что ID и данные обоих детей стабильны, а чужой пользователь не может использовать их профили.

Регрессионный тест для backend-задачи должен создавать одного родителя, двух детей и две заявки, проверять разные profile ID, повторное использование каждого профиля и запрет доступа другого родителя. Существующие проверки запрета второй привязки потребуется согласовать с новой моделью; в S10 они не менялись.

Во время первоначальной проверки управляемая среда оставалась в состоянии `pending` без доступного executor. При фиксации уточнения владельца executor стал доступен, но `git fetch` завершился ошибкой соединения с настроенным proxy:8080; локальный checkout не содержит ветку PR. Правка документа выполнена через GitHub connector и проверена обратным чтением. `npm test` / typecheck в scripts/demo, `mvn -q test`, frontend `npm test`, build и lint не выполнялись. Новых автотестов нет: реализация остановлена до согласования и изменения контракта, backend-тесты вне разрешённой области. Требование QA00 о регрессии для функционального дефекта остаётся открытым для backend-задачи.

Полный HTTP-прогон календаря, повторный запуск, advance, анонимные PDF и SQL-сброс не выполнены: реализации календаря нет. **Время полного прогона и объём БД после: не измерены.** На sportgate.pro запросы с изменением данных не отправлялись.
