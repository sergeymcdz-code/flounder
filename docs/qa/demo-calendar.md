# S10 — календарь тестовых данных SportGate

Календарь работает только через HTTP API выделенного демо-стенда. Требуется `DEMO_SEED_ENABLED=true`; защита `production/prod` из S02 сохранена. Скрипт использует ту же демо-организацию, аккаунты, регламент, Excel-импорт и PDF-fixture, что и S02. A/B/C не изменяет. Собственных миграций и изменений backend в S10 нет; в ветку S10 слита SEC01 (#75) с миграцией V050 и защитой служебного аккаунта.

Уточнения владельца приоритетнее исходного S10: **25 недель (−12…+12), ≈28–30 соревнований, полный прогон ≤90 минут, advance ≤10 минут**. Блокер S10-01 снят: у `DEMO_OWNER_EMAIL` один ребёнок, тот же профиль участвует в трёх событиях календаря — прошедшем и двух открытых. При наличии S02 C используется его профиль; несовпадающий существующий профиль/служебный аккаунт отклоняется без изменения данных пользователя.

## Что создаётся

По умолчанию `DEMO_DATE=2026-10-19`, `CALENDAR_START=2026-07-27`, `CALENDAR_WEEKS=25`, `CALENDAR_PREFIX` пуст. `CALENDAR_START` должен быть понедельником, число недель — целым 1–104. Начало по умолчанию — понедельник за 12 недель до недели DEMO_DATE. Соревнования проходят по субботам; в каждой шестой неделе, начиная с третьей, добавляется воскресенье в другом городе. Сезон по умолчанию содержит 29 событий, из них 14 завершённых; один дальний черновик скрыт публично.

Девять площадок: два бассейна Самары, Тольятти, Казань, Уфа, Саратов, Ульяновск, Пенза, Оренбург. Шесть — 25 м / 8 дорожек, три — 50 м / 10 дорожек. Время сессий — 10:00 и 15:00 в TZ площадки; у части событий одна сессия. Площадки в текущем API глобальные: используются названия бассейнов и города без бренда платформы, а все события принадлежат исключительно демо-организации. Существующие чужие площадки/события не перенастраиваются.

Названия городских кубков, мемориала и остальных одиночных соревнований содержат месяц/год; «этап N» используется только в серии кубка SportGate и нумеруется последовательно по событиям (1, 2, 3, 4 по умолчанию). API не поддерживает переименование событий: у ранее созданных этапов сохраняются прежние названия и slug, скрипт распознаёт их без дублей и сброса результатов. Названия площадок — например «Бассейн «Волга», Самара». Описание читается публично: `Тестовые данные SportGate. Сезон с 2026-07-27, 25 недель, неделя 1, суббота (точка отсчёта 2026-10-19).` У копии добавляется `, копия «Резерв»` перед последней точкой. По этому формату скрипт проверяет исходные параметры сезона.

Пул — 900 уникальных пловцов 2010–2016 г. р. из 16 клубов. Исходные 120 спортсменов set-M и восемь их клубов сохранены как одна когорта; добавлены ещё восемь региональных клубов. Около 14–15% обычных заявок — гости. Спортсмены повторяются между неделями; заявочные времена немного улучшаются по ходу сезона. В names.ts ≥80 имён каждого пола и ≥250 фамилий; прежние имена S02 фиксированы и не меняются при расширении пулов. В API создаются только использованные профили, а не весь резерв.

На событие — 6–12 видов из пула вольного стиля, спины, брасса, баттерфляя и комплекса, М/Ж, три возрастные группы. Часть событий имеет общий лимит; очередь создаётся обычной публичной подачей после заполнения лимита M-50. Дополнительные аккаунты — только семь `s10-parent-N@flounder.demo` и владелец; остальные профили без e-mail.

Все прошлые недели завершены с полными опубликованными результатами и протоколами. У четырёх из 14 прошлых событий — 1–2 CORRECTED и три DNS/DNF; у трёх — DSQ. Текущая неделя закрыта, посев опубликован, первые два заплыва первой сессии FINISHED, табло показывает третий. На +1…+3 неделях — открытая регистрация, 3–6 заявок на исправлении, у ближайшего субботнего события четыре WAITLISTED. Два исходных открытых события имеют по два PDF-документа. +4…+8 — PUBLISHED, заполнение 0–20%; дальше — без заявок, один DRAFT.

## Запуск на сервере без Node

Из корня checkout, как в README S02. Предварительно настроить `scripts/demo/.env`: API_URL, ADMIN_EMAIL/ADMIN_PASSWORD, DEMO_PASSWORD (либо пароли аккаунтов), DEMO_OWNER_EMAIL и DEMO_SEED_ENABLED=true. Общий бутстрап S02/S10 сначала ищет служебный аккаунт: отсутствующий создаёт до первого входа, а при неверном пароле существующего останавливается без попытки создания. ADMIN_EMAIL должен указывать на рабочего bootstrap-администратора; собственные ADMIN_PASSWORD/DEMO_PASSWORD должны содержать не менее 12 символов. Пароли существующих аккаунтов должны совпадать; .env не печатать и не добавлять в Git. Почту на локальном стенде отключить; на сервере учитывать уведомления на вымышленные адреса.

```bash
cd /home/deploy/flounder
mkdir -p /home/deploy/backups
flock -n /home/deploy/backups/demo-calendar.lock \
  docker run --rm --user "$(id -u):$(id -g)" -e HOME=/tmp \
  -e DEMO_DATE=2026-10-19 -e CALENDAR_WEEKS=25 \
  -v "$PWD":/repo -w /repo/scripts/demo node:22-alpine \
  sh -eu -c 'npm ci && npx tsx calendar.ts'
```

Для отдельной копии добавить `-e CALENDAR_PREFIX="Резерв"`. Повторный запуск с тем же DEMO_DATE/началом/префиксом достраивает отсутствующее, не создаёт дублей и не пересоздаёт опубликованные заплывы. При изменении дат или состава существующего события скрипт предлагает reset. CALENDAR_START после первого сида менять только через reset. После advance использовать advance для текущего состояния; повторный seed не понижает уже достигнутые статусы и сохраняет накопленные заявки.

События обрабатываются последовательно, заявки импортируются HTTP-пачками не более 100 строк. В конце — JSON `S10` с неделями, датами, slug, статусами, заявками, заплывами, результатами и временем. Публичные ссылки брать из фактического slug: `/e/{slug}`, `/start-list`, `/results`, `/live`.

Сверка фактических slug и статусов публичного каталога (на чистом календаре 28 карточек):

```bash
curl -fsS https://sportgate.pro/api/v1/public/events | python3 -c 'import json,sys; payload=json.load(sys.stdin); events=payload if isinstance(payload,list) else payload.get("items",payload.get("content",[])); [print(e["eventStartAt"][:10], e["status"], e["publicSlug"]) for e in sorted(events,key=lambda e:e["eventStartAt"])]'
```

Локально: `cd scripts/demo && npm ci && npx tsx calendar.ts`. Для просмотра плана без HTTP и секретов: `npx tsx calendar.ts --plan`. Проверки: `npm test && npm run typecheck`.

## Еженедельное обновление

```bash
cd /home/deploy/flounder
flock -n /home/deploy/backups/demo-calendar.lock \
  docker run --rm --user "$(id -u):$(id -g)" -e HOME=/tmp \
  -v "$PWD":/repo -w /repo/scripts/demo node:22-alpine \
  sh -eu -c 'npm ci && npx tsx calendar.ts --advance'
```

`--advance` по умолчанию использует текущую UTC-дату сервера, **игнорируя DEMO_DATE из .env**. Для проверки на фиксированной дате передать DEMO_DATE непосредственно в окружение команды (в Docker — `-e DEMO_DATE=2026-10-26`). Исходные начало, длина, anchorDate и префикс читаются из человекочитаемых описаний событий, поэтому сезон не сдвигается на неделю и новые хвостовые события не создаются. CALENDAR_PREFIX ограничивает обновление выбранной копией (пустое значение — копия без префикса); если переменная вообще не задана, обновляются все календари демо-организации. Более ранняя дата не откатывает уже достигнутую неделю. Ошибка отдельного события попадает в поле `error` его сводки; остальные события обрабатываются, затем CLI завершается с кодом 1. Повторный запуск продолжает обработку. При ошибке до завершения fill скрипт читает фактические заявки события для сводки; если чтение недоступно, `registrations: null` означает неизвестное количество.

Режим закрывает текущую неделю, завершает прошедшие с результатами, открывает следующие, публикует дальний DRAFT при приближении до восьми недель. В каждую открытую неделю добавляется 10–15 заявок в пределах общего лимита; новые исправления и очередь входят в этот бюджет. Очередь переходит к ближайшему открытому субботнему событию. При закрытии сценарные заявки исправляются/подтверждаются через API, лимит очереди расширяется; затем формируется посев. Пропущенные недели учитываются детерминированно. Повтор в ту же неделю не добавляет данных.

Пример cron **не включён**: одна закомментированная строка добавлена в `infra/crontab.example`. Для хоста с TZ Europe/Moscow — понедельник 06:00 МСК; для UTC-хоста заменить час на 3. Не использовать две строки одновременно. Пример целиком:

```cron
0 6 * * 1 cd /home/deploy/flounder && /usr/bin/flock -n /home/deploy/backups/demo-calendar.lock /usr/bin/docker run --rm --user "$(id -u):$(id -g)" -e HOME=/tmp -v "$PWD":/repo -w /repo/scripts/demo node:22-alpine sh -eu -c 'npm ci && npx tsx calendar.ts --advance' >> /home/deploy/backups/demo-calendar.log 2>&1
```

Вручную устанавливать только после проверки часового пояса и путей. flock защищает от пересечения с ручным сидом. Скрипт не устанавливает cron сам.

## Сброс календаря

Сначала резервная копия БД и файлов. Из корня checkout выполнить read-only план; A/B/C не попадают в календарный выбор:

```bash
cd /home/deploy/flounder
docker run --rm --user "$(id -u):$(id -g)" -e HOME=/tmp \
  -e DEMO_CALENDAR=true \
  -v "$PWD":/repo -w /repo/scripts/demo node:22-alpine \
  sh -eu -c 'npm ci && npx tsx reset.ts'
```

С `-e CALENDAR_PREFIX="Резерв"` выбирается только эта копия. **Без CALENDAR_PREFIX выбираются все копии календаря, включая копии с QA-префиксами**, по описанию «Тестовые данные SportGate». Явный DEMO_SLUGS дополнительно проверяется; чужой или отсутствующий slug останавливает сброс. Проверяются демо-организация, известная календарная площадка, UUID/название/slug/имя площадки. JSON `demo_targets` и точная команда psql печатаются без записи в БД.

Поле `venue` в JSON берётся из проверки reset.ts; JSON целей руками не редактировать.

Если на сервере нет psql, взять **точный JSON** из строки `demo_targets:`, задать его в переменной S10_DEMO_TARGETS и применить тот же reset.sql через PostgreSQL-контейнер после остановки API/фоновых записей:

```bash
# S10_DEMO_TARGETS contains the reviewed JSON from reset.ts, not a hand-built list.
docker compose -f infra/compose.prod.yaml --env-file infra/.env.prod stop api
docker exec -i flounder-postgres psql -X -U sport_user -d sport_platform \
  -v ON_ERROR_STOP=1 -v "demo_targets=$S10_DEMO_TARGETS" < scripts/demo/reset.sql
docker compose -f infra/compose.prod.yaml --env-file infra/.env.prod start api
curl -fsS https://sportgate.pro/actuator/health
```

Календарь старой версии с JSON в описании нужно сбросить (`DEMO_CALENDAR=true npx tsx reset.ts`, затем применить выведенный SQL) перед повторным сидом. Старые названия площадок распознаются для этого сброса. Ранее сохранённый demo_targets без поля `venue` получить заново через reset.ts.

SQL повторно проверяет все цели, включая точное имя площадки из `demo_targets.venue`, в одной транзакции. Удаляются документы выбранных событий, результаты, заплывы, заявки и осиротевшие импортированные профили; общие профили с заявками в S02/других событиях и аккаунты сохраняются. Площадки календаря SportGate (включая прежние брендированные названия) и шаблоны дисциплин `T10-*` остаются в общих справочниках. Физические PDF остаются для штатной очистки хранилища. Сброс S02 по DEMO_EVENTS/DEMO_SLUGS без DEMO_CALENDAR продолжает работать по прежним правилам.

## Ограничения и проверка

- S05 не слит в базовый main bdb8cd8: все взносы нулевые, PAID/PENDING/WAIVED не имитируются. Перед использованием на main с S05 проверить новый платёжный контракт.
- Публичная подача и resubmit используют реальные часы backend. Для подготовки сценариев скрипт временно снимает границы регистрации и восстанавливает их в finally; после прерывания восстанавливает отсутствующие границы из плана. При искусственном DEMO_DATE открытым событиям при необходимости корректируются даты регистрации, чтобы публичная форма работала и по реальным часам. Если плановое закрытие в будущем, оно сохраняется; иначе граница ставится не раньше чем через семь реальных дней. При DEMO_DATE, отличной от реальной даты, шедулер закроет открытые события по этой границе. Даты соревнований/сессий не сдвигаются.
- Посторонние заявки в незавершённых событиях сохраняются и учитываются в `registrations`/`states` сводки и лимите очереди; свои заявки добавляются только при отсутствии. Наличие своих заявок проверяется и после завершения; посторонние заявки с результатами сохраняются при последующих advance.
- Окончательные результаты охватывают все подтверждённые старты. DNS/DNF/DSQ не получают мест. Исправления выполняются секретарём после публикации; судья используется для исходного ввода.
- Сезон конечный. Для нового сезона выполнить seed с другим CALENDAR_PREFIX и подходящими CALENDAR_START/DEMO_DATE. Состав, имена или схему маркера уже заполненного календаря менять через reset соответствующих событий.
- Серверное время, сетевые задержки и скорость PDF на sportgate.pro отдельно не измерялись. На production данные этим заданием не создавались.
