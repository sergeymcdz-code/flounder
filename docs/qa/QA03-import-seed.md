Риск относится к тестовому tooling, в частности при появлении недоверенных worker options или доступного извне mock-сервера; текущий `vitest run` такого сервера не публикует.

## Не удалось проверить и почему

- Объединение импортированного спортсмена с другим профилем аккаунта — отдельная задача QA03-04 (вместе с владением профилем QA04-10). Сейчас конфликт возвращает 409, профиль не переименовывается. Будущий успешный сценарий зафиксирован в `Qa03KnownDefectsIT`, запускается явно: `mvn -q test -Dtest=Qa03KnownDefectsIT`; обычный `mvn test` зелёный.
- Реальные Android/iOS, sportgate.pro и мобильная сеть не проверялись. Проверка 375 px выполнена в Chromium с эмуляцией viewport на локальном API.
- `reset.ts --apply` с реальным хостовым psql не запускался: psql использован внутри контейнера для реального `reset.sql`; orchestration `--apply` покрыта существующими автотестами.
- Инструкция запуска с буквальным `JWT_SECRET=local-development-secret-must-be-at-least-32-characters-long` дала 500 при login (JwtService ожидает Base64). Для дальнейшего локального прогона использован валидный тестовый Base64-секрет. Это проблема prerequisites в области identity/документации запуска; код авторизации в QA03 не менялся.
