# Flounder — техническое задание на MVP «50 соревнований» (горизонт до июля 2027)

Версия 1.0 · 12.10.2026. Надстройка над `02_ТЗ_демо.md`: всё, что там описано, входит в MVP. Здесь — что добавляется, нефункциональные и юридические требования, приоритеты и критерии успеха.

## 1. Цель и критерии успеха

Цель MVP: региональный организатор проводит соревнование по плаванию на 200–1 000 участников полностью в Flounder — от заявок до публикации результатов — без Excel и мессенджеров.

Критерии (из рабочей гипотезы проекта, измеряются на пилотах):
- ручные операции организатора на пути «заявки → протокол → результат» сокращаются ≥ 50 % (ΔT, хронометраж baseline vs Flounder);
- результаты заплыва публикуются ≤ 7 мин после финиша (p95 по событию);
- 0 ошибок стартового протокола (валидатор) и 0 расхождений итогового протокола с судейскими записями;
- SUS ≥ 70, NPS ≥ 30 у организаторов пилотов; ≥ 50 % пилотных организаторов соглашаются на платный старт.

Объёмы: 50 соревнований за первый сезон, до 1 000 участников и 100 заплывов в день на событие, до 20 одновременно активных организаторов, до 1 000 одновременных зрителей табло на событие.

## 2. Роли (дополнение)
`platform_admin`, `organizer` (владелец/менеджер организации), `secretary` (= operator: заявки, оплаты, протоколы, результаты), `judge` (результаты своих заплывов), `coach` (подаёт и правит заявки своих спортсменов, видит их результаты), `participant`/`parent` (свои заявки, документы, результаты), `viewer` (аноним). Права — матрица в приложении А (составить на этапе 2 по модулям × действиям).

## 3. Функциональные требования по модулям

### 3.1 Организации и события
- Самостоятельная регистрация организации с модерацией администратором; несколько пользователей в организации с ролями; справочник площадок с параметрами бассейна (дорожки, длина, хронометраж: ручной/электронный).
- Шаблоны соревнований: сохранить структуру (сессии, виды, группы, взносы) и создать новое событие из шаблона; клонирование события.
- Положение/регламент события: файл (PDF) + структурированные поля (сроки регистрации, взносы, допуск, документы) — версии (`regulation_versions`, уже есть).
- Статусы события: DRAFT → PUBLISHED → REGISTRATION_OPEN → REGISTRATION_CLOSED → LIVE → COMPLETED → ARCHIVED; автопереходы по датам (открытие/закрытие регистрации по расписанию).
- Лимиты: по событию, по виду, по возрастной группе; лист ожидания.

### 3.2 Регистрация и заявки
- Каналы: публичная форма (родитель/спортсмен), кабинет тренера (массовая подача за команду, импорт Excel своего клуба), импорт Excel организатором, (этап 3) импорт Lenex.
- Профиль спортсмена: ФИО, дата рождения, пол, клуб/город, разряд, тренер, контакты законного представителя (для несовершеннолетних), история стартов. Дедупликация по ФИО+дата рождения; объединение дублей администратором.
- Документы: медицинская справка (дата, срок действия), страховка, согласие родителя, согласие на обработку ПДн — загрузка файлов (jpg/pdf ≤ 10 МБ), статусы проверки (не загружен / на проверке / принят / отклонён с причиной), напоминания. Автопроверка допуска: возраст, пол, лимиты, срок справки ≥ даты старта.
- Мандатная комиссия онлайн: экран «проверка документов» со списком по клубам, массовое подтверждение, печать листа допуска.
- Изменение заявки: до закрытия регистрации — участником/тренером; после — только организатором с аудитом; снятие с дистанции с указанием причины.
- Уведомления по каждому изменению статуса (см. 3.7).

### 3.3 Оплата
- Этап 2 (после регистрации юрлица в РФ): онлайн-оплата взноса через ЮKassa (уже есть каркас) и/или Т-Банк; чеки 54-ФЗ через провайдера; возвраты; взнос по виду/по количеству дистанций/по событию; скидки/промокоды — по потребности пилотов.
- Модель расчётов: вариант А — организатор принимает платежи на свой аккаунт провайдера (Flounder — только интеграция, без приёма денег; рекомендуемый старт); вариант Б — Flounder как платёжный агент со сплит-платежами (требует договора-оферты, 115-ФЗ комплаенс, бухгалтерию) — только после юридического заключения.
- Биллинг Flounder для организатора: тариф за событие (45/90/150 тыс. ₽ по размеру старта — проверяется пилотами), счёт-оферта, акт; на этапе MVP — вручную, в системе только флаг «оплачен тариф».

### 3.4 Программа, посев, расписание
- Всё из ТЗ демо + : эстафеты (команды, этапы), предварительные/финальные заплывы (SW 3.1.1.3 круговой посев, финалы A/B), несколько бассейнов/дней, перерывы и церемонии в расписании, ручное перетаскивание заплывов, блокировка опубликованных, пересчёт при задержке («сдвинуть на +20 мин»), минимальный интервал между стартами спортсмена как жёсткое ограничение с автоподбором заплыва (переход на CP-решатель, если rule-based не справляется — по результатам эксперимента Судовцева).
- Стартовые номера (bib), карточки заплыва для судей (печать).

### 3.5 Результаты и протоколы
- Ввод: секретарь (как в демо), судья по дорожке с телефона (опционально, по решению организатора), импорт из файлов электронного хронометража (Omega/Colorado/«Старт»: CSV/Lenex — этап 3), поправки с историей (аудит, кто/когда/было/стало), дисквалификации с кодом правила.
- Расчёты: места в абсолюте и по группам, очки FINA/World Aquatics по таблице года, выполнение разрядов ЕВСК (таблица нормативов — загружаемый справочник), командный зачёт по регламенту (конфигурация очков за места), рекорды соревнований.
- Протоколы: стартовый, по виду, итоговый, сводный, лист награждения (1–3 места по группам), грамоты (шаблон с подстановкой) — серверный PDF (OpenHTMLtoPDF с кириллическими шрифтами), экспорт XLSX/CSV, (этап 3) Lenex-экспорт для федераций.
- Публикация: по заплыву/виду/событию; «неофициальный → официальный» статус; протесты (отметка, пересчёт).

### 3.6 Публичные страницы и приложение
- Всё из демо + страница организации (календарь стартов), архив результатов, профиль спортсмена с историей (при согласии), поиск по спортсменам, подписка на уведомления о своём заплыве («за 3 заплыва до вашего»), табло для ТВ/проектора (режим большого экрана, автопрокрутка).
- Мобильное приложение: PWA (демо) → Expo (React Native) с тем же API: уведомления push (Firebase + RuStore push), офлайн-кэш расписания; публикация в RuStore, Google Play, App Store (этап 3).
- Real-time: SSE `GET /api/v1/public/events/{slug}/stream` (события: live, result_published, schedule_changed); fallback — опрос.

### 3.7 Уведомления
Каналы: e-mail (транзакционные: Unisender Go / SMTP), Telegram-бот (привязка аккаунта по коду; уведомления и быстрые ответы «мой заплыв»), web-push/push. События: подтверждение заявки, запрос документов, оплата, публикация стартового протокола, изменение расписания, «ваш заплыв через N», результат, награждение. Шаблоны с переменными, настройки организатора (что слать), журнал доставки. Массовые рассылки по сегментам (клуб, вид, статус).

### 3.8 Аналитика и отчёты
Панель события: заявки по дням, воронка (подано → подтверждено → оплачено → допущено), распределение по видам/группам/клубам, загрузка сессий (минуты), время публикации результатов (критерий 2), ошибки валидатора; панель организации: события, участники, выручка (если оплаты), повторные участники. Экспорт в XLSX. Метрики продукта (для гипотез): время ручных операций по шагам (таймеры UI), число правок протокола после генерации.

### 3.9 Администрирование и аудит
Справочники (виды спорта, дисциплины, нормативы, таблицы очков), пользователи, организации, тарифы, журнал аудита с фильтрами, экспорт, настройки уведомлений, фича-флаги (эстафеты, онлайн-оплата, судьи с телефона).

## 4. Нефункциональные требования
- Производительность: API p95 ≤ 1 с; посев ≤ 5 с/дисциплина; страница табло ≤ 2 с на 4G; 1 000 одновременных зрителей — через кэш и SSE.
- Надёжность: 99,5 % в дни стартов; ежедневный бэкап БД (30 дней) + файлов; RPO 24 ч, RTO 2 ч; процедура восстановления проверяется раз в квартал.
- Безопасность: OWASP ASVS L1; refresh-токены и выход со всех устройств; ограничение попыток входа; TLS 1.2+; секреты в переменных окружения/секрет-хранилище; шифрование файлов документов (AES-256 at rest), подписанные временные ссылки; журнал доступа к документам; зависимости — Dependabot.
- 152-ФЗ: серверы и бэкапы в РФ; политика конфиденциальности и согласия (отдельно — на спецкатегорию «здоровье» для медсправок, отдельно — согласие родителя для < 18 лет, форма согласия на передачу третьим лицам — организатору); уведомление Роскомнадзора об обработке ПДн; локализация ПДн; сроки хранения и удаление по запросу; DPA-приложение к договору с организатором (организатор — оператор, Flounder — обработчик по поручению или совместный оператор — зафиксировать юристом).
- Наблюдаемость: structured-логи, correlation-id, Sentry (ошибки backend/frontend), метрики Prometheus + Grafana (или Uptime Kuma + алерты в Telegram на старте), health-checks.
- Качество: unit + интеграционные тесты (Testcontainers), e2e Playwright на ключевой путь (заявка → посев → результат), покрытие ядра посева/ранжирования ≥ 90 %, CI на каждый PR, staging-стенд.
- Доступность: WCAG 2.1 AA для публичных страниц; поддержка Chrome/Safari/Яндекс.Браузер последних 2 версий; минимальная ширина 360 px.
- Локализация: русский; архитектурно — i18n-готовность (строки в ресурсах).

## 5. Архитектурные решения этапа 2
- SSE и кэш публичных представлений (Caffeine → Redis при > 1 сервере).
- Файлы — S3-совместимое хранилище в РФ (Selectel/Yandex Object Storage/VK Cloud), доступ по пресайн-ссылкам.
- Очередь задач для уведомлений и PDF — Spring `@Async` + таблица outbox (Modulith event publication уже есть) → при росте — Redis/RabbitMQ.
- Expo-приложение — отдельный репозиторий/папка `apps/mobile`, общий OpenAPI-клиент (генерация `openapi-typescript`).
- Lenex-импорт/экспорт — модуль `interop`.
