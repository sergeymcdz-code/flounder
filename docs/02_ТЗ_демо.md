## 2. Сценарии (user stories) с критериями приёмки

### US-1. Организатор настраивает соревнование
Как организатор, я создаю событие с площадкой (бассейн: число дорожек 6/8/10, длина 25/50 м), сессиями (дата, время старта, пауза между видами) и видами программы.
Приёмка: событие создаётся пользователем с ролью `organizer`, состоящим в организации (без `platform_admin`); дисциплина имеет дистанцию, стиль, пол, набор возрастных групп, режим посева, сессию и порядок; событие можно опубликовать и открыть регистрацию из UI.

### US-2. Заявки: импорт из Excel и публичная форма
Как организатор, я загружаю Excel со списком заявок и получаю отчёт: сколько создано, сколько с ошибками, какие строки и почему. Как родитель, я с телефона подаю заявку на 1–3 вида программы с заявочным временем.
Приёмка: шаблон Excel скачивается из UI; файл на 200 строк импортируется ≤ 10 с; повторный импорт того же файла не создаёт дублей (ключ: фамилия+имя+дата рождения+пол → профиль; профиль+дисциплина → заявка); ошибки показаны по строкам; публичная форма работает на экране 375 px.

### US-3. Автоформирование заплывов
Как организатор, я нажимаю «Сформировать заплывы» по дисциплине или по всему событию и получаю стартовый протокол: заплывы, дорожки, расчётное время старта; и отчёт валидатора.
Приёмка: алгоритм соответствует §4 (тесты из §4.6 проходят); 200 заявок × 4 дисциплины формируются ≤ 5 с; валидатор возвращает 0 ошибок на корректных данных и находит все нарушения из §4.5; повторный запуск на тех же данных даёт тот же результат.

### US-4. Печать и публикация стартового протокола
Приёмка: страница «Стартовый протокол» печатается на A4 (Chrome → Печать → PDF) без обрезания: шапка соревнования, по каждому виду — таблица заплывов (№ заплыва, дорожка, фамилия имя, год рождения, клуб, заявочное время, время старта); публичная ссылка `/e/{slug}/start-list` открывается без входа; QR на ссылку показывается в UI организатора.

### US-5. Изменения и пересчёт
Как организатор, я снимаю участника (статус WITHDRAWN) или добавляю заявку и нажимаю «Пересчитать».
Приёмка: заплывы в статусе DRAFT перестраиваются полностью; для PUBLISHED-заплывов участник помечается как снятый (дорожка пустая) без перестановки остальных, валидатор выдаёт WARNING «опубликованный заплыв изменён»; расписание пересчитывается.

### US-6. Ввод и публикация результатов
Как секретарь/судья, я открываю заплыв, ввожу время каждой дорожке в формате `мм:сс.сс` (допустимо `сс.сс`, `ч:мм:сс.сс`), выбираю DNS/DNF/DSQ, нажимаю «Сохранить и пересчитать места», затем «Опубликовать».
Приёмка: места считаются в абсолюте по виду программы и внутри возрастной группы; равные времена делят место (1, 1, 3); DNS/DNF/DSQ без места; итоговый протокол печатается на A4; публичная страница результатов обновляется. **Исправление после публикации:** повторная отправка результатов по уже опубликованному заплыву разрешена ролям `operator|organizer`; изменённые записи получают статус `CORRECTED`, места пересчитываются, публичная страница обновляется, предыдущая таблица сохраняется в `rule_execution_logs` (kind = RANKING).

### US-7. Табло участника (PWA)
Приёмка: публичная страница `/e/{slug}/live` показывает «Сейчас: вид №, заплыв №», следующие 3 заплыва со временем, кнопку «Найти себя» (поиск по фамилии → все заплывы и результаты спортсмена); страница обновляется каждые 15 с; сайт устанавливается на телефон как приложение (manifest + service worker), иконка и название «Flounder».

## 4. Алгоритм посева и расписания (модуль `scheduling`)

Эталонная реализация на TypeScript приложена (`reference/seeding.ts`, `lanes.ts`, `schedule.ts`) — переносится на Java 1:1 как чистые классы без Spring-зависимостей в пакете `com.acme.sportplatform.scheduling.domain`.

### 4.1 Вход
Дисциплина (дистанция, стиль, пол, возрастные группы, режим посева), площадка (число дорожек, `minSwimmersInHeat` = 3), заявки со статусом `CONFIRMED | PAID | ADMITTED` и снимком участника (фамилия, имя, год рождения, пол, клуб), заявочное время `seed_time_ms` или `null` (NT).

### 4.2 Допуск (каждая отклонённая заявка — ERROR в отчёт, в посев не идёт)
- `ATHLETE_NOT_FOUND` — нет профиля;
- `DUPLICATE_ENTRY` — второй раз тот же спортсмен в этом виде;
- `GENDER_MISMATCH` — пол спортсмена ≠ пол вида (если вид не `X`);
- `AGE_GROUP_MISMATCH` — год рождения не попадает ни в одну группу вида (если группы заданы). Правило попадания: `birthYearFrom == null || birthYear >= birthYearFrom` и `birthYearTo == null || birthYear <= birthYearTo` (from — старший год, меньшее число; to — младший год, большее число; `from <= to`), пол группы `X` или равен полу спортсмена.

### 4.3 Сортировка
По `seed_time_ms` по возрастанию; `NT` — в конец; при равенстве — по фамилии, имени (`ru` collation), затем по id заявки. Детерминировано.

### 4.4 Размеры заплывов (SW 3.1.1.1) и дорожки (SW 3.1.1.2)
`heatSizes(n, lanes, min=3)`:
- `n ≤ lanes` → `[n]`;
- `rest = n mod lanes`; `rest == 0` → все заплывы по `lanes`;
- `rest ≥ 3` → `[rest, lanes, lanes, …]` (слабейший заплыв первый, неполный);
- `rest ∈ {1,2}` → `[3, lanes − (3 − rest), lanes, …]` — недостающих берём из второго заплыва.
Примеры (8 дорожек): 17 → `[3, 6, 8]`; 9 → `[3, 6]`; 16 → `[8, 8]`; 11 → `[3, 8]`; 20 → `[4, 8, 8]`; (6 дорожек): 7 → `[3, 4]`; 13 → `[3, 4, 6]`.

Заполнение: самые быстрые — в **последний** заплыв, далее по убыванию. Порядок дорожек `laneOrder(lanes)`: 8 → `4,5,3,6,2,7,1,8`; 6 → `3,4,2,5,1,6`; 10 → `5,6,4,7,3,8,2,9,1,10` (центр, затем попеременно вправо/влево). Внутри заплыва i-й по скорости получает i-ю дорожку из этого порядка.

Режим `BY_AGE_GROUP`: заявки делятся по группам вида в порядке их перечисления; каждая группа сеется отдельно; номера заплывов сквозные по виду; у заплыва заполняется `age_group_code`. Режим `BY_TIME_ALL`: все вместе, `age_group_code = null` (места по группам считаются при ранжировании).

Опция `circleSeedTopHeats` (круговой посев трёх сильнейших заплывов, SW 3.1.1.3) — реализовать как флаг, по умолчанию `false`.

### 4.5 Валидатор (независимый от генератора; на вход — готовые заплывы)
ERROR: участник в двух заплывах одного вида; две заявки на одной дорожке; дорожка вне `1..lanes`; участник не допущен (повтор проверок 4.2); число участников в заплыве > дорожек; номера заплывов не сквозные с 1.
WARNING: заплыв < 3 участников (кроме случая `n < 3` во всём виде/группе); у спортсмена между двумя стартами < `minRestBetweenStartsSec` (по умолчанию 15 мин, по расписанию); опубликованный заплыв изменён при пересчёте; `NT` у > 50 % участников вида.
Выход: список `{code, severity, message, eventDisciplineId, heatNumber?, athleteId?, registrationId?}`; сохранить в `rule_execution_logs` (kind = VALIDATION).

### 4.6 Обязательные тесты (JUnit, без Spring-контекста)
1. `laneOrder(8) == [4,5,3,6,2,7,1,8]`, `laneOrder(6) == [3,4,2,5,1,6]`, `laneOrder(10) == [5,6,4,7,3,8,2,9,1,10]`.
2. `heatSizes` — все примеры из 4.4 плюс `n=0 → []`, `n=3,lanes=8 → [3]`, `n=1 → [1]`.
3. 17 участников, 8 дорожек, времена 30.00…46.00 с шагом 1 с: заплыв 3 (последний) содержит 8 самых быстрых, 30.00 на дорожке 4, 31.00 на 5, 32.00 на 3; заплыв 1 содержит трёх самых медленных.
4. NT в конце: 10 участников, двое NT → оба в заплыве 1 на дорожках после всех с временем.
5. `BY_AGE_GROUP`: две группы по 5 → два заплыва, номера 1 и 2, `age_group_code` заполнен.
6. Допуск: девушка в мужском виде → `GENDER_MISMATCH`; 2007 г.р. при группах 2008–2015 → `AGE_GROUP_MISMATCH`; дубль заявки → `DUPLICATE_ENTRY`.
7. Детерминированность: два запуска подряд дают одинаковый JSON.
8. Производительность: 200 заявок × 4 вида — суммарно < 5 с (и реально ожидается < 100 мс).
9. Валидатор: искусственно поменять местами дорожки так, чтобы два участника оказались на дорожке 4 → ERROR `LANE_CONFLICT`; поставить одного участника в два заплыва → ERROR `ATHLETE_IN_TWO_HEATS`.
10. Расписание: сессия с 10:00, вид 50 м (90 с/заплыв) с 3 заплывами, затем пауза 60 с и вид 100 м (150 с/заплыв) с 2 заплывами → старты 10:00:00, 10:01:30, 10:03:00, 10:05:30, 10:08:00.

### 4.7 Расписание
Длительность заплыва по дистанции (сек) по умолчанию: 25→60, 50→90, 100→150, 200→270, 400→480, 800→840, 1500→1500; иначе 180; переопределяется `event_disciplines.heat_duration_sec`. Внутри сессии виды по `order_in_session`, заплывы по номеру; между видами пауза сессии. `scheduled_at` записывается в `competition_units`. Порядковый номер заплыва в сессии (`sequence_in_session`) используется табло.

### 4.8 Ранжирование результатов
Статусы результата в коде (`ResultStatus`): `VALID, PENDING, CORRECTED, DISQUALIFIED, DID_NOT_START, DID_NOT_FINISH, EXHIBITION`. API и UI используют короткие коды и маппят их: `DNS → DID_NOT_START`, `DNF → DID_NOT_FINISH`, `DSQ → DISQUALIFIED`, `OK/VALID → VALID`. Новые значения в enum не добавлять.
По виду программы: сортировка `time_ms` по возрастанию среди статусов `VALID`; равные времена — одно место, следующий пропускает (1,1,3). `place_in_age_group` — то же внутри группы спортсмена (группа определяется по `age_groups_json` вида и году рождения/полу; при `BY_AGE_GROUP` — по `age_group_code` заплыва). DNS/DNF/DSQ — без места; при печати выводятся в конце с пометкой.

## 5. Контракты API (дополнение к существующему `/api/v1`)

Общие правила: JSON; ошибки в существующем формате `ApiErrorResponse{code,message,timestamp,violations}`; все эндпоинты организатора требуют роль `organizer|operator|platform_admin` **и** `EventAccessService.assertCanManage(eventId)`; публичные — без токена. Даты ISO-8601 с зоной. Время результата — `timeMs` (целое) и `display` (`мм:сс.сс`).

### 5.1 Организации (T01)
- `POST /api/v1/organization-registration-requests/{id}/approve` (admin) → создаёт `organization_members(owner)` для заявителя; `.../reject`.
- `POST /api/v1/organizations/{id}/members` (admin или owner) `{userId, memberRole}`; `GET …/members`.

### 5.2 Сессии (T03)
- `GET/POST /api/v1/events/{eventId}/sessions`, `PATCH/DELETE /api/v1/event-sessions/{id}`.
  Тело: `{name, orderNo, startsAt, breakBetweenEventsSec}`. Ответ GET дополнительно содержит `heatsCount` и `estimatedEndsAt` (время последнего заплыва сессии + его длительность) — во вкладке «Сессии» строка показывает «10:00 — расч. 13:42 · 46 заплывов».

### 5.3 Дисциплины (T03 — расширить существующие)
`POST /api/v1/events/{eventId}/disciplines` и `PATCH /api/v1/event-disciplines/{id}` принимают дополнительно:
```json
{"distanceM":50,"stroke":"FREE","gender":"F","seedingMode":"BY_AGE_GROUP","sessionId":"uuid","orderInSession":3,"heatDurationSec":null,
 "ageGroups":[{"code":"F-2014-2015","name":"Девушки 2014–2015","gender":"F","birthYearFrom":2014,"birthYearTo":2015}]}
```
`name` можно не передавать — формируется: «50 м вольный стиль, девушки». Добавить `DELETE /api/v1/event-disciplines/{id}` (только DRAFT-событие или без заявок).

Дополнения M06 (существующие поля и эндпоинты сохранены): у события и вида добавлен nullable `maxParticipants`, у вида — `limitsByAgeGroup` (код группы → положительный лимит). `null` означает отсутствие лимита; старый `participantLimit` продолжает действовать, эффективный лимит вида — минимум заданных лимитов. В REGISTRATION_OPEN/REGISTRATION_CLOSED PATCH вида допускает только `maxParticipants`, `limitsByAgeGroup`, `participantLimit`. Повышение/снятие лимита автоматически продвигает подходящие заявки из очереди.

`PATCH /api/v1/events/{id}` изменяет `maxParticipants`, `registrationOpenAt`, `registrationCloseAt` (явный `null` очищает поле). Жизненный цикл дополнен `REGISTRATION_CLOSED` и `ARCHIVED`: закрытие регистрации автоматически по дате или через `close-registration`; повторное `open-registration` требует будущей даты закрытия либо отсутствия срока. `POST /api/v1/events/{id}/archive` переводит COMPLETED в ARCHIVED: публичные страницы остаются доступны, изменения запрещены. Ошибки: `events.invalid_transition`, `events.invalid_dates`, `events.archived` (400).

### 5.4 Заявки (T03, T05)
- `POST /api/v1/registrations` — добавить `seedTimeMs` (или `seedTime: "00:32.15"`), ответ содержит оба.
- `PATCH /api/v1/registrations/{id}` (организатор): `{seedTimeMs, status}` для WITHDRAWN/ADMITTED.
- `POST /api/v1/registrations/{id}/withdraw` (участник — своя; организатор — любая своего события).
- Оплата: `POST /api/v1/payments/{id}/confirm` теперь переводит заявку в `payment_status = PAID` и `status = PAID` (если была CONFIRMED). `POST /api/v1/registrations/{id}/mark-paid` (operator) — то же без платёжной записи (демо).
- Публичная форма: `GET /api/v1/public/events/{slug}/registration-form` → `{disciplines:[{id,name,distanceM,stroke,gender,ageGroups,entryFee}], requiresSeedTime:true}`; `POST /api/v1/public/events/{slug}/registrations` (участник авторизован) `{profile:{lastName,firstName,middleName,birthDate,gender,club}, items:[{eventDisciplineId, seedTimeMs}]}` → создаёт/обновляет профиль пользователя и N заявок (одна заявка = одна дисциплина, как сейчас).
- Импорт: `GET /api/v1/events/{eventId}/registrations/import-template` → xlsx; `POST /api/v1/events/{eventId}/registrations/import` (multipart `file`) → 
```json
{"total":200,"created":196,"updated":2,"skipped":0,"errors":[{"row":17,"column":"Дата рождения","message":"неверный формат, ожидается ДД.ММ.ГГГГ"}],"createdProfiles":180}
```
Колонки шаблона (первая строка — заголовки, строго): `Фамилия | Имя | Отчество | Дата рождения (ДД.ММ.ГГГГ) | Пол (М/Ж) | Клуб/Город | Дисциплина (код) | Заявочное время (мм:сс.сс или пусто)`. Код дисциплины = `event_disciplines.code` (например `F-50-FREE`). Одна строка = одна заявка; несколько дисциплин — несколько строк. Статус импортированных заявок `CONFIRMED`, `source = IMPORT`, `payment_status = NOT_REQUIRED` (если взнос 0) иначе `PENDING`.

Дополнения M06: при заполнении лимита публичная заявка получает `WAITLISTED` и `waitlistPosition`; лимит события считает уникальных участников, лимиты вида/группы — заявки. Снятие, отклонение, возврат на исправление или повышение лимита продвигает первую подходящую заявку в SUBMITTED, очищает позицию и публикует события продвижения и подачи. Организатор может подтвердить WAITLISTED вне лимита; очередь не участвует в посеве. Импорт сохраняет контракт CONFIRMED выше.

Форма дополнена `registrationOpen`, `maxParticipants`, `participantsCount`; каждый вид — `maxParticipants`, `limitsByAgeGroup`, `participantsByAgeGroup`. Закрытая форма доступна для чтения, подача возвращает 400 `registrations.registration_closed`. Все поля добавлены, прежние сохранены.

### 5.6 Результаты (T08 backend-часть, минимальная)

### 5.7 Публичные представления и live (T06)
- `GET /api/v1/public/events/{slug}` — расширить: `{…, venue:{name,city,lanes,courseLength}, sessions:[…], disciplines:[{id,number,name,distanceM,stroke,gender,sessionId,orderInSession,unitsPublished:true}]}`.
- `GET /api/v1/public/events/{slug}/start-list` → все опубликованные заплывы сгруппированные по сессии → виду → заплыву с дорожками и `scheduledAt`.
- `GET /api/v1/public/events/{slug}/schedule` → список `{sessionName, disciplineName, heatNumber, sequenceInSession, scheduledAt, status}`.
- `GET /api/v1/public/events/{slug}/live` → `{currentUnit:{…}, next:[…3], updatedAt}`.
- `GET /api/v1/public/events/{slug}/results` → опубликованные результаты по видам и группам.
- `GET /api/v1/public/events/{slug}/athletes?q=Иванов` → `[{athleteKey, lastName, firstName, birthYear, club, swims:[{disciplineName, heatNumber, lane, scheduledAt, result:{display, status, place, placeInAgeGroup}|null}]}]`.
- `PUT /api/v1/events/{eventId}/live` `{currentUnitId}` (operator/judge/organizer) и `POST /api/v1/competition-units/{id}/start` / `/finish` — `/start` начинает заплыв; `/finish` из `IN_PROGRESS` → `FINISHED`, из `FINISHED` — идемпотентен (200, статус и время изменения заплыва сохраняются); в обоих случаях `/finish` переводит `current_unit_id` на следующий по расписанию.
- **Задержки в день старта (M07):** `POST /start` записывает `actual_started_at = now()` и переводит заплыв в `IN_PROGRESS`; повторный старт — 409 `results.unit_already_started`. Миграция `V034__unit_actual_times.sql` добавляет nullable `actual_started_at` и `actual_finished_at` (V027 уже занят). Первый переход в `FINISHED` через `/finish` или `/publication` записывает `actual_finished_at`; повторный `/finish` не меняет время согласно [ADR M10](decisions/2026-10-13-publikaciya-rezultatov.md). Снятие/повторная публикация сохраняют факт финиша; разрешённый после снятия публикации новый старт записывает новый факт старта и очищает факт финиша.
- `/live` дополнительно возвращает `delaySec = max(0, actual_started_at − scheduled_at)` текущего заплыва, 0 при отсутствии факта/плана/текущего заплыва. У `currentUnit` и `next` добавлены nullable `actualStartedAt`, `estimatedStartAt`; расчётное время = `scheduledAt + delaySec` (null при отсутствии плана). При `delaySec = 0` `estimatedStartAt` равен `scheduledAt`. Старт не меняет `scheduledAt`; отрицательного отставания нет. Это принятое уточнение M07 вместо прежнего автоматического пересчёта §5.7.
- `POST /api/v1/events/{eventId}/schedule/shift` `{fromUnitId,deltaSec}` (operator/organizer/platform_admin, доступ к событию) сдвигает оставшуюся часть сессии и, при перекрытии, следующие сессии того же дня площадки на величину перекрытия. Целое `deltaSec` от −86400 до 86400, кроме 0; сдвиг раньше начала сессии/конца предыдущего заплыва, перенос на другой день, начатые/завершённые/отменённые заплывы и отсутствие плана отклоняются с 400. Порядок, статусы и дорожки сохраняются. `/schedule/shift/preview` с тем же телом и доступом возвращает тот же расчёт без записи. Ответ `{units:[{id,previousScheduledAt,scheduledAt}],shiftedAt}` (preview: shiftedAt=null). `/schedule` сохраняет форму массива и добавляет nullable `scheduleShiftedAt` — время последней команды сдвига события. Аудит `SCHEDULE_SHIFT` и `ScheduleChangedEvent` выполняются в транзакции команды; `recalculate` сохранён. Подробности: [ADR M07](decisions/2026-10-13-start-delays.md).

### 5.8 Админка (M01)

Новые административные эндпоинты доступны только `platform_admin`, кроме управления членами организаций: там также разрешены локальные `owner/admin`. Запросы и ответы ниже — JSON; ошибки `identity.*` / `organizations.*` с русским сообщением.

| Эндпоинт | Контракт / изменение M01 |

Ответ `{items:[{id,email,firstName,lastName,status,roles:[code],createdAt}],page,size,total}`; `items[].roles` содержит только глобальные назначения. Scoped-роли остаются в деталях пользователя. |

Добавлены `memberships:[{organizationId,organizationName,memberRole}]`. PATCH принимает `{status:"ACTIVE"\|"BLOCKED"}` наряду с существующими полями профиля. |

Без поля — прежняя саморегистрация с `participant`. `POST /users` с `roles` без прав администратора → 403 `identity.access_denied`, пользователь не создаётся. `password` — 8–72 символа; остальные обязательные поля, включая `birthDate`, сохраняются. |

В JWT после `POST /api/v1/auth/login` и в `GET /api/v1/auth/me` поле `roles:[code]` содержит **только глобальные назначения** (`organization_id` и `event_id` равны null). Назначения с областью видны в деталях пользователя; глобальный редактор сохраняет их и не превращает в глобальные права. DTO пользователя возвращают статусы в верхнем регистре (`ACTIVE/BLOCKED/INACTIVE`), в БД сохраняются `active/blocked/inactive`.

Логин заблокированного: 403 `identity.user_blocked` только при верном пароле, при неверном — 401 `identity.invalid_credentials` без раскрытия статуса аккаунта. При запросе с прежним JWT заблокированный получает 401 `identity.user_blocked`. Статус и актуальные глобальные роли проверяются в БД на каждом запросе с JWT, **без кеша**: изменения действуют немедленно, цена — одно дополнительное SQL-чтение пользователя вместе с глобальными ролями на аутентифицированный запрос. Страница пользователей и `total` выбираются одним запросом с `count(*) over()`, профили и роли — ещё двумя пакетными запросами. Полный `GET /users?size=100` с JWT укладывается в четыре SQL-запроса; для пустой страницы за пределами списка `total` уточняется отдельным запросом без чтения профилей/ролей. Смена пароля не отзывает JWT; восстановление пароля, refresh-токены и аудит — M02.

Маршруты новой админки: `/admin/users`, `/admin/organizations`, `/admin/organizations/:id`, `/admin/registration-requests`, `/admin/sports`. Прежняя форма рассмотрения **заявки спортсмена** доступна организатору по `/organizer/registrations/review` вместо `/admin/registrations/review`; старый маршрут остаётся административным алиасом только для `platform_admin`.

### 5.9 Аутентификация (M02)

Все POST принимают JSON; пути ниже включают общий префикс `/api/v1`.

| Метод | Путь | Тело | Доступ | Успешный код |
| --- | --- | --- | --- | --- |
| POST | `/api/v1/auth/change-password` | `{currentPassword,newPassword}` | Bearer access JWT | 204 |
| POST | `/api/v1/auth/password-reset/request` | `{email}` | Без Bearer; 202 для существующего, неизвестного и заблокированного email | 202 |
| POST | `/api/v1/auth/password-reset/confirm` | `{token,newPassword}` | Владение reset-токеном, без Bearer | 204 |
| POST | `/api/v1/auth/refresh` | `{refreshToken}` | Владение refresh-токеном, без Bearer | 200, новая пара токенов |
| POST | `/api/v1/auth/logout` | `{refreshToken}` | Владение refresh-токеном, без Bearer; повторный вызов безопасен | 204 |
| POST | `/api/v1/auth/logout-all` | Без тела | Bearer access JWT | 204 |

Ответ существующего `POST /api/v1/auth/login` дополнен полем `refreshToken`:
`{accessToken,tokenType:"Bearer",expiresIn,refreshToken}`. `expiresIn` — секунды из
`app.jwt.access-ttl`, по умолчанию `PT2H` (прежний срок для демо); после обновления
фронта можно включить `PT1H` через `APP_JWT_ACCESS_TTL`. Refresh возвращает тот же
формат ответа. Issuer и формат access JWT сохраняются.

| Код ошибки | HTTP | Значение |
| --- | --- | --- |
| `identity.password_weak` | 400 | Новый пароль не соответствует политике |
| `identity.password_mismatch` | 400 | Неверный текущий пароль |
| `identity.reset_token_invalid` | 400 | Неизвестный, истёкший, использованный или заменённый reset-токен |
| `identity.refresh_token_invalid` | 401 | Неизвестный, истёкший или отозванный refresh-токен |
| `identity.too_many_attempts` | 429 + `Retry-After` | Вход временно ограничен; заголовок содержит секунды ожидания |
| `identity.user_blocked` | 403 на refresh | Пользователь заблокирован |

Новый пароль при самостоятельной смене и восстановлении: минимум 8 символов,
буквы и цифры, не более 72 байт UTF-8 (bcrypt). Непереданный/пустой новый пароль
отклоняется валидацией DTO с сообщением «Укажите новый пароль» (400 `validation_error`).
Текущий пароль проверяется при смене. Сообщения ошибок и письмо — на русском.

Reset: 32 случайных байта, срок 1 час, в БД только SHA-256 хеш; одноразовое
подтверждение, новый запрос заменяет прежнюю ссылку. Ссылка письма:
`${APP_PUBLIC_URL}/reset-password?token=…`; до notifications/SMTP применяется
временный `LoggingMailSender` (INFO, пометка DEV).

Refresh: opaque-токен из 32 случайных байт, в БД только SHA-256 хеш, срок 30 дней.
При каждом refresh старый токен отзывается, выдаётся новая пара. Повторное
предъявление отозванного refresh возвращает 401 и отзывает все refresh пользователя,
включая новую пару после ротации. Заблокированный пользователь не получает новую пару.

Logout отзывает текущий refresh; logout-all отзывает refresh и access всех устройств.
Смена/восстановление пароля отзывают access, refresh и reset-токены всех устройств;
повторное использование refresh и блокировка пользователя отзывают access и refresh.
При каждом запросе JWT сравнивается с `users.tokens_valid_after` в том же SQL,
который читает роли и членства. Граница отзыва продвигается по целым секундам;
новые токены получают `iat` не раньше этой границы, включая повторный отзыв в ту же секунду.

Существующий административный `PATCH /api/v1/users/{id}/password` теперь делает
тот же отзыв (контракт M01 по телу и успешному коду 204 сохраняется). После
самостоятельной смены фронт завершает сессию и предлагает войти с новым паролем.

По умолчанию 5 неудачных входов за скользящие 15 минут ограничивают пару
нормализованный email + IP; отдельный порог IP — 30 неудач независимо от email.
Превышение жёсткого порога возвращает 429 с `Retry-After` и русским сообщением.
Настройки: `APP_AUTH_LOGIN_MAX_FAILURES` (5), `APP_AUTH_LOGIN_MAX_FAILURES_PER_IP`
(30), `APP_AUTH_LOGIN_WINDOW` (`PT15M`). Успех сбрасывает только счётчик пары;
общие счётчики IP и email сохраняются. После 20 неудач по email за это окно
ответ задерживается на 2 секунды; доступ с верными учётными данными сохраняется.
Лимиты входа не влияют на публичное live и импорт.

Регистрация (`POST /auth/register` и `/users`) использует общие счётчики по
нормализованному email и IP: 3 запроса на email и 20 на IP за час. На `/users`
освобождён только PLATFORM_ADMIN. Попытка учитывается после bean-валидации и
проверки политики пароля. Превышение возвращает 429 и `Retry-After`.
Для `POST /auth/password-reset/request` действуют отдельные счётчики с теми же
значениями по умолчанию; превышение сохраняет пустой 202 без отправки письма.

| Настройка | Переменная окружения | По умолчанию |
|---|---|---|
| `app.auth.registration.max-per-email` | `APP_AUTH_REGISTRATION_MAX_PER_EMAIL` | 3 |
| `app.auth.registration.max-per-ip` | `APP_AUTH_REGISTRATION_MAX_PER_IP` | 20 |
| `app.auth.registration.window` | `APP_AUTH_REGISTRATION_WINDOW` | PT1H |
| `app.auth.password-reset.max-per-email` | `APP_AUTH_PASSWORD_RESET_MAX_PER_EMAIL` | 3 |
| `app.auth.password-reset.max-per-ip` | `APP_AUTH_PASSWORD_RESET_MAX_PER_IP` | 20 |
| `app.auth.password-reset.window` | `APP_AUTH_PASSWORD_RESET_WINDOW` | PT1H |

Пороги должны быть не меньше 1, окна — положительными ISO-8601 Duration.
Настройки проверяются при старте; production compose передаёт их контейнеру API.

## 6. Интерфейс (web-кабинет и публичные страницы)

Общие требования: русский язык; экраны организатора — десктоп ≥ 1280 px, но не ломаются на 1024; публичные страницы — mobile-first (375 px); существующая дизайн-система (`globals.css`: Inter, primary `#0b5b7b`, токены радиусов/теней) сохраняется; без новых UI-китов, чтобы не растить сборку (допустимо добавить `@tanstack/react-query` для загрузки данных и `qrcode.react` для QR).

### 6.1 Кабинет организатора — страница события `/organizer/events/:id`
Вкладки: **Обзор** (статус, кнопки «Опубликовать», «Открыть регистрацию», «Закрыть регистрацию», публичная ссылка + QR), **Сессии и виды программы** (таблица сессий; таблица видов с формой: дистанция, стиль, пол, возрастные группы [добавить из пресета «детские 2 года» или вручную], режим посева, сессия, порядок; действия: изменить, удалить), **Заявки** (таблица с фильтрами статус/вид/поиск; колонка «Допуск»: ✓ или причина из §4.2 (`GENDER_MISMATCH`, `AGE_GROUP_MISMATCH`, `DUPLICATE_ENTRY`) по последнему запуску посева, фильтр «Не допущены», подсказка с русским текстом; действия: подтвердить, вернуть на исправление, отклонить, отметить оплату, снять; кнопка «Импорт из Excel» → модальное окно: скачать шаблон, выбрать файл, отчёт по строкам), **Заплывы** (кнопка «Сформировать заплывы» по событию; по каждому виду — карточки заплывов: № заплыва, время старта, таблица дорожек; ручная смена дорожки селектом; панель валидатора с нарушениями; кнопки «Пересчитать расписание», «Опубликовать стартовый протокол», «Печать»), **Результаты** (список заплывов со статусами; переход в панель ввода; «Опубликовать результаты вида»; «Печать итогового протокола»).

### 6.2 Панель ввода результатов `/operator/competition-units/:unitId` (существует — доработать)
Поле времени с маской `мм:сс.сс`, Enter переводит на следующую дорожку, статус-кнопки DNS/DNF/DSQ, «Сохранить и пересчитать», «Опубликовать результаты», «Сохранить исправление» после публикации (operator/organizer/platform_admin), «Финиш», «Следующий заплыв» (и автоматическое `PUT /live`). Ошибки ввода — рядом с полем.

### 6.3 Публичные страницы
- `/e/:slug` — карточка соревнования: даты, площадка, сессии, ссылки на стартовый протокол, расписание, live, результаты, «Подать заявку» (если регистрация открыта).
- `/e/:slug/start-list` — печатная форма (§6.4).
- `/e/:slug/schedule` — лента заплывов по времени.
- `/e/:slug/live` — «Сейчас: вид № / заплыв №» крупно, следующие 3, поиск «Найти себя»; автообновление 15 с.
- `/e/:slug/results` — результаты по видам и группам, печатная форма.
- `/e/:slug/register` — форма заявки (телефон): ФИО, дата рождения, пол, клуб, выбор видов (чекбоксы с фильтром по полу/возрасту), заявочное время на каждый вид, согласие на обработку ПДн (текст-заглушка на демо), отправка; требует входа (кнопка «Войти/Зарегистрироваться» ведёт на существующие страницы).

### 6.4 Печать (`@media print`)
A4 портрет, поля 15 мм, шрифт 10–11 pt, шапка на каждой странице (название соревнования, дата, площадка), `page-break-inside: avoid` для заплыва, скрыть навигацию и кнопки. Стартовый протокол: по видам — заголовок «Вид № 3. 50 м вольный стиль, девушки» → для каждого заплыва таблица `Дорожка | Фамилия Имя | Год | Клуб | Заявочное время`, строка «Заплыв 2 — 10:03» над таблицей. Итоговый протокол: по видам и группам — `Место | Фамилия Имя | Год | Клуб | Результат`, затем блок DNS/DNF/DSQ.

**Серверные PDF (M03).** Отдельная кнопка «Скачать PDF» на страницах заплывов и результатов организатора, а также на публичных `/e/{slug}/start-list` и `/results`, дополняет существующую браузерную печать без изменения `@media print`.

| Метод | Путь | Права |
| --- | --- | --- |
| GET | `/api/v1/events/{eventId}/documents/start-list.pdf` | organizer/operator/platform_admin + `EventAccessService.assertCanManage(eventId, principal)` |
| GET | `/api/v1/events/{eventId}/documents/results.pdf` | organizer/operator/platform_admin + `EventAccessService.assertCanManage(eventId, principal)` |
| GET | `/api/v1/public/events/{slug}/start-list.pdf` | Без входа; публичное событие, виды PUBLISHED и заплывы PUBLISHED/IN_PROGRESS/FINISHED/COMPLETED |
| GET | `/api/v1/public/events/{slug}/results.pdf` | Без входа; те же правила публикации, результаты только FINISHED/COMPLETED, PENDING исключён |

Публичный PDF кешируется на сервере 60 с по slug и типу протокола: после публикации или исправления может отставать до 60 с. Видимость события перепроверяется при каждом скачивании, в том числе при попадании в кеш. Организаторский PDF генерируется заново. Ответ: `Content-Type: application/pdf`, `Content-Disposition: attachment; filename*=UTF-8''…`, `Content-Length`, `Cache-Control: no-store`; имя файла — тип протокола, publicSlug (при null — eventId) и дата старта `yyyy-MM-dd` в часовом поясе площадки. PDF исключены из PWA-кеша. Одновременно рендерятся максимум два документа; если разрешение не получено за 10 с, ответ 503 `documents.busy` с русским сообщением о повторной попытке.

### 6.5 PWA
`vite-plugin-pwa`: manifest (name «Flounder», short_name «Flounder», theme `#0b5b7b`, иконки 192/512), service worker «network-first» для API и «cache-first» для статики; офлайн-заглушка «Нет связи». Проверка: Chrome на Android предлагает «Установить приложение»; Lighthouse PWA — installable.

## 7. Набор демо-данных M (T10)
Готово: `docs/scripts/demo/out/set-M.xlsx`, `set-M-with-errors.xlsx`, `set-M.json`, генератор `docs/scripts/demo/generate_set_m.py` (seed 2026). Описание ниже — спецификация, по которой они сделаны.
200 заявок, 4 вида программы (50 в/с Ю/Д, 100 в/с Ю/Д), 2 сессии, 8 дорожек, возрастные группы 2014–2015, 2012–2013, 2010–2011; у 90 % заявок заявочное время (нормальное распределение вокруг реалистичных средних по возрасту), 10 % NT; 5 % клубов повторяются; 3 намеренно ошибочных строки в Excel для демонстрации отчёта импорта (неверная дата, неизвестный код дисциплины, пустая фамилия). Генератор — скрипт `scripts/demo/generate-set-m.(py|ts)` с фиксированным seed; выход — `set-M.xlsx` и `set-M.json`.

## 8. Критерии готовности демо (чек-лист приёмки Claude 14.10 вечером)
1. `mvn test` и `npm run build` зелёные в CI на `main`.
2. Сквозной прогон US-1…US-7 на демо-стенде по скрипту `docs/demo-script.md` — без ошибок 500 и без ручных правок в БД.
3. Посев набора M: 0 ERROR валидатора; время ≤ 5 с (в логе `rule_execution_logs.duration_ms`).
4. Печать стартового и итогового протоколов — PDF открыт, страницы не обрезаны.
5. Публичные страницы на телефоне (Android Chrome, iOS Safari) читаемы; PWA устанавливается.
6. Секретов в git нет; `.env.example` актуален; README описывает запуск за 5 команд.
7. Резервная копия БД демо-стенда снята (`pg_dump`) и восстановление проверено.
8. Сценарий демо содержит ответы словами на вопросы: документы/мандатная комиссия (ноябрь), онлайн-оплата (декабрь), очки/разряды/электронный хронометраж (этапы 3–4).
