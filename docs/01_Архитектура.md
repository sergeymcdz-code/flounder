# Flounder — целевая архитектура и её отображение на текущий код

Версия 1.0 · 12.10.2026

## 1. Принципы

1. **Модульный монолит** (Spring Modulith) с явными границами модулей и событиями между ними; выделение сервисов — только при появлении оснований (нагрузка, отдельная команда). Это подтверждённая гипотеза №1 проекта.
2. **Мультиспортивное ядро, плавание как первый преднастроенный сценарий.** Нейтральные сущности: `competition_unit` (заплыв/забег/волна), `result` (время/очки/место). Спортивная специфика — в конфигурации дисциплины и регламента, не в именах таблиц.
3. **Один API для всех клиентов**: web-кабинет организатора, публичные страницы, PWA, в будущем Expo-приложение и интеграции (хронометраж, федерации) — всё через `/api/v1`, описанный OpenAPI.
4. **Детерминированные расчёты**: посев, расписание и места считаются чистыми функциями от входных данных; корректность проверяет независимый валидатор; каждый расчёт логируется (`rule_execution_logs`).
5. **Данные граждан РФ — в РФ** (152-ФЗ), аудит чувствительных действий, роли на уровне объектов (организатор видит только свои события).

## 2. Логическая архитектура

```
┌────────────────────────── Клиенты ──────────────────────────┐
│ Web-кабинет организатора/секретаря/судьи (React, ноутбук)   │

│ (этап 2) Expo-приложение · интеграции хронометража · экспорт │
└──────────────────────────────┬──────────────────────────────┘
                               │ HTTPS · REST /api/v1 · SSE (этап 2)
┌──────────────────────────────▼──────────────────────────────┐
│ Spring Boot 3 · Spring Modulith — модульный монолит          │
│ identity · organizations · sports · regulations · events ·   │
│ competition (дисциплины) · registrations · payments ·        │
│ scheduling (посев/расписание/валидатор — НОВЫЙ) · results ·  │
│ publication (публичные представления, live — НОВЫЙ) ·        │
│ imports (Excel — НОВЫЙ) · notifications (этап 2) ·           │
│ documents (этап 2) · analytics (этап 2) · audit               │
└──────────────┬───────────────────────────────┬──────────────┘
               │ JPA/Flyway                     │ S3 API (этап 2)
```

Инфраструктура демо и первых 50 соревнований: один VPS (2 vCPU / 4 ГБ) с Docker Compose: `caddy` (HTTPS, статика фронта) → `api` (Spring Boot) → `postgres`. Redis и Kafka из compose убираются до появления реальной потребности.

## 3. Модули и ответственность

| Модуль | Есть в коде | Отвечает за | Изменения для демо |
|---|---|---|---|
| identity | да | пользователи, профили, роли, JWT | seed-админ с рабочим хешем; роль `judge` в seed; профили без пользователя (импортированные спортсмены) |
| organizations | да | организации, площадки, членство, заявки на регистрацию организации | создание членства при одобрении заявки; `POST /organizations/{id}/members` |
| sports / regulations | да | справочник видов спорта, шаблоны дисциплин, версии регламентов (`rules_json`) | без изменений |
| events | да | событие, статусы, публичный slug | сессии события (`event_sessions`), ownership-проверки, slug для кириллицы (транслитерация) |
| competition | да | дисциплины события | типизированные поля плавания: дистанция, стиль, пол, возрастные группы, режим посева, сессия, порядок |
| registrations | да | заявки, модерация, снимок участника | `seed_time_ms`, `source` (FORM/IMPORT), `payment_status`, статусы PAID/ADMITTED/WITHDRAWN |
| payments | да | ручная оплата, ЮKassa-webhook | подтверждение оплаты → заявка PAID; подпись webhook (этап 2) |
| **scheduling** | нет | посев заплывов по SW 3, расписание сессий, валидатор, пересчёт | новый модуль, см. ТЗ демо §4 |
| results | да | стартовые единицы, участники в них, результаты, места, публикация | `time_ms`, `place_in_age_group`, ничьи, печатные протоколы |
| **publication** | частично | публичные представления: каталог, стартовый протокол, расписание, live-состояние, результаты | новые эндпоинты, `event_live_state` |
| **imports** | нет | импорт заявок из Excel/CSV с отчётом по строкам | новый модуль (Apache POI) |
| audit | частично | журнал действий | `audit_logs` на публикацию/изменение результатов (этап 2 — полный) |

## 4. Модель данных (ключевые таблицы после демо-миграций)

Существующие: `users, profiles, roles, user_role_assignments, organizations, organization_members, organization_registration_requests, venues, sports, discipline_templates, regulation_templates, regulation_versions, category_rules, events, event_disciplines, registrations, payments, payment_webhook_events, competition_units, competition_unit_entries, results, event_publication`.

Новые/изменённые (миграции V020–V026, детально в ТЗ демо §3):
- `event_sessions` — сессии (части) соревнования: дата/время старта, пауза между видами.
- `event_disciplines` + `distance_m, stroke, gender, age_groups_json, seeding_mode, session_id, order_in_session, heat_duration_sec`.
- `profiles.user_id` → nullable (спортсмен без аккаунта), `+ birth_year` вычисляемое, `external_key` для дедупликации импорта.
- `registrations` + `seed_time_ms, source, payment_status`.
- `competition_units` + `age_group_code, heat_duration_sec`; статусы приведены к enum `DRAFT, PUBLISHED, IN_PROGRESS, FINISHED, CANCELLED` с CHECK.
- `competition_unit_entries` + `seed_time_ms`.
- `results` + `time_ms, place_in_age_group`.
- `event_live_state (event_id pk, current_unit_id, updated_at)`.
- `rule_execution_logs` — уже спроектирована, используется модулем scheduling.

## 5. Поток данных «заявки → протокол → результаты»

1. Организатор создаёт событие (статус DRAFT), сессии, дисциплины с параметрами плавания → `PUBLISHED` → `REGISTRATION_OPEN`.
2. Заявки приходят из публичной формы (участник/родитель, с аккаунтом) и из импорта Excel (профили без аккаунта). Модерация → `CONFIRMED`; оплата (отметка) → `PAID`; допуск → `ADMITTED`.
3. `POST /event-disciplines/{id}/generate-competition-units`: модуль scheduling берёт заявки со статусом ≥ CONFIRMED, проверяет допуск, сортирует по заявочному времени, формирует заплывы и дорожки, записывает `competition_units` + `entries` (статус DRAFT), лог расчёта. Валидатор проверяет результат и возвращает список нарушений.
4. `POST /events/{id}/schedule/recalculate` расставляет `scheduled_at` по сессиям.
5. Публикация стартового протокола (`competition_units.status = PUBLISHED`) → публичные страницы и печатная форма.
6. Секретарь вводит результаты по заплыву; `recalculate` считает места в абсолюте и по возрастным группам; публикация результатов → публичная страница. `event_live_state.current_unit_id` двигает табло «сейчас идёт заплыв №N».
7. Изменение заявки после публикации → пересчёт с сохранением опубликованных заплывов без изменений, если возможно, иначе предупреждение валидатора.

## 6. Безопасность и соответствие

- JWT (HS256, TTL 2 ч) + refresh-токены (этап 2); пароли BCrypt; роли `platform_admin, organizer, operator, judge, participant`.
- Object-level авторизация: `EventAccessService.assertCanManage(eventId, user)` — членство в организации события или `platform_admin`; применяется во всех контроллерах событий, дисциплин, заявок, заплывов, результатов.
- Секреты — только через переменные окружения; `.env` в `.gitignore`; ротация JWT-секрета после удаления из истории git.
- 152-ФЗ (этап 2): согласие на обработку ПДн в форме регистрации, согласие родителя для детей, спецкатегория (медсправки) — отдельное согласие и шифрование файлов; сервер в РФ; политика конфиденциальности; уведомление Роскомнадзора как оператора ПДн.
- Аудит: публикация/изменение результатов, изменение статусов заявок, импорт — в `audit_logs` (кто, что, до/после).

## 7. Нефункциональные требования (демо → 50 соревнований)

| Показатель | Демо | 50 соревнований |
|---|---|---|
| Участников на событие | 200 | 1 000 |
| Время посева дисциплины (200 заявок) | ≤ 5 с | ≤ 5 с |
| Отклик API (p95) | ≤ 2 с | ≤ 1 с |
| Публикация результата → видно на телефоне | ≤ 30 с (обновление по таймеру) | ≤ 5 с (SSE) |
| Доступность в день старта | best effort | 99,5 % |
| Резервные копии БД | вручную перед демо | ежедневно, хранение 30 дней |
| Одновременных зрителей табло | 50 | 1 000 |

## 8. Эволюция после демо

- Выделение `scheduling` в отдельный сервис не планируется до 500+ стартов/год; при росте нагрузки на табло — кэш публичных представлений (Redis) и SSE.
- Мобильное приложение: PWA → Expo (React Native) с тем же API; push через Firebase/RuStore.
- Интеграции: импорт/экспорт форматов Lenex (стандарт обмена в плавании, используется Splash/Hy-Tek) — открывает путь к электронному хронометражу и L-Sport.
