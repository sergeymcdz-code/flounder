# M08 — аналитика события и организации

Панель доступна организатору и администратору платформы. Аналитика события и XLSX проверяют `EventAccessService.assertCanManage` перед каждым чтением кеша. Аналитика организации дополнительно требует `organization_members.member_role = owner | admin`; администратор платформы имеет доступ ко всем организациям. Роль `organizer` внутри организации сама по себе не даёт доступ к аналитике организации. Оператор и судья не имеют доступа (уточнение заказчика для M08 важнее общей матрицы демо §5).

## API и интерфейс

| Метод | Путь | Результат |
|---|---|---|
| GET | `/api/v1/events/{eventId}/analytics` | Метрики события |
| GET | `/api/v1/events/{eventId}/analytics/export.xlsx` | Те же данные, 12 листов XLSX |
| GET | `/api/v1/organizations/{id}/analytics` | Метрики организации |
| GET | `/api/v1/organizations/{id}/analytics/export.xlsx` | Те же данные, 3 листа XLSX |

Все четыре маршрута включены в `qa04-endpoints.tsv`. Интерфейс: вкладка «Аналитика» в `/organizer/events/:eventId`; «Аналитика организаций» в навигации кабинета → `/organizer/organizations/:orgId/analytics`. Диаграмма SVG без новой зависимости; точные дневные значения доступны в раскрываемой таблице. Доступны загрузка XLSX, повтор запроса после ошибки и пустые состояния. При 401 выполняется выход и переход на страницу входа; 403 показывает отсутствие доступа.

## Определения и источники

| Метрика | Источник и определение |
|---|---|
| Всего заявок | `count(*)` в `registrations`, включая все текущие статусы |
| Участники события | `count(distinct participant_profile_id)` по всем заявкам события |
| Статусы | SQL `group by registrations.status` |
| Заявки по дням | `coalesce(submitted_at, created_at)` в часовом поясе `venues.timezone` (fallback UTC); нулевые дни включены с открытия регистрации до текущего дня/закрытия. Если данные находятся вне этого диапазона, диапазон расширяется, чтобы суммы сходились |
| Подано | Все заявки, кроме DRAFT; это текущий срез, а не история переходов |
| Подтверждено | Текущие статусы CONFIRMED, PAID, ADMITTED |
| Оплачено | Подтверждённые заявки с `payment_status = PAID | NOT_REQUIRED`; бесплатные заявки входят в этот этап |
| Допущено | Подмножество оплаченных заявок с действующим `competition_unit_entries.entry_status = ASSIGNED` в заплыве своей дисциплины, кроме CANCELLED. Снятая дорожка не считается допуском. Неконсистентные назначения неоплаченных/неподтверждённых заявок не увеличивают этап |
| По видам | Независимые SQL-агрегаты заявок, уникальных профилей и заплывов по `event_disciplines.id`. Отменённые заплывы исключены; виды без заявок включены |
| По возрастным группам | Первая подходящая группа в порядке `event_disciplines.age_groups_json`, год рождения/пол из текущего `profiles`. Границы включительны; null означает открытую границу. Группы X подходят любому полу; без совпадения — «Без группы». Группы с одинаковым кодом разных видов объединяются |
| По клубам | Текущий `profiles.club_name`, trim; пустое значение — «Без клуба». Топ-20 по числу заявок, стабильный порядок по имени при равенстве; остальные агрегируются в «Прочие» |
| По полу | Текущий `profiles.gender`, нормализованный по M/m/male, F/f/female, X/x/other; неизвестное значение явно выделяется |
| Длительность сессии | Сумма длительностей неотменённых заплывов плюс паузы **между непустыми видами**, как в `ScheduleBuilder`. Приоритет: `competition_units.heat_duration_sec`, затем `event_disciplines.heat_duration_sec`, затем таблица дистанций из ТЗ демо §4.7 |
| Расчётное окончание | Последний `scheduled_at + duration`; если расписания ещё нет — `starts_at + расчётная длительность`; для пустой сессии null |
| Фактическая задержка | `delaySec = null`, TODO M07. Плановое расписание не заменяет факт |
| Опубликовано заплывов | `competition_units.status in (FINISHED, COMPLETED)` в дисциплинах PUBLISHED — семантика M10. PUBLISHED у заплыва означает только стартовый протокол |
| Задержка публикации | Пока null, `latencySamples=0`, `latencySource=UNAVAILABLE_M07`. В текущем main нет ни фактического финиша, ни неизменяемой отметки публикации. `rule_execution_logs.duration_ms` — длительность расчёта, не интервал финиш → публикация; `updated_at` изменяется при правках и также непригоден |
| Медиана/p95 при наличии источника | SQL `percentile_cont(0.5/0.95)` по секундам между двумя неизменяемыми отметками. Опциональное чтение через `to_jsonb(competition_units)` переносит отсутствие колонок без миграции. Предварительные имена `actual_finished_at` / `results_published_at` требуют сверки с будущим производителем M07; это **не** реализованный контракт M07. Отсутствующие и отрицательные интервалы исключены. Синтетический PostgreSQL-тест проверяет 20 интервалов 10…200 секунд: медиана 105, p95 190,5 |
| Исправленные результаты | Число текущих `results.status = CORRECTED`. Это число исправленных записей, не количество исторических правок одной записи |
| Валидатор | Последний `rule_execution_logs.kind=VALIDATION` по `executed_at, id`; число ERROR/WARNING в `violations_json`. Показывает один последний прогон, не сумму прогонов всех видов |
| Импорты | `available=false`, пустой список и причина. `ExcelImportService` пишет статистику только в текстовый лог, таблицы истории импортов нет |
| События организации | Все события по `events.organization_id`, включая пустые; SQL-группировка по статусам |
| Участия организации | Сумма уникальных профилей внутри каждого события; несколько дистанций одного спортсмена в одном событии не увеличивают число участий |
| Уникальные/повторные | Уникальные профили по событиям организации; повторный — профиль минимум в двух разных событиях. DRAFT, REJECTED и WITHDRAWN заявки исключены |
| Средний размер события | Среднее числа уникальных профилей каждого события, включая события без участников |
| Выручка | Сумма `payments.amount` только при `payments.status=SUCCEEDED`, раздельно по валютам; возвраты и оплаты без записи платежа не входят. Статус PAID принадлежит заявке, не таблице payments |

Разбивки события показывают текущие данные профиля и все заявки; суммы заявок сходятся между статусами, днями, видами, группами, клубами и полом. Уникальные участники разбивок не суммируются между видами/группами: один профиль может участвовать в нескольких видах.

## Архитектура и ограничения

Новый модуль `com.acme.sportplatform.analytics` читает только native SQL-агрегаты через `EntityManager`, как publication; списки исходных заявок/профилей/результатов в память не загружаются. Межмодульные Java-вызовы используют публичные `EventAccessService` и `OrganizationLookup`. Транзакции read-only с repeatable read обеспечивают согласованный снимок нескольких агрегатов; кеш Caffeine по eventId имеет TTL 60 секунд и максимум 500 записей. Проверка доступа находится до кеша; XLSX события использует тот же снимок. Организация читается без кеша.

Миграций и изменений чужих таблиц нет. Test-only DDL в откатываемой транзакции моделирует будущие отметки для проверки p95 и не изменяет production-схему. В рамках read-only M08 не добавлены производители истории импорта, фактических задержек, таймеров ручных операций и истории правок протокола; без них измерять сокращение ручных операций ≥50% пока нельзя. Публикация за ≤7 минут не объявляется достигнутой при отсутствии отметок.

## Ручная проверка

1. Запустить backend с PostgreSQL и frontend по AGENTS.md. Войти организатором, открыть своё событие с импортированным набором M.
2. Перейти во вкладку «Аналитика». Сверить общее число заявок с разделом «Заявки»; сумма по видам/клубам/полу/группам и по дням должна совпадать. Числа в воронке не возрастают слева направо/сверху вниз.
3. Проверить таблицу под графиком, часовой пояс площадки, загрузку сессий, последний прогон валидатора. FINISHED/COMPLETED учитываются как опубликованные результаты; PUBLISHED не учитывается.
4. Нажать «Скачать XLSX», открыть книгу: 12 листов, числа совпадают с панелью. Недоступные задержки пустые, лист «Импорты» содержит причину отсутствия данных.
5. Изменить заявку в другом разделе, подождать истечения 60 секунд и нажать «Обновить»; проверить новый снимок. Выход/отзыв доступа не даёт читать ранее закешированные данные.
6. Перейти в «Аналитика организаций», открыть организацию своего owner/admin-членства. Проверить события по статусам, участия/уникальных/повторных, средний размер и выручку по валютам; XLSX имеет 3 листа.
7. Войти чужим организатором и запросить JSON/XLSX события и организации: 403. Участник, оператор и судья также получают 403; без токена — 401. Проверить пустое событие/организацию и ширину 360 px.

По условиям этой задачи PR оставлен без слияния и автослияния. При финальном fetch в main появился ADR `docs/decisions/2026-10-13-demo-19-oktyabrya.md`: дата демо перенесена с 15.10 на 19.10.2026, график слияний пересмотрен. Решение о слиянии M08 остаётся за владельцем проекта.
