# S05. Оплата заявок: взносы, статусы, ручное подтверждение, реквизиты, сводка по клубам

Прочитай `AGENTS.md`, `docs/03_ТЗ_MVP_50_соревнований.md` §3.3 (оплата, «вариант А»: деньги принимает организатор, платформа только учитывает), §3.8 (воронка «оплачено»), `docs/02_ТЗ_демо.md` §5.4 (текущие `mark-paid`, `payment_status`). Ветка `feat/S05-registration-payments` от актуального `origin/main`. Модули `payments`, `registrations`, `notifications` (один новый шаблон). Один PR. Миграция **V035** (номер зарезервирован за этой задачей, не менять). Приоритет: высокий. **Слияние после демо 19.10** (меняется шаг демо «отметить оплату»).

## Зачем
До онлайн-оплаты (этап 3, после юрлица) организатор принимает взносы сам: переводом, наличными на мандатной комиссии, по счёту от клуба. Платформа должна (1) показать участнику/тренеру сколько и куда платить, (2) дать секретарю отметить оплату с деталями и массово по клубу, (3) показать долги по клубам и воронку «оплачено». Сейчас есть только `POST /registrations/{id}/mark-paid` без суммы, способа и аудита, и расчёт суммы только по `entry_fee` вида.

## Текущее состояние кода (отправная точка)
- `registrations.payment_status` ∈ `NOT_REQUIRED|PENDING|PAID|REFUNDED` (V024), статус заявки `PAID` после `mark-paid` (`registrations/application/RegistrationPaymentService.markPaid` — только из `CONFIRMED`).
- `event_disciplines.entry_fee_amount/currency` (V012). Таблица `payments` (V013) — для провайдера (ЮKassa, manual), 1 платёж на заявку, `PaymentReviewController`/`PaymentsController`.
- Фронт: `features/payments/OperatorPaymentsPage.tsx`, `OperatorRegistrationPage.tsx`, `PaymentPage.tsx` (участник), `features/organizer/OrganizerEntriesPage.tsx` (список заявок с действиями).

## Что сделать

### 1. Миграция `V035__registration_payment_details.sql` (только добавление)
```sql
alter table registrations
  add column fee_amount numeric(12,2),            -- сумма к оплате, зафиксированная при подтверждении заявки
  add column fee_currency varchar(3),
  add column paid_amount numeric(12,2),
  add column paid_at timestamptz,
  add column paid_by_user_id uuid references users(id),
  add column payment_method varchar(16) check (payment_method in ('CASH','TRANSFER','ONLINE','CLUB_INVOICE','OTHER')),
  add column payment_comment varchar(500),
  add column payment_reference varchar(128);      -- номер платёжки/чека, вводится вручную
alter table registrations drop constraint if exists registrations_payment_status_chk;  -- имя уточнить по V024; если CHECK безымянный — найти по pg_constraint в тесте и указать в PR
alter table registrations add constraint registrations_payment_status_chk
  check (payment_status in ('NOT_REQUIRED','PENDING','PAID','REFUNDED','WAIVED'));
create index idx_registrations_payment_status on registrations(payment_status);

create table registration_payment_log (
  id uuid primary key,
  registration_id uuid not null references registrations(id) on delete cascade,
  action varchar(16) not null check (action in ('MARK_PAID','WAIVE','REFUND','RESET')),
  amount numeric(12,2), currency varchar(3), method varchar(16), reference varchar(128), comment varchar(500),
  performed_by uuid not null references users(id),
  performed_at timestamptz not null default now()
);
create index idx_registration_payment_log_registration on registration_payment_log(registration_id);
```
Единственное допустимое изменение существующего CHECK — расширение списка значений (как в V033). Старые миграции не редактировать.

### 2. Настройки оплаты события (модуль `events`, без миграции)
В `events.settings_json` добавить ключ `payment` (DTO `EventPaymentSettings`): `{"enabled":true,"instructions":"Перевод на карту … , в назначении: Фамилия, клуб","feeMode":"PER_DISCIPLINE|PER_EVENT","eventFeeAmount":null,"currency":"RUB","dueDays":3}`. `feeMode=PER_DISCIPLINE` — сумма = `entry_fee_amount` вида (как сейчас); `PER_EVENT` — одна сумма на участника за событие, относится к первой подтверждённой заявке, остальные `NOT_REQUIRED` (правило зафиксировать в тесте). `enabled=false` → все заявки `NOT_REQUIRED`.
- `PATCH /api/v1/events/{id}` принимает `payment` (опционально, прежние поля сохранены); `GET /api/v1/events/{id}` и публичный `GET /api/v1/public/events/{slug}` возвращают `payment` (`instructions`, `feeMode`, суммы) — публично только при `enabled`.
- Доступ к PATCH — как сейчас (`assertCanModify`).

### 3. Расчёт и фиксация суммы (модуль `registrations`)
- При переходе заявки в `CONFIRMED` (`ReviewRegistrationUseCase`, импорт Excel, продвижение из листа ожидания) заполнять `fee_amount/fee_currency` по правилам п. 2 и ставить `payment_status = PENDING` при сумме > 0, иначе `NOT_REQUIRED`. Для уже существующих заявок — ленивое заполнение при первом показе не делать; вместо этого одноразовый админский `POST /api/v1/events/{eventId}/payments/recalculate-fees` (organizer/operator, `assertCanModify`), который заполняет суммы у CONFIRMED/PAID заявок без `fee_amount` и не трогает уже оплаченные.
- Расширить `RegistrationResponse`: `feeAmount, feeCurrency, paidAmount, paidAt, paidBy{userId,name}, paymentMethod, paymentReference, paymentComment` (все nullable, прежние поля сохранены).

### 4. Операции секретаря (модуль `registrations`, контроллер `RegistrationController` — расширить `mark-paid`, добавить новые)
Все — роли `organizer|operator|platform_admin` + `EventAccessService.assertCanModify(eventId, principal)`; каждая пишет строку в `registration_payment_log` и `updated_at`.
- `POST /api/v1/registrations/{id}/mark-paid` — тело теперь опциональное `{amount?, method?, reference?, comment?, paidAt?}`; без тела — как раньше (сумма = `fee_amount`, метод `OTHER`) — обратная совместимость для e2e QA05. Допустимо из `CONFIRMED` и `ADMITTED` (сейчас только CONFIRMED — расширить, статус заявки при этом не менять на `PAID`, если был `ADMITTED`; из `CONFIRMED` → `PAID` как раньше). Повторный вызов на PAID → 409 `registrations.already_paid`.
- `POST /api/v1/registrations/{id}/waive-payment` `{comment}` → `payment_status = WAIVED` (освобождён от взноса), статус заявки как при оплате.
- `POST /api/v1/registrations/{id}/refund-payment` `{amount?, comment}` → `REFUNDED`; статус заявки не меняется (снятие — отдельное действие `withdraw`).
- `POST /api/v1/registrations/{id}/reset-payment` `{comment}` → обратно в `PENDING` (ошибочная отметка); статус заявки `PAID` → `CONFIRMED`.
- `POST /api/v1/events/{eventId}/payments/mark-paid-bulk` `{registrationIds:[…], method, reference?, comment?}` → `{updated, skipped:[{id, reason}]}` — массовая отметка (оплата клубом по счёту). Одна транзакция, частичный успех допустим (skipped с причинами).
- `GET /api/v1/events/{eventId}/payments/summary` (organizer/operator, `assertCanManage`) → `{currency, totals:{due, paid, pending, waived, refunded}, byClub:[{club, participants, registrations, due, paid, pending, pendingRegistrationIds:[…]}]}` — долги по клубам; один SQL с группировкой, без N+1.
- `GET /api/v1/registrations/{id}/payment-log` (organizer/operator) → история действий.
Ошибки: `registrations.payment_not_applicable` (неподходящий статус), `registrations.already_paid`, `registrations.payment_disabled` (оплата выключена в событии), `validation_error` при отрицательной сумме. Сообщения на русском.

### 5. Участник
- `GET /api/v1/registrations/me` — в каждой заявке `feeAmount`, `paymentStatus`, и на уровне ответа (или отдельным `GET /api/v1/events/{eventId}/payment-instructions`, доступ `authenticated`) — реквизиты `instructions` и срок `dueAt = confirmedAt + dueDays`.
- Существующий `POST /api/v1/registrations/{id}/payments` (создание платежа провайдера) — не ломать; при `feeMode`/`enabled=false` → 409 `payments.not_required` (если такого кода нет — добавить).

### 6. Напоминание об оплате (модуль `notifications`)
- Шаблон `payment_reminder` (html/txt): «Ожидается оплата взноса за участие в {событие}: {сумма} {валюта}. {реквизиты}. Срок: {dueAt}». Настройка организации — как у других шаблонов, включена по умолчанию.
- Отправка: (а) при `CONFIRMED` с `PENDING` — сразу (в том же письме `registration_confirmed` добавить блок об оплате, если сумма > 0 — предпочтительно, чтобы не слать два письма; если шаблон `registration_confirmed` проще не трогать — отдельное письмо, указать в PR), (б) планировщик раз в день 09:00 по поясу площадки: заявки `PENDING` старше `dueDays` без напоминания за последние 3 дня — повторное письмо, максимум 2 повтора. Факт отправки хранить в outbox (поиск по `template_code` + `registration_id` в payload) — без новой таблицы.
- При `mark-paid` — письмо `payment_received` **не** делать (достаточно статуса в кабинете; отметить в PR как возможное расширение).
