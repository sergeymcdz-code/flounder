# S10 — Календарь тестовых данных: еженедельные соревнования на несколько месяцев

Ветка: `feat/S10-demo-calendar` от актуального `origin/main`. Один PR. Область: только `scripts/demo/**`, `docs/qa/demo-calendar.md`, `infra/crontab.example` (одна строка), `docs/scripts/demo/out/**` (новые наборы). Код приложения (`sport-platform/**`) не трогать; если без изменения API задачу выполнить нельзя — остановиться и описать в PR, что именно нужно.

## Зачем
Стенд https://sportgate.pro должен выглядеть как живая платформа: на каждой неделе — соревнование с полным набором данных (заявки, посев, протоколы, результаты, документы, очередь, исправления), прошлые — завершены, ближайшее — готово к старту, будущие — с открытой регистрацией. Данные реалистичные, но не затрагивают ничего, кроме демо-организации и её площадок. Основа — сид S02 (`scripts/demo/seed.ts`, `plan.ts`, `bodies.ts`, `reset.ts`); его не ломать, повторно использовать.

## Что сделать

### 1. Генератор календаря `scripts/demo/calendar.ts` (+ `calendar-plan.ts`)
- Вход: `CALENDAR_START` (понедельник первой недели, default — понедельник 4 недели назад от `DEMO_DATE`), `CALENDAR_WEEKS` (default 16), `DEMO_DATE` (как в S02, «сегодня» для статусов), `CALENDAR_PREFIX` (default пусто; при непустом добавляется к названиям, как `EVENT_TITLE_SUFFIX`).
- На каждую неделю — одно соревнование в субботу (10:00 и 15:00 по TZ площадки), для 3–4 недель из 16 — два (суббота и воскресенье, разные города). Итого ≈ 20 соревнований.
- Шаблоны (чередовать детерминированно, по номеру недели): «Кубок города …», «Открытое первенство … среди юношей и девушек», «Клубные старты «…»», «Первенство области», «Мемориал …», «Спринт-фестиваль», «Осенний/Зимний кубок SportGate». Города и площадки: Самара (2 бассейна), Тольятти, Казань, Уфа, Саратов, Ульяновск, Пенза, Оренбург — площадки создаются через API в демо-организации (25 м / 8 дорожек, две-три — 50 м / 10 дорожек), повторно используются по названию.
- Программа: 6–12 видов из пула (50/100/200/400 в/с, 50/100 на спине, 50/100 брасс, 50/100 баттерфляй, 200 к/п; М/Ж; возрастные группы 2010–2016 г. р.), 1–2 сессии, лимиты на вид/событие — у части событий.
- Состояние по положению недели относительно `DEMO_DATE`:
  - прошедшие недели — `COMPLETED`: все заплывы `FINISHED`, результаты опубликованы, 1–3 `CORRECTED`, 2–4 DNS/DNF, 0–1 DSQ, протоколы доступны анонимно;
  - текущая неделя — `REGISTRATION_CLOSED`, посев и стартовый протокол готовы, первые 2 заплыва сессии 1 `FINISHED` (как B в S02);
  - +1…+3 недели — `REGISTRATION_OPEN`: заполненность 40–90 %, 3–6 `NEEDS_CORRECTION`, у одного события очередь (`WAITLISTED` 3–5), у двух — PDF-документы участников (из fixtures S02);
  - +4…+8 недель — `PUBLISHED`, регистрация открывается по дате (через API — как позволяет lifecycle M06), заявок 0–20 %;
  - +9 и дальше — `PUBLISHED` без заявок, одно событие — `DRAFT` (не виден публично).
- Участники: расширить `names.ts` до ≥ 80 мужских / 80 женских имён и ≥ 250 фамилий; собрать стабильный пул ≈ 900 пловцов, разбитый по 14–16 клубам (клуб ↔ город); на событие брать 80–220 заявок из клубов «своего» региона плюс 10–20 % «гостей», чтобы одни и те же спортсмены повторялись из недели в неделю (это видно в «Мои пловцы» и результатах). Заявочные времена — через `entryTime` с прогрессом по неделям (чуть быстрее к концу сезона). Набор S02 (`set-M`) включить как один из клубов.
- Аккаунты: существующие `org/sec/judge/parent@flounder.demo` + `DEMO_OWNER_EMAIL` (участник, у него 2 ребёнка в разных событиях). Новых служебных аккаунтов не плодить; профили участников — без e-mail, кроме 6–8 «родителей» `s10-parent-N@flounder.demo` для сценариев исправления/очереди.
- Если в `main` к моменту работы слит S05 (оплата) — у событий с взносом (половина) проставить `PAID`/`PENDING`/`WAIVED` в правдоподобной пропорции; если S05 не слит — пропустить и написать в PR.
- Всё только через HTTP API (как S02). Идемпотентность: повторный запуск находит события по названию+дате, не создаёт дублей, достраивает недостающее; при расхождении дат — понятная ошибка с указанием `reset`.
- Безопасность: `DEMO_SEED_ENABLED=true` обязателен; трогать только события демо-организации; в описание каждого события писать «Тестовые данные SportGate» (в `description`), а в названия — нет.
- Производительность: ≈ 20 событий × ~150 заявок — бюджет полного прогона ≤ 60 мин через контейнер на сервере; параллелить по событиям нельзя (посев/расписание), но заявки одного события подавать пачками. Выводить прогресс по событиям и итоговую JSON-сводку `S10` (недели, slug, статусы, количества).

### 2. Еженедельное «проживание» `scripts/demo/calendar.ts --advance`
- Режим `--advance` переводит календарь на текущую дату сервера: закрывает регистрацию событиям этой недели, завершает прошедшие (судейский ввод + публикация результатов, как для прошлых недель), открывает регистрацию следующим по датам, добавляет 5–15 новых заявок в открытые события (имитация жизни), переводит DRAFT в PUBLISHED, когда до события ≤ 8 недель. Идемпотентно; без изменений, если делать нечего.
- Строка для `infra/crontab.example`: понедельник 06:00 МСК, через контейнер `node:22-alpine` (команда как в README S02), лог в `/home/deploy/backups/demo-calendar.log`. Не включать cron автоматически — только пример и инструкция.

### 3. Сброс
- `reset.ts`: режим `DEMO_CALENDAR=true` — выбирает все события демо-организации с описанием «Тестовые данные SportGate» (или по `CALENDAR_PREFIX`), печатает JSON `demo_targets` и точную команду `psql`; существующий `reset.sql` переиспользовать (проверить, что он удаляет документы, результаты, заплывы, заявки, профили без других заявок). События A/B/C из S02 сброс календаря не трогает, если они не входят в выбор.

### 4. Тесты и документация
- Vitest: план календаря детерминирован (снимок на 16 недель: даты, статусы, числа заявок), пул участников без дублей, распределение клубов по регионам, `--advance` на фиксированных датах меняет ровно ожидаемые события. `npm test` в `scripts/demo` зелёный.
- `docs/qa/demo-calendar.md`: что создаётся (таблица недель), команды для сервера без Node (контейнер), сброс, cron, ограничения; `scripts/demo/README.md` — ссылка на него. `docs/qa/rehearsal-2026-10-17.md` не менять.
- В описании PR — по п.10 AGENTS.md; отдельно: время полного прогона на локальном стенде и объём БД после.

## Приёмка
1. Чистая БД → `calendar.ts` (16 недель, `DEMO_DATE=2026-10-19`) завершается без ошибок ≤ 60 мин, сводка S10 напечатана.
2. Публичный каталог показывает ≈ 20 соревнований; у прошлых — результаты и PDF, у текущего — табло с третьим заплывом, у ближайших — открытая регистрация с очередью/исправлениями.
3. Повторный запуск ничего не дублирует. `--advance` с `DEMO_DATE` на неделю позже меняет статусы ровно по правилам.
4. `reset.ts` с `DEMO_CALENDAR=true` печатает корректный список целей; после `psql` стенд чист, A/B/C на месте.
