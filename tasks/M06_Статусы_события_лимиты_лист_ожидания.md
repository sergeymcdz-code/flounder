# M06. Жизненный цикл события: автопереходы по датам, REGISTRATION_CLOSED/ARCHIVED, лимиты и лист ожидания

Прочитай `AGENTS.md`, `docs/02_ТЗ_демо.md` §5.3–5.4, `docs/03_ТЗ_MVP_50_соревнований.md` §3.1 (статусы, лимиты). Ветка `feat/M06-event-lifecycle-limits` от актуального `main`. Модули `events`/`competition`/`registrations`. Один PR. Поток A пересекается с QA01 (тесты ядра): не переименовывать существующие статусы и эндпоинты, только добавлять.

## Что сделать
1. Статусы события: добавить `REGISTRATION_CLOSED` и `ARCHIVED` (если нет) в enum и CHECK (миграция `V033__event_status_lifecycle.sql` — только расширение CHECK/значений); переходы: REGISTRATION_OPEN → REGISTRATION_CLOSED (вручную `POST /events/{id}/close-registration` и автоматически по `registrationCloseAt`), REGISTRATION_CLOSED → REGISTRATION_OPEN (вручную, «продлить»), COMPLETED → ARCHIVED (вручную, `POST /events/{id}/archive`; архивное событие read-only для организатора, публичные страницы доступны). Запрещённые переходы → `events.invalid_transition`.
2. Автопереходы: `@Scheduled(cron="0 * * * * *")` задача в `events`: открыть регистрацию по `registrationOpenAt` (только если событие PUBLISHED), закрыть по `registrationCloseAt`; идемпотентно; логировать переходы в существующую таблицу журналов (если есть `event_logs`/`rule_execution_logs` kind — использовать, иначе лог приложения). Публичная форма заявки при закрытой регистрации → `registrations.registration_closed` (сообщение на русском, фронт показывает «Регистрация закрыта»).
3. Лимиты: поля `maxParticipants` на событии и `maxParticipants` на дисциплине (+ по возрастной группе — `jsonb` `limitsByAgeGroup` в дисциплине; миграция та же V033, nullable = без лимита); API `PATCH` события/дисциплины принимают их (расширить существующие DTO, не ломая контракт §5.3: новые поля опциональны).
4. Лист ожидания: при достижении лимита новая заявка получает статус `WAITLISTED` (расширить CHECK статусов заявок) с `waitlistPosition`; при снятии/отклонении подтверждённой заявки — первая из листа ожидания переходит в `SUBMITTED` и публикуется событие (для M05). Организатор видит лист ожидания в списке заявок (фильтр по статусу) и может подтвердить вручную «вне лимита». Посев игнорирует `WAITLISTED`.
5. Фронт: в форме события/дисциплины поля лимитов; бейджи «Лимит: 120/150»; кнопки «Закрыть регистрацию»/«Продлить»/«В архив» с подтверждением; на публичной странице — «Регистрация закрыта» / «Мест нет, запись в лист ожидания».
6. Тесты: таблица переходов (разрешённые/запрещённые), автопереход с подменой `Clock`, лимит по событию/виду/группе, продвижение из листа ожидания, посев без WAITLISTED, публичная форма при закрытой регистрации.
