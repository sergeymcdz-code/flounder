# M04. Документы участников: загрузка медсправки, страховки, согласий (без проверки комиссией)

Прочитай `AGENTS.md`, `docs/03_ТЗ_MVP_50_соревнований.md` §3.2 «Документы», §4 (152-ФЗ, шифрование, подписанные ссылки), §5 (S3). Ветка `feat/M04-participant-documents` от актуального `main`. Новый модуль `documents-storage` → назови `files` (`com.acme.sportplatform.files`) + расширение `registrations`. Один PR. Этап 1 дорожной карты: «загрузка без проверки» — статусная модель закладывается, экран мандатной комиссии будет в следующей задаче.

## Что сделать
1. Хранилище файлов: интерфейс `FileStorage` (put/get/delete/presignedUrl) с двумя реализациями — `LocalFileStorage` (каталог `app.files.local-dir`, по умолчанию `./data/files`, в `compose.prod.yaml` — именованный том `flounder_files`, смонтированный в `api`) и `S3FileStorage` (AWS SDK v2, совместимо с Selectel/Yandex: endpoint, bucket, ключи из переменных окружения; выбирается `app.files.provider=local|s3`). Файлы шифровать at rest AES-256-GCM ключом из `APP_FILES_ENCRYPTION_KEY` (base64, 32 байта); без ключа приложение не стартует в профиле `prod`. Ограничения: jpg/jpeg/png/pdf, ≤10 МБ, проверка magic-bytes, а не только расширения.
2. Миграция `V031__participant_documents.sql`: таблица `participant_documents` (id, profile_id FK, event_id FK nullable — документ может быть общим для профиля, type ∈ MEDICAL_CERT|INSURANCE|PARENT_CONSENT|PDN_CONSENT, file_key, original_name, content_type, size_bytes, issued_at date, valid_until date, status ∈ NOT_UPLOADED|PENDING|ACCEPTED|REJECTED, reject_reason, uploaded_by, uploaded_at, reviewed_by, reviewed_at); индексы по profile_id, event_id, status; CHECK на типы/статусы. Таблица `file_access_log` (id, file_key, user_id, action, at) — журнал доступа к документам.
3. API (`registrations` или новый `participants` web-слой):
   - `POST /api/v1/profiles/{profileId}/documents` multipart (`type`, `file`, `issuedAt?`, `validUntil?`) — участник для своего профиля/ребёнка (связь родитель→профиль как сейчас в T03), организатор/оператор — для профилей своего события; ответ — документ со статусом `PENDING`.
   - `GET /api/v1/profiles/{profileId}/documents`, `DELETE /api/v1/profiles/{profileId}/documents/{id}` (только PENDING, свой).
   - `GET /api/v1/documents/{id}/download` — подписанная временная ссылка (10 мин) или стрим с проверкой прав + запись в `file_access_log`.
   - `GET /api/v1/events/{eventId}/registrations` — дополнить каждой заявке сводку `documents: {MEDICAL_CERT: status, …}` без N+1 (один запрос).
   - Автопроверка допуска (справка действует ≥ даты старта): поле `admissionWarnings[]` в заявке; **не** блокировать посев — только предупреждение (блокировка — в задаче мандатной комиссии).
4. Фронт: в кабинете участника (`my/registrations`) блок «Документы» по профилю: загрузка с телефона (input `accept="image/*,application/pdf"`, `capture`), статус, срок действия; у организатора в списке заявок — колонка-иконки статусов документов и фильтр «нет справки». Русские тексты, состояния, 375 px.
5. Тесты: загрузка/скачивание через `LocalFileStorage` в temp-dir, шифрование (файл на диске не равен исходному, после чтения равен), отказ по типу/размеру/magic-bytes, права (чужой профиль → 403), журнал доступа, сводка документов в списке заявок без N+1 (assert на число SQL через статистику Hibernate).

## Не делать
Экран мандатной комиссии, напоминания, печать листа допуска — следующая задача. Не менять алгоритм посева.
