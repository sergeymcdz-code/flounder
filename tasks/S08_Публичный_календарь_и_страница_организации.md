# S08. Публичный календарь соревнований и страница организации

Прочитай `AGENTS.md`, `docs/03_ТЗ_MVP_50_соревнований.md` §3.6 («страница организации (календарь стартов), архив результатов»), §4 (публичные страницы: WCAG AA, 360 px, p95 ≤ 1 с), `docs/02_ТЗ_демо.md` §5.7, §6.3 (существующие публичные страницы), `docs/design/D01_Концепция.md` (стиль). Ветка `feat/S08-public-calendar-org-page` от актуального `origin/main`. Модули `publication` (новые публичные эндпоинты), `organizations` (публичный профиль — **новые файлы**, существующие контроллеры не трогать), `events` (расширение `EventPublicLookup`), фронт `features/public`. Один PR. Миграция **V039** (номер зарезервирован). Приоритет: высокий. Слияние после демо 19.10 и **после S07** (тот же модуль `organizations`; при конфликте ребейзиться на S07).

## Зачем
Сейчас у платформы нет «витрины»: главная страница (`EventsPage` по маршруту `/`, API `GET /api/v1/public/events` в модуле `competition`) показывает плоский список событий без фильтров, а у организации нет публичной страницы со своими стартами и архивом результатов. Для 20 организаторов и родителей, которые ищут «ближайшие старты в Самаре», нужен календарь с фильтрами и страница организации с постоянной ссылкой — её организаторы будут ставить в соцсети.

## Что сделать

### 1. Миграция `V039__organization_public_profile.sql`
```sql
alter table organizations
  add column public_slug varchar(128),
  add column description text,
  add column website varchar(255),
  add column public_email varchar(255),
  add column public_phone varchar(32),
  add column is_public boolean not null default true,
  add column logo_file_key varchar(255);
create unique index uq_organizations_public_slug on organizations(public_slug) where public_slug is not null;
```
Заполнение `public_slug` для существующих организаций — не в миграции (данные), а лениво: при первом публичном обращении или при сохранении профиля; для стенда — команда в PR-описании (`UPDATE … set public_slug = …` выполняет владелец) **или** автогенерация из `name` при старте через `ApplicationRunner` (транслитерация, как для `public_slug` событий — переиспользовать существующий генератор slug из `events`, если он доступен; иначе скопировать правило: латиница, `-`, уникальность суффиксом `-2`). Выбранный способ описать в PR.

### 2. Публичный профиль организации (модуль `organizations`, новые файлы)
- `GET /api/v1/organizations/{id}/public-profile` и `PUT /api/v1/organizations/{id}/public-profile` `{publicSlug, description, website, publicEmail, publicPhone, isPublic}` — доступ `platform_admin` или `owner|admin` организации (политика `owner` в TSV; проверка через `OrganizationManagementAccess.isOwnerOrAdmin`). Валидация slug: `^[a-z0-9][a-z0-9-]{2,127}$`, уникальность → 409 `organizations.slug_taken`; зарезервированные значения (`new`, `admin`, `api`) → 400.
- Логотип: `POST /api/v1/organizations/{id}/logo` (multipart `file`, png/jpg ≤ 2 МБ, magic-bytes как в M04) и `DELETE`. Хранить через `files.FileLookup`/`FileStorage` модуля `files` (M04) **без шифрования** (публичный файл; если `FileStorage` шифрует всегда — добавить метод `putPublic`/флаг в модуле `files` минимальным изменением и описать в PR). Отдача: `GET /api/v1/public/organizations/{slug}/logo` (кеш `max-age=3600`).
- `OrganizationLookup` (корень модуля): добавить `PublicOrganization publicBySlug(String slug)` и `Map<UUID, PublicOrganizationCard> cards(Collection<UUID> ids)` (`{id, name, publicSlug, city, hasLogo}`) — для календаря и карточки события.

### 3. Публичный календарь (модуль `publication`, новый контроллер `PublicCalendarController`)
- `GET /api/v1/public/calendar?from=2026-10-01&to=2026-12-31&city=&organization=&q=&status=upcoming|past|all&page=0&size=20` → `{items:[{slug, title, startDate, endDate, city, venueName, organization:{name, publicSlug}, status, registrationOpen, registrationCloseAt, participantsCount?, disciplinesCount, hasResults}], page, size, total, cities:[…]}`. Видимость — те же правила, что у `GET /public/events/{slug}` (`PUBLISHED` и позже; `DRAFT` не показывать; `ARCHIVED` показывать в `past`). Сортировка: `upcoming` — по дате старта по возрастанию, `past` — по убыванию. `cities` — список городов площадок среди видимых событий (для фильтра). Один SQL с `count(*) over()`, без N+1 (организации и площадки — пакетно через Lookup'ы или join в read-модели `publication`, как в `PublicationReadRepository`).
- `GET /api/v1/public/organizations/{slug}` → `{name, publicSlug, city, description, website, publicEmail, publicPhone, hasLogo, stats:{eventsTotal, eventsUpcoming, participantsTotal}, upcoming:[карточки как в календаре, ≤10], past:[≤10]}`; `isPublic=false` или нет slug → 404 `organizations.not_found`.
- `GET /api/v1/public/organizations/{slug}/events?status=&page=&size=` — тот же формат карточек, что календарь.
- Кеш: Caffeine 30 с на календарь по строке запроса и на страницу организации по slug (сброс не нужен — TTL), заголовок `X-Flounder-Cached` как в существующем публичном кеше. `Cache-Control: public, max-age=15`.
- Расширить `EventPublicLookupResult` (модуль `events`) полями `organizationId`, `venueId`, `city`, если их нет, — только добавление полей в record (все места создания обновить).
- Карточка события `GET /api/v1/public/events/{slug}`: добавить поле `organization:{name, publicSlug, hasLogo}` (остальное без изменений).
