## Зачем
Сейчас, чтобы секретарь или судья получил доступ к событиям организации, нужны **два** действия администратора платформы: выдать глобальную роль (`POST /users/{id}/roles`) и добавить в члены организации. Организатор сам не может завести себе секретаря. Кроме того, любой член организации с ролью `member` получает полный доступ ко всем событиям (`EventAccessService.assertCanManage` проверяет только факт членства). Для 20 организаторов и 50 стартов нужно: организатор сам приглашает сотрудников по e-mail, роль в организации определяет права, один человек может быть секретарём в двух клубах и видеть, в какой организации он сейчас работает.

## Целевая модель (зафиксировать в `docs/decisions/2026-10-XX-org-roles.md` одним файлом, ≤ 1 стр.)
- Роль члена организации (`organization_members.member_role`) → авторитеты Spring на запросе: `owner`, `admin`, `organizer` → `ROLE_ORGANIZER`; `operator` → `ROLE_OPERATOR`; `judge` → `ROLE_JUDGE`; `member` → ничего (только просмотр). Глобальные роли (`user_role_assignments`) остаются и складываются с ролями из членства (платформенный админ по-прежнему может выдать глобальную роль, но для обычной работы это больше не нужно).
- Права на событие (`EventAccessService`): `assertCanManage` — `platform_admin`, создатель события, члены организации события с ролью `owner|admin|organizer|operator|judge` (как сейчас, **минус `member`**); новое `assertCanView` — все члены, включая `member`; `assertCanAdminister` (новое, для настроек события, архива, оплаты, настроек зачёта) — `owner|admin|organizer` и создатель. Остальные контроллеры **не переписывать**: `@PreAuthorize(hasRole…)` по-прежнему отсекает по роли (теперь — в том числе из членства), а объектный уровень — `assertCanManage`. Исключение — перевести на `assertCanAdminister` только: `PATCH /events/{id}`, `POST /events/{id}/archive`, `DELETE /event-disciplines/{id}`, `PUT/GET /organizations/{id}/notification-settings` (последнее — уже owner-политика, не трогать).
- Судья: роль `judge` даёт только то, что сейчас разрешено `JUDGE` в `@PreAuthorize` (ввод/публикация результатов, live), объектно — события своей организации. Назначение судьи на конкретное событие/заплывы — **не в этой задаче**.
- Участник (`participant`) и `coach` — не меняются (coach — S12).

## Что сделать

### 1. Роли из членства (модуль `identity` + `organizations`)
- В фильтре JWT (`identity/infrastructure/security/JwtAuthenticationFilter`, строки, где из снимка пользователя строятся `authorities`): к глобальным ролям добавить роли, производные от `organization_members` текущего пользователя (через `organizations.UserMembershipLookup` — уже существует в `identity`, проверить, что он возвращает `memberRole`; если нет — расширить). Одним SQL вместе с существующим чтением ролей (не два запроса). `AuthenticatedUserPrincipal` дополнить `memberships: List<{organizationId, memberRole}>` (для `EventAccessService` и UI).
- `GET /api/v1/auth/me`: `roles` по-прежнему только глобальные (контракт M01), добавить `memberships:[{organizationId, organizationName, memberRole}]` и `effectiveRoles:[code]` (объединение). `POST /auth/login` — без изменений.
- `EventAccessService`: реализовать `assertCanView`, `assertCanAdminister`, изменить `assertCanManage` (исключить `member`). `EventLookup.accessibleEventIds(userId)` — все организации членства (как сейчас). Коды ошибок прежние: `events.access_denied`.

### 2. Приглашения (модуль `organizations`, миграция `V037__organization_invitations.sql`)
```sql
create table organization_invitations (
  id uuid primary key,
  organization_id uuid not null references organizations(id) on delete cascade,
  email varchar(255) not null,
  member_role varchar(64) not null check (member_role in ('admin','organizer','operator','judge','member')),
  token_hash varchar(64) not null unique,          -- sha-256 от случайных 32 байт, сам токен только в письме
  invited_by uuid not null references users(id),
  status varchar(16) not null default 'PENDING' check (status in ('PENDING','ACCEPTED','REVOKED','EXPIRED')),
  expires_at timestamptz not null,
  accepted_by uuid references users(id),
  accepted_at timestamptz,
  created_at timestamptz not null default now()
);
create index idx_org_invitations_org on organization_invitations(organization_id);
create unique index uq_org_invitations_pending on organization_invitations(organization_id, lower(email)) where status = 'PENDING';
```
API (доступ `platform_admin` или `owner|admin` организации — существующая политика `owner` из TSV):
- `POST /api/v1/organizations/{id}/invitations` `{email, memberRole}` → приглашение (без токена в ответе), срок 7 дней; письмо `organization_invitation` (модуль `notifications`, через outbox): «{Имя} приглашает вас в организацию {название} на роль {роль}. Принять: {APP_PUBLIC_URL}/invitations/{token}». Повторное приглашение того же e-mail при PENDING → 409 `organizations.invitation_exists`; если пользователь уже член → 409 `organizations.already_member`. Роль `owner` через приглашение не выдаётся.
- `GET /api/v1/organizations/{id}/invitations?status=PENDING` → список; `DELETE /api/v1/organizations/{id}/invitations/{invitationId}` → `REVOKED`, 204.
- `GET /api/v1/invitations/{token}` (публично) → `{organizationName, memberRole, email, expiresAt, status, userExists}` — для страницы приёма; токен в URL, в БД сравнивается хеш; истёкшее → 410 `organizations.invitation_expired`.
- `POST /api/v1/invitations/{token}/accept` (Bearer) → создаёт `organization_members` (если e-mail пользователя совпадает с приглашением без учёта регистра; иначе 403 `organizations.invitation_email_mismatch`), статус `ACCEPTED`, 200 с членством. Повторный accept → 409. Существующий `POST /organizations/{id}/members` остаётся (админ/owner добавляют существующего пользователя напрямую).
- Истечение: статус `EXPIRED` выставляется лениво при чтении (без планировщика).

### 3. Организации пользователя и переключение
- `GET /api/v1/organizations/mine` (authenticated) → `[{id, name, city, memberRole, eventsCount}]`.
- `GET /api/v1/organizer/events?organizationId=` — фильтр (опциональный; без него — как сейчас все доступные).
- `POST /api/v1/events` — `organizationId` обязателен и проверяется членством с ролью `owner|admin|organizer` (проверить текущее поведение; если сейчас берётся «первая организация пользователя» — заменить на явный параметр, сохранив обратную совместимость: при отсутствии параметра и ровно одной организации — она).

### 7. Тесты
- Интеграционные: пользователь без глобальных ролей, член организации с ролью `operator` → `POST /registrations/{id}/review` 200 на событии своей организации, 403 на чужом; тот же с ролью `member` → `GET /events/{id}` 200, `PATCH /events/{id}` 403; `judge` → ввод результатов 200, `PATCH /events/{id}` 403; глобальная роль `operator` без членства → 403 на событие (как сейчас, регресс не допускать).
- Приглашения: полный цикл (создать → письмо в outbox с ссылкой → accept под пользователем с тем же e-mail → член с нужной ролью → повторный accept 409); чужой e-mail → 403; отозванное → 410/409; истёкшее → 410; дубликат PENDING → 409.
- Фильтр JWT: число SQL-запросов на аутентифицированный запрос не выросло больше чем на один (assert по статистике Hibernate или логу, как в M01).
- Фронт: тесты переключателя организации и страницы приглашения.
- `ModulithArchitectureTest`: зависимость `identity → organizations` уже есть через `UserMembershipLookup`; циклов не добавлять.
