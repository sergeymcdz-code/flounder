# S02 — Демо-данные: несколько соревнований с датами относительно демо

Ветка `feat/S02-demo-multi-events` от актуального `origin/main`. Один PR. Правила — AGENTS.md. Приоритет: высокий (демо 19.10, репетиция 17.10).

## Цель
На стенде должно быть **три** соревнования, чтобы показать весь жизненный цикл за одно демо:
- **A «Кубок SportGate — осень» — прошедшее**: дата = демо − 8 дней (11.10 при DEMO_DATE=19.10), статус COMPLETED, все заплывы FINISHED, результаты опубликованы, протокол результатов с медалистами, 2 CORRECTED-правки, 3 DNS/DNF.
- **B «Открытый кубок Самары по плаванию» — ближайшее**: дата = демо + 1 день (20.10), REGISTRATION_CLOSED, 200 заявок (текущий импорт), посев и стартовые протоколы опубликованы, первые 2 заплыва сессии 1 FINISHED с результатами (чтобы табло и «Отставание» были живые), остальные PUBLISHED.
- **C «Первенство области среди юношей» — на регистрации**: дата = демо + 5 дней (24.10), REGISTRATION_OPEN, лимит участников на событие 150 и лимит 16 на один вид, 120 заявок + 4 WAITLISTED (лист ожидания виден), 6 заявок NEEDS_CORRECTION, 2 с загруженными документами (M04), 1 участник с реальным e-mail владельца `sergeymcdz@yandex.ru` (для показа письма; остальные `@flounder.demo`/`@example.com`).

## Что сделать
1. `scripts/demo/seed.ts`: параметры `DEMO_DATE` (день демо) и `DEMO_EVENTS=A,B,C` (по умолчанию все три); даты событий считаются от DEMO_DATE; каждое событие — отдельный slug и название; идемпотентность по названию (повторный прогон не дублирует). Для A и B использовать существующие API (импорт, посев, публикация, результаты через судейский API, finish) — без прямого SQL; если какого-то шага нет в API — остановиться и написать в PR, не обходить через SQL.
2. `scripts/demo/reset.ts/.sql` — сброс по списку slug'ов (все три или один).
3. Все даты сессий/регистрации/заплывов — относительно DEMO_DATE, таймзона площадки Europe/Samara; время старта первой сессии 10:00 местного.
4. Профили: 300 правдоподобных ФИО (муж/жен, 2010–2016 г. р.), 12 клубов Самары/Поволжья, заявочные времена реалистичные по возрасту; без дубликатов ФИО+дата рождения между событиями, но ~40 пловцов участвуют в двух событиях (B и C).
5. `docs/demo-script.md` и `docs/qa/rehearsal-2026-10-17.md`: обновить под три события (какое событие на каком шаге сценария); таблица «slug — назначение — статус».
6. `scripts/demo/seed.test.ts`: тесты расчёта дат и идемпотентности. `npm test` в `scripts/demo`.

## Проверка
Локально: `DEMO_DATE=2026-10-19 npx tsx seed.ts` на чистой БД → три события с ожидаемыми статусами; e2e `npm run test:demo` зелёный (поправить ожидания под новые названия). В PR: время прогона сида, количество записей по событиям. Миграций нет.
