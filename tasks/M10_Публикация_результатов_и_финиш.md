# M10. Публикация результатов отдельно от стартового протокола: «Опубликовать» = FINISHED, «Финиш» идемпотентен

## Зачем

Один столбец `competition_units.status` сегодня означает три разные вещи: опубликован ли стартовый протокол (`DRAFT → PUBLISHED`, модуль `scheduling`), идёт ли заплыв (`IN_PROGRESS → FINISHED`, `EventLiveUseCase`) и опубликованы ли результаты (`PublishCompetitionUnitUseCase` ставит `PUBLISHED`). Из-за этого на демо-сценарии шага 7 (`docs/demo-script.md`) ломается цепочка «Старт → ввод → Сохранить → Опубликовать → исправление → Финиш»:

- **QA05-07.** Судья нажимает «Опубликовать» в панели (`POST /api/v1/competition-units/{unitId}/publication {published:true}`) → use case возвращает статус из `IN_PROGRESS` в `PUBLISHED` → публичная выдача (`PublicationReadRepository.entries`, `left join results … and u.status in ('FINISHED','COMPLETED')`) результаты не отдаёт: `/e/{slug}/results` пуст, «Найти себя» без результата.
- **QA05-09.** После этого «Финиш» (`POST /competition-units/{id}/finish`) → 400 `results.invalid_transition`, потому что `EventLiveUseCase.finish` требует `IN_PROGRESS`.

Добавить `PUBLISHED` в JOIN нельзя: ввод результатов разрешён и в `PUBLISHED` (`SwimResultsUseCase:81`), черновые времена утекут на публичную страницу.

**Принятое решение (ADR ниже, не пересматривать в ходе задачи):** отдельного флага публикации результатов и миграции **не вводим**. Публичность результатов по-прежнему определяется статусом заплыва `FINISHED`/`COMPLETED` (принцип из `docs/09_HANDOFF_руководителю_2026-10-13.md`). Статус `PUBLISHED` остаётся **только** признаком опубликованного стартового протокола. «Опубликовать результаты» в панели судьи — это переход заплыва в `FINISHED` с проверкой полноты результатов (та же `validateResultForPublication`, что сейчас). «Финиш» — отдельное действие: закрыть заплыв, если он ещё идёт, и передвинуть live на следующий; на уже `FINISHED` заплыве — идемпотентен (200, только двигает live). Что мы при этом теряем: нет состояния «заплыв завершён, результаты внесены, но ещё не опубликованы» — результаты, сохранённые в `FINISHED`, видны публично сразу. Для демо и MVP это приемлемо (секретарь вводит результаты в `IN_PROGRESS`, а публикует одной кнопкой); отдельный флаг `results_published_at` — follow-up после демо, если понадобится (см. ADR «Последствия»).

## Backend (модуль `results`; `publication` не менять)

1. **`PublishCompetitionUnitUseCase.execute(unitId, published=true)` — «опубликовать результаты».** Загружать заплыв через `competitionUnitRepository.lockById` (есть в `CompetitionUnitRepository`), чтобы не гоняться с `/start`/`/finish`. Допустимые исходные статусы: `PUBLISHED`, `IN_PROGRESS`. Проверки результатов — как сейчас (`unit_has_no_entries`, `unit_has_missing_results`, `unit_has_unvalidated_results`, `unit_has_unranked_results`, `invalid_status`). Результат: `status = FINISHED`, `updated_at = now()`. **Live-указатель не трогать** (его двигает «Финиш»). Ошибки:
   - `FINISHED`/`COMPLETED` → `results.unit_already_published` (текст «Результаты заплыва уже опубликованы») → 409;
   - `DRAFT`/`SCHEDULED` → `results.start_list_not_published` («Сначала опубликуйте стартовый протокол») → 409;
   - `CANCELLED` → `results.invalid_transition` → 400 (как у live).
2. **`execute(unitId, published=false)` — «снять результаты с публикации».** Только из `FINISHED` → `status = PUBLISHED` (стартовый протокол остаётся публичным, результаты скрываются, `/start` снова разрешён). Из любого другого статуса → `results.unit_not_published` («Результаты заплыва не опубликованы») → 409; из `COMPLETED` → `results.invalid_transition`. Роли: как исправление после публикации (ТЗ §2 US-6) — `ORGANIZER|OPERATOR|PLATFORM_ADMIN`; `JUDGE` → `AccessDeniedException` (403) — проверку сделай так же, как в `SwimResultsUseCase:95-110`, или через `principal` в контроллере; иначе судья может снять с публикации, поправить без `CORRECTED` и опубликовать снова. Live-указатель не трогать. Старую ветку «вернуть в DRAFT» удалить — она снимала стартовый протокол.
3. **`EventLiveUseCase.finish` — идемпотентность.** Допустимые статусы: `IN_PROGRESS` (как сейчас → `FINISHED`) и **`FINISHED`** (статус и `updated_at` не менять). В обоих случаях — `lockState`, `nextScheduled`, `set(eventId, next, principal)` и ответ 200 `LiveStateResponse`. Остальные статусы → `results.invalid_transition` (сообщение «Завершить можно только начатый или опубликованный заплыв»). `start` не менять (из `FINISHED` по-прежнему нельзя).
4. **`SwimResultsUseCase.save`:** `correcting = !existing.isEmpty() && status ∈ {FINISHED, COMPLETED}` (убрать `PUBLISHED` из строк 93–95: при опубликованном стартовом протоколе, но ещё не опубликованных результатах повторное сохранение — обычный ввод, судья не должен получать 403; это сопутствующий дефект того же корня). Разрешённые для ввода статусы (строка 81) — не менять. Запись RANKING-лога и `CORRECTED` — как сейчас.
