# T07 — публичные страницы, печать, PWA

## Что сделано

- Карточка соревнования с площадкой, сессиями, видами и условной кнопкой заявки; публичный layout с нижней навигацией, без боковой панели.
- Стартовый протокол: сессия → вид → заплыв; все 8 дорожек, пустые дорожки с прочерками, NT, зачёркнутые снятые спортсмены.
- Отдельная страница заплыва. Использует опубликованный стартовый протокол: дополнительный публичный эндпоинт не придуман.
- Расписание по сессиям; текущий заплыв выделен, завершённые приглушены. Статусы соответствуют ТЗ §3: IN_PROGRESS, COMPLETED/FINISHED, CANCELLED.
- Live: текущий вид, номер заплыва и общее число заплывов, время, дорожки, следующие 3 старта. Polling **5 секунд по прямому указанию заказчика**, вместо 15 секунд в исходном ТЗ/T07. Пауза в скрытой вкладке, немедленное обновление при возвращении; запросы не перекрываются, отменяются при уходе. Последние успешные данные сохраняются при сетевой ошибке.
- «Найти себя»: поиск фамилии через API, debounce 300 мс, отмена устаревшего запроса, заплывы и опубликованные результаты с абсолютным местом и местом в группе.
- Результаты: абсолют / возрастные группы, серверные места, равные места, DNS/DNF/DSQ после финишировавших.
- Форма заявки: вход/регистрация с `?next=`, безопасный возврат после входа, данные спортсмена, фильтр пола и года рождения, необязательное заявочное время с маской, согласие, отправка, ошибки отдельных видов. POST отправляется с токеном; публичные GET без токена. Ответ POST не интерпретируется как выдуманный DTO — его поля в ТЗ не определены.
- Печать обоих протоколов: A4, поля 15 мм, шрифт 10 pt, повторяемая фиксированная шапка с резервом места через повторяемый `thead`, заплыв не разрывается. Кнопка «Печать» и автоматический диалог после загрузки при `?print=1`. Навигация и кнопки скрыты.
- PWA: manifest Flounder, русский язык, цвета ТЗ, standalone, start_url `/`, SVG → PNG 192/512 и отдельная maskable-иконка, apple-touch-icon. Автообновляемый service worker: оболочка и статика из кэша, публичные GET NetworkFirst (таймаут 3 с, до 80 ответов на сутки). Кэшированные ответы отмечены заголовком, поэтому баннер «Нет связи, показаны последние данные» работает и при недостоверном `navigator.onLine`.
- Мобильная вёрстка 375 px, области действий не менее 44 px, русские тексты, существующие цветовые токены и Inter. Новые UI-киты не добавлены.

## Область изменений

Код новых страниц — `src/features/public`, типизированный клиент — `src/api/public.api.ts`, моки — `src/mocks`.

Файлы страниц организатора T04 и панели судьи T08 **не изменены**. Общие правки: маршруты и lazy-загрузка существующих экранов в `App.tsx` (чтобы их код/CSS не загружались зрителю), bootstrap MSW/PWA, метаданные HTML, build/test-конфигурация. На существующих страницах входа/регистрации изменено только определение возвратного адреса. Общий HTTP-клиент использует текущий origin при отсутствии `VITE_API_BASE_URL`, что позволяет открыть каталог по start_url установленного PWA за одним reverse proxy.

Миграций нет. Backend-эндпоинты не изменялись.

## Маршруты

| Маршрут | Экран |
|---|---|
| `/e/:slug` | Карточка события |
| `/e/:slug/start-list` | Стартовый протокол |
| `/e/:slug/schedule` | Расписание |
| `/e/:slug/live` | Live и поиск |
| `/e/:slug/live#find-me` | Переход сразу к поиску |
| `/e/:slug/results` | Результаты |
| `/e/:slug/register` | Заявка |
| `/e/:slug/heats/:unitId` | Заплыв |
| `/events/:eventCode` | Redirect на `/e/:slug`, с сохранением query/hash |

Для протоколов доступны `?print=1`. Прежние вложенные маршруты регистрации и результатов сохранены.

## Как проверить вручную

1. В `sport-platform/frontend` выполнить `npm ci`, затем `npm run dev:demo -- --host 0.0.0.0`. Открыть `http://localhost:5173/e/demo`. Нужен современный Node, совместимый с текущим Vite проекта; браузер должен разрешать service workers.
2. Проверить карточку: две сессии, четыре вида, восемь дорожек; перейти по ссылкам на все разделы. Моки — 40 заявок в 6 заплывах, выбранных из исходных 200 заявок `docs/scripts/demo/out/set-M.json`. `python3 scripts/generate-public-demo.py` воспроизводит fixture. Строки с NT, пустыми дорожками, снятием, одинаковыми временами и DNS/DNF/DSQ добавлены намеренно.
3. На стартовом протоколе проверить пустые дорожки и зачёркнутое имя; открыть заплыв по его заголовку, вернуться назад. В расписании проверить текущий/завершённые старты. На Live дождаться смены заплыва (мок меняется раз в 15 с, запросы идут раз в 5 с); в DevTools Network проверить интервал, скрыть вкладку и проверить паузу, вернуться и проверить новый запрос.
4. Нажать «Найти себя», ввести фамилию из протокола. Например, выбрать спортсмена из первого заплыва. Проверить заплывы, дорожки, время и оба места; проверить отсутствие совпадений. Мок повторяет prefix-поиск T06, включая эквивалентность е/ё, максимум 20 спортсменов.
5. В результатах переключить «Абсолют / По группам». У DNS/DNF/DSQ места нет. Места берутся с API, браузер их не пересчитывает.
6. На заявке без входа нажать «Войти». В MSW-режиме использовать `parent@flounder.demo` / `Demo2026!`. После входа вернуться на ту же заявку автоматически. Ввести ФИО, дату рождения в диапазоне 2010–2015, выбрать пол, вид, время `003215` → `00:32.15` либо оставить пустым; согласиться и отправить. Для ошибки по виду использовать фамилию `Ошибка`, затем исправить и отправить снова. «Показать все виды» показывает неподходящие виды с пометкой; выбрать их нельзя.
7. На обоих протоколах нажать «Печать» → Chrome «Сохранить как PDF», A4, масштаб 100%, отключить браузерные колонтитулы. Проверить шапку на каждой странице, поля, отсутствие навигации, отсутствие разрыва заплыва. Повторить с URL `?print=1`. Если браузер запрещает автоматический диалог, использовать кнопку.
8. В DevTools выбрать ширину **375×812**. Пройти все 7 экранов, прокрутить таблицы, проверить нижнюю навигацию, отсутствие горизонтального скролла, ввод date/time и клавиатуру поиска.
9. **На настоящем Android:** подключить телефон по USB с разрешённой отладкой, выполнить `adb reverse tcp:5173 tcp:5173`, открыть в Chrome телефона `http://localhost:5173/e/demo`. Это secure localhost, поэтому MSW работает. Альтернатива для Android/iOS — доступ через доверенный HTTPS. Простой HTTP по LAN-IP не поддерживает service workers.
10. **PWA проверять отдельно от MSW:** выполнить `npm run build`, затем `node --experimental-strip-types e2e/public-server.ts` (тестовый API + production-файлы на `http://localhost:5175`). Открыть `/e/demo/live`, дождаться регистрации SW, обновить страницу. Для Android выполнить `adb reverse tcp:5175 tcp:5175`, открыть тот же localhost на телефоне и выбрать в Chrome «Установить приложение». Отключить сеть/включить Offline в DevTools и перезагрузить: оболочка и ранее загруженный live остаются, баннер предупреждает о последних данных. Вернуть сеть — обновление возобновится. На стенде использовать HTTPS и реальный T06 API.
11. Проверить `/events/demo` → `/e/demo`. В production указывать `VITE_API_BASE_URL` только для отдельного backend origin; при одном origin переменную можно не задавать. При переключении MSW ↔ PWA на одном origin удалить старый service worker в DevTools Application, поскольку у них общий scope `/`.

## Проверки и доказательства

- `npm run build` — успешно; production-сборка содержит manifest и service worker, MSW в неё не включается по умолчанию.
- `npm run lint` — exit 0. Остались **21 существующее предупреждение** исходного frontend. Для новых файлов выполнен дополнительный lint с `--deny-warnings`, без предупреждений. Чужие файлы не исправлялись и правила не отключались.
- Vitest + Testing Library + MSW: **15 тестов** (протокол, пустые/снятые дорожки и NT, ранги/DNS, автопечать, live, текущий заплыв, отсутствующий в опубликованном start-list, polling 5 с, пауза/возврат/cleanup, сетевая ошибка, поиск, допуск и время заявки, безопасный возврат, отсутствие данных предыдущего события при 404 нового, сохранение ошибок API и обработка некорректного ответа сервера).
- Playwright: **4 сценария** (все страницы 375 px, поиск/redirect/автопечать, реальный переход через форму входа и отправка заявки с ошибкой по виду, production PWA с кэшем API/оболочки и офлайн-перезагрузкой).
- Lighthouse mobile на production `/e/demo/live` с тестовым API и gzip: **Performance 99 / Accessibility 100**. Установка дополнительно проверена через Chrome DevTools Protocol `Page.getInstallabilityErrors`: пустой список. В современных версиях Lighthouse отдельная PWA-категория отсутствует.
- `mvn -q test` — exit 0; **49 тестов, 0 failures/errors/skipped**, включая интеграционные тесты с PostgreSQL Testcontainers и архитектурную проверку. В логе есть исходное предупреждение о завершении fork JVM после тестов.
- PDF стартового протокола: **6 заплывов, 2 страницы A4**, шапка на обеих, заплывы целиком. Итоговый протокол по группам также проверен.

[Артефакты проверки](verification/T07/): PDF обоих протоколов, screenshots всех экранов в 375×812 и полные страницы, Lighthouse HTML/краткий JSON. Снимки и PDF сгенерированы Chromium через Playwright; физические устройства в этой среде отсутствуют.

## Что не сделано и почему

- Сквозная интеграция с реальным T06 API не проверена: ветка backend ещё не слита, как указано в задаче. API-клиент и MSW используют пути/поля ТЗ §5.4, §5.7 и уточнения `tasks/T06_*.md` (`empty`, `withdrawn`, `overall`, `byAgeGroup.rows`). Для полей, оставленных в ТЗ многоточиями, контракт нужно сверить с T06 при интеграции.
- Физическая проверка Android/iOS и системного диалога установки остаётся владельцу стенда: здесь проверены мобильный viewport Chromium, manifest, installability и offline. Пошаговый сценарий выше.
- `docs/07_CJM*выверка.md` и §5.8 не найдены в актуальном `origin/main`; в доступном ТЗ раздел публичного API — §5.7. Требования доступных документов реализованы.

## Вопросы

1. Где актуальный файл CJM и версия ТЗ с §5.8 для дополнительной выверки?
2. T06: подтвердить развёрнутый DTO `currentUnit`/`next`, внешние обёртки `start-list`/`results` и формат результата POST заявки. Пока live использует DTO заплыва §5.5, метаданные вида и число заплывов берутся из start-list/расписания (расписание сохраняет сведения о заплыве в статусе IN_PROGRESS); POST success воспринимается без предположений о полях.
3. Нужно ли уменьшить TTL live-кэша T06 до 5 с или добавить инвалидацию при переключении заплыва? Polling 5 с реализован по прямому указанию; TTL 10 с из T06 может ограничить фактическую свежесть ответов.
