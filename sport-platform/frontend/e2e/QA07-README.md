# QA07: регрессия этапа 1

`npm run test:qa07` запускает настоящие M01/M10/M02 e2e; MSW выключен. Нужны локальный backend, PostgreSQL с миграциями, зависимости `scripts/demo` и Chromium. Подготовка backend — как в [QA05-README.md](QA05-README.md).

```sh
cd scripts/demo && npm ci
cd ../../sport-platform/frontend && npm ci
npx playwright install chromium
npm run test:qa07
# При установленном системном браузере:
PLAYWRIGHT_CHROMIUM_EXECUTABLE=/usr/bin/chromium npm run test:qa07
# Повтор семи шагов выполнить ДО QA07/429:
DEMO_DATE=2026-10-24 npm run test:demo
```

`QA07_API_URL` (по умолчанию `http://localhost:8080`) принимает только localhost/127.0.0.1. Адрес должен быть разрешён в CORS. `QA07_PASSWORD` задаёт пароль демо-аккаунтов; `DEMO_DATE` по умолчанию `2026-10-24`. При каждом запуске создаётся событие с уникальным суффиксом « · QA07 …» и импортируется M. Тесты создают отдельных пользователей и две организации; существующие демо-аккаунты не блокирует и их пароли не меняет. Удаление/SQL-сброс отсутствуют. Запуски QA05/QA07 последовательны: оба используют порт 5173.

- `qa07-admin.spec.ts`: вход администратора, создание/поиск пользователя, выдача/снятие роли с проверкой UI и API, блокировка/разблокировка, 401 старого JWT и отказ входа, смена пароля, создание организации/член по email, одобрение заявки/заявитель становится owner.
- `qa07-judge.spec.ts`: организатор формирует и публикует стартовые протоколы; судья начинает, вводит и публикует первые два заплыва. Проверяются FINISHED, анонимная выдача и DOM зрителя в общем бюджете ≤15 секунд, запрещённое исправление judge (403 без изменения результата), разрешённая правка operator/CORRECTED, два успешных финиша каждого заплыва и переход live/кнопка следующего заплыва. Поздний повтор финиша первого при идущем втором должен сохранить текущий live.

Журнал сида, UUID/slug, Playwright JSON, trace при ошибке и измеренные задержки — `frontend/work/qa07/`. Это локальные артефакты, их не коммитим. Trace может содержать тестовые токены/пароли: не публикуйте его без очистки. Длительности публикации/правки прикреплены к Playwright-отчёту. Все проверки жёсткие; известных дефектов в новом наборе не маскируем. Намеренно красные backend-регрессии проекта сохраняются в `*IT` с `@Tag("known-defect")` и исключены из обычного `mvn test`.

M02 и M09 уже в main. `qa07-auth.spec.ts` создаёт пользователей через admin API и проверяет смену собственного пароля на **`/account/password`** (фактический маршрут M02), старый пароль 401/новый успешен; реальный access 401 после подмены подписи JWT в sessionStorage → UI `/my/registrations` → настоящий refresh 200 → повтор запроса 200 без /login, refreshToken ротирован. Значения токенов в JSON-сводки не попадают.

**Лимитер и порядок запуска.** Playwright projects с dependencies задают порядок `core` (M01/M10) → `auth` (пароль/refresh) → `rate-limit-last` (429). Последний тест выполняет ровно N неверных паролей отдельного email через `/login`, затем проверяет 429, числовой `Retry-After > 0` и русское сообщение. N берётся из `APP_AUTH_LOGIN_MAX_FAILURES` (по умолчанию 5): передавать одинаковое значение backend и Playwright. Окно backend по умолчанию `APP_AUTH_LOGIN_WINDOW=PT15M`; успешный вход очищает только email, ошибки по IP сохраняются.

Чтобы предыдущие проверки старого пароля не исказили N, последний тест прозрачно пересылает настоящие login-запросы браузера по HTTP socket с отдельным loopback source IP `127.0.0.2` (`QA07_RATE_LIMIT_SOURCE_IP`). Ответы backend, в том числе 401/429, тело и Retry-After, передаются без подмены. Это реальный IP лимитера, а не X-Forwarded-For и не MSW/mock. Новый email не сбрасывает IP-бюджет: повтор последнего теста с тем же source IP раньше 15 минут будет заблокирован уже на первом запросе. Не запускать другие suite после 429 на том же IP. Для нового полного локального прогона дождаться окна или **перезапустить выделенный локальный backend** (лимитер in-memory), затем сначала `test:demo`, потом `test:qa07`. Частые повторы core также расходуют основной IP-бюджет. Повышение N возможно только на отдельном локальном backend с таким же APP_AUTH_LOGIN_MAX_FAILURES у теста; настройку стенда не менять ради зелёного результата.

Условными остаются M06/M07; статус и ограничения — в [отчёте QA07](../../../docs/qa/QA07-stage1-regression.md).
