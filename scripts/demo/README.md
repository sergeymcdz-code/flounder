# T10: подготовка и сброс демо

Скрипты обращаются только к HTTP API. Готовый набор M из `docs/scripts/demo/out/` используется без изменения и генерации. Сид не формирует заплывы, не вводит результаты и не меняет базу напрямую. Сценарий показа и репетиция: [docs/demo-script.md](../../docs/demo-script.md).

## Запуск за пять команд

Предварительно: Node.js 22+, работающий backend демо-стенда с T01/T03/T05, миграциями V020–V026 и доступом к API; администратор из T01. Установка зависимостей независима от frontend.

Из корня репозитория:

```bash
cd scripts/demo
npm ci
cp .env.example .env
${EDITOR:-vi} .env
npx tsx seed.ts
```

В `.env` укажите origin backend в `API_URL` (например, `http://localhost:8080`, без `/api/v1`), `ADMIN_EMAIL`, `ADMIN_PASSWORD`, `DEMO_PASSWORD`, `DEMO_SEED_ENABLED=true`. Последнее — явное включение только на выделенном демо-стенде; при `NODE_ENV=production` или профиле `prod` скрипты отказываются работать. Скрипт не может определить серверный профиль по HTTP, поэтому адрес проверяет оператор. Пример паролей находится только в `.env.example`; `.env` игнорируется Git. Можно передать настройки через окружение: оно имеет приоритет над `.env`. Индивидуальные пароли: `ORG_PASSWORD`, `SEC_PASSWORD`, `JUDGE_PASSWORD`, `PARENT_PASSWORD`.

Сид создаёт организацию, аккаунты организатора/секретаря/судьи/родителя, назначает роли, добавляет организатора как `owner`, секретаря и судью как `staff`. Родитель остаётся внешним участником без служебного членства. Администратор уже создан T01. Площадка — Самара, часовой пояс `Europe/Samara` (UTC+04), 25 м, 8 дорожек. Создаются собственные шаблоны четырёх дисциплин и опубликованный демо-регламент, необходимые существующему API для создания события. Взнос равен нулю: импортированные заявки имеют `NOT_REQUIRED`; отметка оплаты родительской заявки в сценарии — демонстрационное действие без реального платежа.

Дата — ближайшая суббота в Самаре, до начала утренней сессии; после 10:00 субботы берётся следующая. На неделе релиза это **17.10.2026**; сам показ проводится 15.10. Для фиксированной даты репетиции задайте `DEMO_DATE=2026-10-17`. Повторный запуск сохраняет дату существующего события; изменение даты требует сброса.

Ожидаемый успех: пять аккаунтов вместе с администратором, одна организация/площадка/событие, две сессии (10:00 и 15:00), четыре вида с группами 2014–2015, 2012–2013, 2010–2011, открытая регистрация, 200 заявок, 120 импортированных профилей, ноль заплывов. Сид печатает `eventId`, `publicSlug`, дату и сводку импорта. Исходные профили четырёх аккаунтов не входят в число 120.

## Повторный запуск и незавершённый импорт

```bash
npx tsx seed.ts                  # Повторить; сущности находятся по названию/email/коду.
npx tsx seed.ts --skip-import    # Подготовить структуру без вызова импорта.
```

Пользователи находятся по email посредством входа и `/auth/me`: API не имеет поиска пользователя по email. Неверный пароль существующего пользователя приводит к понятной ошибке, а не смене пароля. Роли проверяются через `/auth/me`, членство через `GET …/members`. Организация, площадка и событие находятся по точному названию, сессии по имени, дисциплины и шаблоны по коду. При нескольких совпадениях сид останавливается. Используйте один процесс сида на стенд: API не предоставляет атомарного upsert по названиям.

Повторный импорт использует штатную дедупликацию T05 по профилю/дисциплине (§5.4): 200 строк должны дать `created+updated+skipped=200`, без ошибок. Повторите сид и сравните число сущностей в UI: оно не должно расти. После частичного сбоя скрипт продолжает с найденных объектов. Он не исправляет вручную изменённые настройки: при расхождении сообщает о необходимости сброса. HTTP-запрос ограничен 15 с, общий бюджет запросов — 115 с; реальный критерий ≤2 мин необходимо измерить на собранном стенде.

Если эндпоинт отсутствует (404/405), вывод содержит «Эндпоинт не найден», метод и путь. `--skip-import` пропускает исключительно импорт и не подменяет недоступные эндпоинты T01/T03. Запуск без флага после готовности T05 загрузит Excel. Сообщения ошибок не печатают пароли, токены и тела ответов сервера.

## Зависимость параметров площадки

ТЗ §7 / T10 требуют `venue_meta={lanes:8,courseLength:25}`, но §5 не определяет DTO записи этих параметров, а `CreateVenueRequest`/`VenueResponse` текущего main их не содержат. Сид отправляет `venueMeta` объектом (camelCase существующих JSON DTO) и проверяет его через `GET /venues/{id}`. Backend должен принять, сохранить и вернуть это поле; иначе сид останавливается с объяснением, без обхода API и без ложного сообщения об успехе. Это открытый вопрос контракта, требующий согласования с backend-потоком. Ошибку нельзя устранить `--skip-import`.

## Сброс между прогонами

```bash
npx tsx reset.ts
```

В текущем API и ТЗ нет `DELETE /events/{id}`. Поэтому `reset.ts` только находит и проверяет точное демо-событие через API, затем выводит команду SQL для оператора с его UUID. Он **не удаляет данные сам**. Не вызывается выдуманный DELETE и нет SQL-сидинга.

Перед сбросом остановите приложение и фоновые обработчики, снимите резервную копию. В отдельном окружении оператора задайте `DEMO_DATABASE_URL` (URL подключения к PostgreSQL; не коммитить), выполните **команду, выведенную reset.ts**:

```bash
psql "$DEMO_DATABASE_URL" -v ON_ERROR_STOP=1 -v demo_event_id=<UUID-из-reset> -f reset.sql
```

`reset.sql` рассчитан на V020–V026, выполняется одной транзакцией и ограничен одновременно UUID, названием события, названием организации и площадки. Он удаляет связанные результаты, дорожки, заплывы, live-состояние, журналы правил/событий, платежи, заявки, дисциплины, сессии и событие; осиротевшие импортированные профили удаляются только при `user_id IS NULL` и отсутствии заявок на другие события. Служебные аккаунты, профили с аккаунтом, организация, площадка и шаблоны сохраняются. При несовпадении или повторном сбросе — без удаления. Затем запустите приложение и сид. SQL-сброс нужен **до показа**, не во время сквозного прогона US-1…US-7.

## Проверки

```bash
npm test
npm run typecheck
npx tsx seed.ts --help
npx tsx reset.ts --help
```

Vitest проверяет тела запросов, multipart, роли/членство, даты, сессии, группы, обработку 404/405, повторный запуск и восстановление после частичного сбоя. Все тесты без сети. Проверки репозитория: `cd sport-platform && mvn -q test`, затем `cd frontend && npm run build && npm run lint`.

## Ручная приёмка после слияния зависимостей

1. На чистом демо-стенде включить сид и выполнить полный запуск с секундомером (≤2 мин).
2. Проверить перечисленные выше количества и отсутствие заплывов; повторить запуск и сверить неизменность количества.
3. Проверить вход в каждый аккаунт, доступ организатора к событию, секретаря/судьи к результатам; у родителя нет служебных прав.
4. Выполнить `reset.ts`, SQL-команду на демо-БД и снова сид; стороннее событие и его профили должны сохраниться.
5. Для начала показа с пустым списком заявок после сброса выполнить `seed.ts --skip-import`; импортировать M вживую на шаге 2 сценария.
6. Пройти сценарий и чек-лист 14.10, сохранить фактические времена и замечания. Наличие файлов сценария само по себе не означает успешную репетицию.
